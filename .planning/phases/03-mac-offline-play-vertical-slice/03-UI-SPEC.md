# Phase 3 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope of this contract:** the shared library/curation experience across BOTH clients this phase ships — the Phoenix LiveView console (plan 03-05) and the native Mac SwiftUI client (plans 03-06, 03-07, 03-09, 03-10). Per D-17, this is the one document both clients cite; SwiftUI/HEEx drift is the top long-term risk this file exists to prevent. Out of this contract's scope: exact preflight-remedy microcopy per blocking condition (plan 03-09 authors it against this contract's status vocabulary and tone), controller remap UI (plan 03-10), and the notarized-build first-run chrome (plan 03-10) — those plans extend this contract, they do not restate it.

This contract inherits and does not re-litigate Phase 1's console design system (`01-UI-SPEC.md`): the dark console surface, the semantic accent/destructive/success/warning roles, and the Inter/JetBrains Mono webfonts remain load-bearing for setup, login, pairing, and devices. Phase 3 adds two new, deliberately disjoint color vocabularies (system identity, status ladder) that live alongside — never replace — Phase 1's roles, and extends the type scale and spacing scale to the native Mac client for the first time.

## Design System

| Property | Value |
|----------|-------|
| Tool | none — Phoenix LiveView console + native SwiftUI/AppKit client; the shadcn gate does not apply to either stack |
| Preset | not applicable |
| Component library (console) | Phoenix 1.8 CoreComponents + Tailwind CSS utility classes (unchanged from Phase 1) |
| Component library (Mac) | SwiftUI native controls + a small hand-built `Design/` token module (`DesignTokens`, `SystemAccent`, `StatusToken`) — no third-party UI kit |
| Icon library (console) | Heroicons — outline for default/quiet state, solid for active/filled state (unchanged from Phase 1) |
| Icon library (Mac) | SF Symbols, matched glyph-for-glyph to the Heroicons names used on the console per the mapping table below, so both clients name the same concept the same way in code review even though the rendered glyph sets differ per platform convention |
| Font (console UI) | `Inter, ui-sans-serif, system-ui, sans-serif` (unchanged, self-hosted per Phase 1) |
| Font (Mac UI) | SF Pro (`Font.system`, the platform default) — the one deliberate cross-platform divergence in this contract. Native Dynamic Type, VoiceOver, and Bold Text accessibility settings depend on the system font; bundling Inter into the Mac client would silently break them. Both fonts are matched to the identical 4-role point/pixel scale below so a screenshot comparison reads as "the same app," not "a port." |
| Font (codes, console only) | `"JetBrains Mono"` — unchanged from Phase 1, not used anywhere in this phase's new surfaces |

Rationale: this phase is the first to add a native Mac client to a design system that, until now, existed only as a Phoenix/Tailwind contract. Rather than inventing a second, unrelated visual language, this contract keeps Phase 1's spacing unit, type scale, and weight discipline as the cross-platform spine, and adds exactly two new color vocabularies scoped to what D-12/D-13 actually require: system identity and content status. Nothing here reopens Phase 1's login/setup/devices surfaces.

## Spacing Scale

Declared values (must be multiples of 4), unchanged from Phase 1, now binding on the Mac client too (1pt = 1px at the SwiftUI layout level; no additional platform scaling is applied):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps, chip inline padding, glyph-to-count gaps |
| sm | 8px | Compact element spacing (meta line chip gaps, card internal micro-gaps) |
| md | 16px | Default element spacing (card internal padding, filter chip row gaps) |
| lg | 24px | Section padding (shelf heading to shelf content, sidebar section gaps) |
| xl | 32px | Layout gaps between major page regions (sidebar to content, shelf to shelf) |
| 2xl | 48px | Major section breaks (Home's shelf stack rhythm) |
| 3xl | 64px | Page-level spacing (content inset from window chrome) |

Exceptions:
- Every icon-only control (favorite toggle, queue add/remove, pin, filter chip, sidebar disclosure) uses a 44×44px minimum interactive target on both platforms — the QUAL-01 accessibility floor and the practical minimum for controller/touch-adjacent pointing, not a spacing-scale violation since the extra area is hit-target padding around a smaller visible glyph. Every such control carries an accessible name equal to its action verb plus its subject (`aria-label="Add {title} to Favorites"` on the console; `.accessibilityLabel("Add \(title) to Favorites")` on the Mac client) — never satisfied by a tooltip or `title` attribute alone.
- Game card tiles are a fixed size, not derived from the spacing scale: 280×158px (landscape, 16:9-adjacent — see Typography for why this ratio) in the shelf/grid view, with the three anatomy zones (title, meta line, status slot) laid out inside that fixed box using the scale above. Fixed size is deliberate: D-16 requires zero skeletons and stable row heights for a 500-item library, which is only possible if tile geometry never depends on content length.

## Typography

Both clients share one 4-role scale, unchanged in size/weight/line-height from Phase 1 — this phase does not add a 5th size or a 3rd weight:

| Role | Size | Weight | Line Height | Usage this phase |
|------|------|--------|-------------|-------------------|
| Body | 16px | 400 (regular) | 1.5 | Empty-state body copy, search-result explanations, collection descriptions |
| Label | 14px | 400 or 600 | 1.5 | Meta-line chips (400, muted color — quiet by design), sidebar entries and status list-view text labels (600) |
| Heading | 20px | 600 (semibold) | 1.2 | Card title (two-line clamped), shelf headings, collection names |
| Display | 28px | 600 (semibold) | 1.2 | Home page title, empty-state headings |

Only 2 weights exist system-wide: 400 regular and 600 semibold. Weight is chosen per element by intent (chips are quiet → 400; titles and labels that anchor navigation → 600), never by role alone — this is why Label appears at both weights above, and it is the only role that does.

**Card title clamping:** exactly 2 lines, `-webkit-line-clamp: 2` / `lineLimit(2)` with `.truncationMode(.tail)`, no tooltip-on-truncate — a two-line title is long enough that a third line would rarely add information, and neither client shows hover tooltips on a controller-first surface.

**System monogram:** the Heading role at 600 weight, uppercase, 0.04em letter-spacing (matching Phase 1's precedent for code-like short strings that must be scanned quickly), rendered from the frozen `Formats.SystemId` registry, never a designer-chosen abbreviation:

| System id | Monogram | Display name (for meta-line, sidebar, and accessible names) |
|-----------|----------|----------------------------------------------------------------|
| `gba` | GBA | Game Boy Advance |
| `gb` | GB | Game Boy |
| `gbc` | GBC | Game Boy Color |
| `nes` | NES | NES |
| `snes` | SNES | Super Nintendo |
| `md` | MD | Sega Genesis |
| `psx` | PSX | PlayStation |
| `unknown` | ? | Unidentified |

## Status Vocabulary & Priority Ladder

This is the single most safety-critical contract in this phase (D-13, D-17) — both clients implement it from this table with no local invention. A card renders **exactly one** status slot. When more than one condition applies simultaneously, the highest-ranked row wins; lower-ranked conditions are not shown anywhere on the card.

| Rank | State | Glyph (Heroicons / SF Symbols) | Badge shape | Color | List-view text label | Accessible name template |
|------|-------|----------------------------------|-------------|-------|------------------------|----------------------------|
| 1 (highest) | Needs attention | `exclamation-triangle` (solid) / `exclamationmark.triangle.fill` | Triangular badge | `--status-attention` | "Needs attention" | "{title} needs your attention." |
| 2 | Missing dependency | `wrench-screwdriver` (solid) / `wrench.and.screwdriver.fill` | Hexagonal badge | `--status-missing-dependency` | "Missing dependency" | "{title} is missing something it needs to play." |
| 3 | Downloading | determinate progress ring (no static glyph) / `ProgressView` circular determinate style | Circular ring, no fill | `--status-downloading` | "Downloading — {percent}%" | "{title} is downloading, {percent} percent complete." |
| 4 | Queued | `clock` (outline) / `clock` | Rounded-square badge | `--status-queued` | "Queued" | "{title} is queued to download." |
| 5 | Pinned (verified + pinned) | `map-pin` (solid) / `mappin.circle.fill` | Teardrop/pin silhouette, no separate badge container | `--status-pinned` | "Pinned" | "{title} is pinned and ready to play offline." |
| 5 | Verified (verified, not pinned) | `check-circle` (solid) / `checkmark.circle.fill` | Circular badge, filled | `--status-verified` | "Ready offline" | "{title} is downloaded and ready to play offline." |
| 6 (lowest) | Server-only | `cloud` (outline) / `icloud` | Cloud silhouette, no badge fill | `--status-server-only` | "On server" | "{title} is on your server. Choose Download to play it offline." |
| — (storage view only, never a card rank) | Safe to evict | none on the card; storage-view row uses a plain text label, no glyph | — | `--status-safe-to-evict` | "Safe to remove" | "{title} can be removed to free up space — it will stay on your server." |

Rank 5 has two mutually exclusive glyphs at the same ladder position: pinned always implies locally verified (D-21 — pin requires the content already be downloaded), so a pinned item never separately shows the verified glyph. A verified-but-unpinned item shows the check-circle. Nothing else on the ladder has this two-glyph-one-rank exception.

**Derivation, not storage:** exactly as D-21 specifies, no client ever persists a status enum. The ladder rank is computed at render time from (queue row presence and its progress fraction, partial-file presence, CAS/verified-record presence, pin flag). A stored status column is a bug, not an optimization — it can drift from disk truth.

**Server-only primary action (D-17, verbatim requirement):** a server-only card's primary action is a button labeled **"Download"** — never a disabled or grayed-out "Play" control. Play only ever appears, enabled, after CACH-04's full preflight passes.

## Navigation & Information Architecture

One canonical sidebar/source-list order, identical on both clients (D-14):

1. **Home** — the default landing view; renders the Continue, Favorites, Collections, Queue, Recent, and (if the server has nothing imported) the calm import-invitation state, plus the recommended-first-downloads shelf on a newly paired device.
2. **Continue**
3. **Favorites**
4. **Collections**
5. **Queue**
6. **Recent**
7. **Systems** — only systems with at least one asset set, listed in the frozen registry order (`gba, gb, gbc, nes, snes, md, psx`) filtered to non-empty, never alphabetically re-sorted and never including a system with zero content
8. **Unidentified** — always last, always present once at least one unrecognized asset set exists; hidden entirely (not shown as an empty entry) when there are none, since "unidentified" is itself a status rather than a curated noun a user chose

Home and Continue are two separate sidebar entries, not a merged one — the plan-level acceptance criteria (03-05, 03-06) both assert this literal 8-step order and a test regression here is a contract violation, not a style nit.

**Search and filters:** free-text search matches display title and original filename (case- and diacritic-insensitive). Filter chips narrow by system and by availability (the six card-eligible ladder states, minus the pin/verify split — filtering treats pinned and verified as one "ready offline" availability value since that is what a user is actually choosing between). On a controller, chips are the only search surface in this phase — no on-screen keyboard is offered (explicitly deferred, see CONTEXT.md Deferred Ideas); a controller user narrows by system and availability chips and switches to keyboard/pointer for free text.

**Show all systems:** systems with zero asset sets are hidden behind one control. Its label always states the count: **"Show all systems ({N} hidden)"**; once expanded, the same control reads **"Hide empty systems"**. This is LIBR-04's literal mechanism — hiding is driven by emptiness, never by a persisted user preference toggle.

**Advanced settings placement:** adapter, BIOS, and controller settings do not appear anywhere in library chrome (sidebar, shelves, filters). They surface only contextually — as links from a game's detail view when a download or launch first needs them, and as remedies inside the readiness view plan 03-09 builds. This document does not specify that readiness-remedy copy; it only establishes that library browsing stays free of it.

## Motion & Focus Specification

Directly implements D-16. Motion exists only to explain a state change; nothing here is decorative.

| Interaction | Behavior | Duration | Reduced-motion behavior |
|---|---|---|---|
| Focus move (keyboard/controller) | Directional focus ring slides to the newly focused element | ~120ms, ease-out | Unchanged — a focus ring is not motion in the sense reduced-motion disables; it always renders instantly regardless |
| Download progress | Determinate ring fills continuously as bytes verify | Continuous, tied to actual progress, no artificial easing | Ring fill is retained — it carries information, not decoration |
| Download completion | Ring morphs into the verified check-circle (or pin, if the item is also pinned) | ~250ms crossfade | Replaced with an instant swap — no morph animation, same end state |
| Status change (any ladder transition, e.g. queued → downloading) | In-place crossfade of the status slot's glyph and badge | ~150ms | Replaced with an instant swap |
| Eviction (verified → server-only) | In-place crossfade to the cloud glyph; the card itself never disappears or re-flows the grid | ~150ms | Instant swap; the "item never vanishes" rule holds regardless of the motion setting |
| Shelf/grid scroll | Native platform scroll only | N/A | N/A |

Explicitly prohibited on both clients, with or without reduced motion: ambient tile motion (idle bounce, breathing, shimmer), staggered fly-in on shelf load, marquee/scrolling titles, and any full-page loading skeleton on a view whose data is already local (console: post-mount LiveView stream; Mac: post-sync SQLite read). A skeleton implies data has not arrived; on a synced view it has, so a skeleton would be a placeholder for nothing and is treated as a contract violation, not a stylistic choice.

**Reduced-motion detection:** console reads `prefers-reduced-motion: reduce` via CSS media query, gating the transition/animation declarations directly (no JS branch needed for the swap-to-instant behavior). Mac reads `NSWorkspace.shared.accessibilityDisplayShouldReduceMotion` (or the SwiftUI `accessibilityReduceMotion` environment value) and branches the same way.

## Accessibility Floor (QUAL-01)

Binding on both clients for every library, curation, search, and browse surface this phase ships (readiness/controller-remap flows are plan 03-09/03-10's own accessibility floor, built on this same foundation):

- **Keyboard/controller parity:** every interactive element (favorite toggle, queue add/remove/reorder, collection create/rename/delete/reorder-member, search field, filter chips, show-all-systems, sidebar navigation, card selection) is reachable and fully operable without a pointer. A controller disconnecting mid-session never strands the user in a state only a controller can exit — keyboard and pointer remain live at all times, they are not "activated" only on controller loss.
- **Visible focus:** every focusable element shows the shared `#38BDF8` focus ring (console: CSS `:focus-visible`; Mac: SwiftUI `.focused()` + a custom ring overlay, since AppKit's default focus ring does not match this token). Focus never becomes invisible on a dark surface.
- **Screen reader / VoiceOver semantics:** every card exposes one accessible name combining title, system display name, and the status ladder's accessible-name sentence — e.g. "Metroid Fusion, Game Boy Advance, downloaded and ready to play offline." Decorative elements (the monogram glyph itself, badge shapes) are marked presentational/hidden from the accessibility tree since their meaning is already carried in the combined name.
- **No color-only state:** already covered by the Status Ladder table's glyph+shape+color triad and the filter chips' pressed-state accessibility trait (not color alone).
- **Reduced motion:** covered above.
- **Text scaling:** the Mac client respects Dynamic Type up to at least the "Large" accessibility size for Body and Label roles without truncating below what the card's fixed geometry can show two full lines of; the console relies on standard browser zoom, which Tailwind's `rem`-based type scale already supports without additional work this phase.
