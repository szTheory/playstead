<objective>
Deliver LIBR-03 on the Mac: all five curation nouns usable offline, expressed as per-row idempotent intents in a durable outbox that reconciles through the change journal when the server returns, plus coarse play-session reporting that can never affect a launch.

Purpose: curation that only works online is curation the user cannot trust on a plane, and an offline edit that is silently dropped when a second device also edited is worse than no sync at all. The intent-plus-journal shape is what prevents both.
Output: outbox, curation intents, the five curation surfaces in the Mac client, and play-session reporting.
</objective>

    - Favoriting while offline writes an outbox entry and updates the local read model immediately.
    - The favorite persists across an application restart while still unsent.
    - When the server becomes reachable, the entry sends once, receives success, and is marked done.
    - Replaying an entry whose response was never observed produces no second row on the server.
    - A permanent rejection reverts the local row and surfaces the server's problem code to the user.
    - A transient failure retries with backoff and does not revert the local row.
    - Entries send in the order they were created.
    - A favorite created on the console arrives through the journal without any outbox entry existing.
  </behavior>
  <action>
Add an `outbox_entries` migration holding a client-generated identifier, an intent kind, a JSON payload, an idempotency key, a state covering pending, in-flight, done, and rejected, an attempt count, the created-at timestamp, and the last error code.

`CurationIntent` models one mutation as an enumeration with an associated payload whose field names match the server changeset fields from plan 03-04 exactly. Each intent carries the client-generated row identifier that is also the row's natural key on the server, and an idempotency key derived from that identifier and the intent kind. This is the Phase 1 mechanism unchanged: the natural key makes a repeat insert converge, and the idempotency key makes a repeat request return the first response.

`Outbox` enqueues, lists in creation order, and transitions entries inside transactions. `OutboxWorker` is an actor that drains pending entries one at a time while reachable, marking in-flight before the request and resolving afterwards. A transport failure or a five-hundred-class response retries with exponential backoff and leaves the local row alone, because the mutation may well have succeeded. A four-hundred-class rejection other than the idempotency conflict is permanent: revert the optimistic local row, mark the entry rejected with its problem code, and show it. Discarding a rejected intent silently would mean the user's library quietly differs from what they asked for, which is the specific failure this whole mechanism exists to avoid.

Apply every intent to the local read model optimistically before sending, so the interface never waits on the network for a favorite. The authoritative row still arrives later as a journal entry through the existing applier; because both the local write and the journal apply are upserts keyed on the same client-generated identifier, the reconciliation is a no-op rather than a duplicate.

Build `FavoritesViewModel` and `FavoritesShelfView` over this path as the first noun, reading from `CurationStore` and writing through `Outbox`.

  <action>
`PlaySessionRecorder` observes the adapter host's launch and exit events and records a session carrying a client-generated identifier, the asset set id, a start time, and an end time. Nothing else: no input capture, no frame or performance data, no per-session device detail beyond what the device credential already establishes. Recent and Continue are the only two things this data exists to produce.

Delivery is through the outbox after the fact. Batch pending sessions into one request per drain cycle when more than one is waiting, since the endpoint is idempotent per session identifier and a batch reduces wakeups on a machine that has been offline for a while; individual posting remains correct and is the fallback when a batch is partially rejected.

The recorder subscribes to the adapter host's published events and never sits between the user's action and the launch. There is no code path in which starting a game reads, writes, awaits, or checks a play-session record — a launch that failed because a usage-reporting write failed would be the least defensible failure this product could have.

Let the user see and delete pending and delivered sessions from the Recent shelf; a deletion enqueues the corresponding delete intent.
