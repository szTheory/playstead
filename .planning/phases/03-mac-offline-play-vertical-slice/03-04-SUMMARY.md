# Phase 3 Plan 04: Server-Canonical Curation Summary

**Six curation tables (favorites, collections, collection members, queue items, continue dismissals, play sessions) riding Phase 1's change-journal/snapshot/idempotency spine through one new `curation` entity kind, a base-36 fractional-index ordering module, and per-row idempotent REST intents.**

## Performance

- **Duration:** ~55 min
- **Tasks:** 3
- **Files created:** 22
- **Files modified:** 7
- **Server test suite:** 846 tests, 0 failures (up from 797 before this plan)

## Accomplishments

- Favorites, Collections, the play queue, Continue dismissals, and coarse play sessions are all server-canonical, per-user, and synced through the existing D-21 recovery spine via one additive `curation` entity kind (D-08) and a `curation` snapshot branch read inside the same transaction as `catalogue` and `job`.
- `Playstead.Curation.Position` implements base-36 fractional-index ordering: cheap amortized-O(log n) append/prepend via digit increment/decrement-with-carry, exact midpoint bisection for genuine insert-between, `needs_rebalance?/2` as a proactive precision-budget signal, and `spaced/1` for even redistribution.
- All mutations are per-row idempotent REST intents under `/api/v1/curation/*` and `/api/v1/play-sessions`, Idempotency-Key gated, converging on natural keys via `on_conflict` upserts. Move intents name their own two neighbours; a client that submits a whole ordered list as truth is rejected outright (D-09's no-silent-loss invariant).
- Recent and Continue are honest derived-on-read views over coarse play sessions -- never stored, never gating a launch. A compact `recent` journal summary is re-derived and re-journaled per game on every session record/delete.
- D-10's sanity caps (500 collections, 5000 members/collection, 500 queue items) are enforced with the registered `curation_limit_exceeded` problem code.
- Every context function is scoped to the calling user; a request naming another user's row, asset set, or move-neighbour returns 404.

## Decisions Made

- **`curation` is a deliberate, logged additive amendment to the "frozen" six-kind `EntityKind` list**, made in Phase 3 before any client ships (D-08). The freeze's protected property — no unregistered kind can be written — survives an additive registration made now; the same addition after a client ships would need capability gating instead.
- **Fractional-index append/prepend uses increment/decrement-with-carry, not repeated bisection toward an open bound.** The first implementation bisected `between(low, nil)` toward a `36^len` ceiling on every append, which needed hundreds of characters of precision after only a few hundred sequential appends and overflowed the `varchar(255)` position column. The fix generates the next value by incrementing the position's last digit (extending with a fresh low digit only when that digit is maxed), giving amortized O(log₃₆ n) growth — matching how real fractional-indexing libraries handle sequential append.
- **`Position.between/2` never fails**; `needs_rebalance?/2` is a separate proactive signal (simulating precision growth up to a budget) that callers check before a tight insert, rather than a hard failure path `between/2` itself enforces.
- **Recent/Continue are computed on read, never stored**, per D-10 — "Curation is user-directed before it is algorithmic." The journal only carries a compact `recent` summary per game so a resuming client can reconstruct the shelf from the journal alone.
- **Move intents accept only two neighbour ids, never a whole ordered list.** The controller explicitly rejects an array-shaped JSON body (`%{"_json" => [...]}`) with the registered `validation_failed` code before it ever reaches the idempotency receipt, so a malformed request doesn't consume the client's Idempotency-Key.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `SnapshotController` never rendered the branches `Snapshot.read/2` already computed**
- **Found during:** Task 1 (writing the curation snapshot-branch controller test)
- **Issue:** `GET /api/v1/snapshot`'s JSON response only included `entries`/`cursor`/`has_more`/`next_after_id` — the `catalogue`, `job`, and (new) `curation` maps `Snapshot.read/2` returns were computed and then silently dropped before serialization. This predates this plan; it just happened to have no test asserting the catalogue/job payload contents to catch it.
- **Fix:** Added `catalogue`, `job`, and `curation` keys to the controller's JSON response.
- **Files modified:** `playstead-server/lib/playstead_web/controllers/api/v1/snapshot_controller.ex`
- **Verification:** `curation_controller_test.exs`'s snapshot tests and `snapshot_test.exs` assert on `page.curation`/`page.catalogue`/`page.job` directly against the context function; the controller test additionally exercises the HTTP JSON body.
- **Committed in:** `7a6c529` (Task 1 commit)

**2. [Rule 1 - Bug] `on_conflict` upsert with a client-supplied primary key silently returned the caller's own id, not the converged row's id**
- **Found during:** Task 1 (repeated-favorite-intent test)
- **Issue:** `Ecto.Multi.insert` with `on_conflict: {:replace, [:updated_at]}` and a non-autogenerated `binary_id` primary key hands back the *submitted* changeset struct unless `returning: true` is set — Ecto has no autogenerated field to force a re-read. On a genuine conflict, the caller got back its own newly-generated `id` instead of the pre-existing row's, defeating "a repeated intent converges on one row."
- **Fix:** Added `returning: true` to every natural-key upsert (favorites, collection members, queue items), mirroring the identical, already-documented fix in `Playstead.Pairing.insert_credential/3` (D-20b).
- **Files modified:** `playstead-server/lib/playstead/curation.ex`
- **Verification:** "repeating the identical favorite intent" / "re-enqueuing" / "re-adding a member" tests assert the second call's row id equals the first's.
- **Committed in:** `7a6c529` (Task 1 commit)

**3. [Rule 1 - Bug] Naive fractional-index append overflowed `varchar(255)` after a few hundred sequential inserts**
- **Found during:** Task 2 (the 5001-member cap test)
- **Issue:** `Position.between(low, nil)` (used by every "add to end of list" call) bisected toward an implicit `36^len` ceiling on each append. Because the ceiling recedes only by doubling relative headroom rather than resetting, growth is roughly one new digit every ~17 appends instead of ~35 — around 300 characters were needed for 5000 sequential enqueues/collection-member-adds, exceeding the `varchar(255)` position column and raising a Postgres truncation error.
- **Fix:** Replaced the bisect-toward-ceiling approach with increment/decrement-with-carry (see Decisions above), giving amortized O(log₃₆ n) growth — a few characters suffice for tens of thousands of sequential appends.
- **Files modified:** `playstead-server/lib/playstead/curation/position.ex`
- **Verification:** `position_test.exs`, and `collections_test.exs`'s 5000-member-cap and 200-item property tests, all pass without column truncation.
- **Committed in:** `734683e` (Task 2 commit)

**4. [Rule 1 - Bug] Comparing a usec-precision `PlaySession.inserted_at` against the journal's second-precision as-of time could wrongly exclude a same-second session**
- **Found during:** Task 3 (curation-snapshot-contains-`recent` test)
- **Issue:** `Sync.Entry.inserted_at` is `:utc_datetime` (second precision); `PlaySession.inserted_at` is `:utc_datetime_usec` (D-07's deterministic-burst-ordering requirement). A session inserted later within the *same second* as the pinning journal entry has a later microsecond value, so a plain `<=` comparison against the truncated `as_of_time` incorrectly excluded it from the `recent` branch.
- **Fix:** `fetch_recent/2` compares against the end of that second (`as_of_time + 1s`, exclusive) instead of the truncated instant itself — this can only include rows that existed by `as_of_time`'s real-world instant, never rows from a later second.
- **Files modified:** `playstead-server/lib/playstead/sync/snapshot.ex`
- **Verification:** "the curation snapshot branch contains recent and continue_dismissal entries" test in `continue_test.exs`.
- **Committed in:** `847e194` (Task 3 commit)

**5. [Rule 3 - Blocking] Test-suite connection-pool contention from the change journal's global advisory lock**
- **Found during:** Task 3 (full-suite run after adding `continue_test.exs`)
- **Issue:** `ChangeJournal.write/5` serializes every write behind one fixed `pg_advisory_xact_lock` key — a deliberate, documented single-owner-server simplicity tradeoff (see `ChangeJournal`'s moduledoc). Running this plan's write-heavy curation test files (`favorites_test.exs`, `queue_test.exs`, `collections_test.exs`, `continue_test.exs` — several with hundreds of sequential mutations) with `async: true` alongside each other caused enough real lock-wait contention to exceed Ecto's 15-second connection-ownership timeout in a full-suite run.
- **Fix:** Marked those four test files `async: false`; they still run in parallel with the rest of the suite's unrelated async files, just not against each other.
- **Files modified:** `playstead-server/test/playstead/curation/{favorites,queue,collections,continue}_test.exs`
- **Verification:** Full suite (846 tests) passes with 0 failures and no connection-ownership timeouts.
- **Committed in:** `734683e` (queue/collections), `847e194` (continue); `favorites_test.exs`'s flag flip is also in `847e194`.

**6. [Rule 3 - Blocking] Plan referenced `playstead-server/lib/playstead/sync/catalogue_payload.ex`, which doesn't exist**

- **Fix:** Ran the acceptance grep against the real path instead; confirmed zero matches (curation payload logic lives entirely in the new `Playstead.Sync.CurationPayload`, never in the catalogue payload).
- **Files modified:** None (verification-only adaptation).
- **Verification:** `grep -rn 'curation' playstead-server/lib/playstead/catalogue/payload.ex` returns no matches.
- **Committed in:** N/A (no code change)
