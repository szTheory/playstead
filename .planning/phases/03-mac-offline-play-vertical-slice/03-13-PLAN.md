<objective>
Close the actionable half of the LIBR-02 gap recorded in `03-VERIFICATION.md`: the console's availability filter discriminates only 2 of its documented values and lets every other value fall through unfiltered.

Two things have to be true before that filter can be honest, and this plan delivers both:

1. **The console must have something true to filter on.** `library_live.ex`'s `status_for/2` today computes exactly one fact - whether a game is in the play queue - and its own comment says so: local download state is Mac-client-local and "not tracked here." The server therefore cannot distinguish downloading from ready-offline from missing-a-dependency for any game, which is *why* four of the values fall through. A chip that exists over a fact the server does not have would be a dead chip, which is worse than the current gap. This plan adds the missing read model: each paired device reports its own per-asset availability facts; the server stores them per device and merges them per user at read time.
2. **The filter must discriminate every value with no catch-all.** The current `matches_availability?(_entry, _other, _queue_ids), do: true` clause is exactly the defect. It goes away and is replaced by a clause per vocabulary value plus an explicit rejection path for anything not in the vocabulary.

**Which six values.** `03-VERIFICATION.md` names the four missing states using the Mac client's `CACH-02` vocabulary (`partial`, `verified-local`, `pinned-offline`, `safe-to-evict`). The locked design contract says something different, and this plan follows the locked contract: `03-UI-SPEC.md` (Navigation & Information Architecture, "Search and filters") specifies the console's availability chips as "the six card-eligible ladder states, minus the pin/verify split - filtering treats pinned and verified as one 'ready offline' availability value," and `03-CONTEXT.md` D-13 states that safe-to-evict "is a storage-view concept, never a card badge." The six console filter values are therefore: `needs_attention`, `missing_dependency`, `downloading`, `ready_offline`, `queued`, `server_only`. The mapping back to the `CACH-02` vocabulary the verifier used is: `serverOnly` to `server_only`, `queued` to `queued`, `partial` to `downloading`, `verifiedLocal` plus `pinnedOffline` to the merged `ready_offline`, and `safeToEvict` deliberately not a console chip (it stays in the Mac storage view, where `AvailabilityState.deriveForStorageView` already implements it). `needs_attention` and `missing_dependency` are the two ladder values the `CACH-02` list does not contain. **This disagreement with the verifier's wording is deliberate, is surfaced here rather than resolved silently, and is the first item put to the owner in Task 1's checkpoint.**

The Mac client's `AvailabilityState.derive` is NOT changed by this plan and is NOT the source of the console's filter. It stays the Mac-local derivation `CACH-02` verified. The console derives its own rank through `StatusSlot.describe/2`, which is already the single status vocabulary for this surface (D-13, D-17) - so there is one ladder implementation on the server, not a second copy of the Mac one.

Purpose: make "find a game by availability or readiness state" true in the console for every value it offers, over facts that are actually true.
Output: a device-reported availability read model, a frozen six-value filter vocabulary shared across both codebases, and a console filter that discriminates all six with no pass-through.

**Scope fence.** This plan is server-side only. The Mac client side of the report (the code that actually sends the facts), the UAT tally defect, and every documentation and requirement flip belong to `03-14-PLAN.md` and must not be touched here. `LIBR-02` stays unchecked in `REQUIREMENTS.md` at the end of this plan. `PLAY-04` (physical controller) and `LIBR-05` (find-a-game UX review) are human-verification items and are not advanced by this plan; `03-14-PLAN.md` records why.
</objective>

ASVS enforcement level: 1. Blocking severity: high.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser LiveView event -> server filter logic | `phx-value-availability` is entirely client-controlled and reaches filter code on every click |
| paired device -> availability report endpoint | A device-authenticated client asserts facts about content it claims to hold; the server cannot independently confirm them |
| one user's devices -> another user's console | Reported rows are per-device and per-user; a scoping miss would leak one household member's library state to another |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-13-01 | Denial of Service | `handle_event("filter-availability", ...)` | high | mitigate | The client value is compared against a frozen list of binaries and never converted to an atom; an acceptance criterion greps the LiveView and the controller for dynamic atom conversion and requires a count of zero. Unbounded atom creation from client input exhausts a non-garbage-collected table and takes the node down |
| T-03-13-02 | Information disclosure | `Playstead.Availability.facts_for_user/1` | high | mitigate | Every query is scope-first and filtered by `user_id` per the project's existing context convention; `replace_for_device/2` filters entries to asset sets owned by `device.user_id` before insert, so a device cannot write a row about content it has no right to name |
| T-03-13-03 | Spoofing | availability report endpoint | medium | accept | A device can assert it holds content it does not hold. Accepted: the console is a convenience view, the launch path never consults it, and the Mac client's own `AvailabilityState.derive` remains the authority for whether a game can actually start. Recorded as a prohibition so no future plan promotes this read model onto the launch path |
| T-03-13-04 | Denial of Service | report payload size | high | mitigate | `replace_for_device/2` rejects a report above a bounded entry count outright rather than streaming it into a transaction, and the percent field is range-checked rather than clamped |
| T-03-13-05 | Tampering | full-replacement semantics | medium | mitigate | The delete and insert run inside one `Ecto.Multi` transaction, so a failed report cannot leave a device with a partially-cleared row set that reads as "nothing is downloaded" |
| T-03-13-06 | Repudiation | reported facts presented as fact | medium | mitigate | `reported_at` is stored per row so a stale report is distinguishable from a current one, and no rank is stored - the rank is re-derived on every render per D-21 |
| T-03-13-07 | Elevation of Privilege | new router scope | high | mitigate | The new scope copies the device-authenticated pipeline list from the existing `/api/v1/play-sessions` scope verbatim rather than declaring its own; a controller test asserts an unauthenticated request is refused |
| T-03-13-SC | Tampering | npm / pip / cargo installs | low | accept | This plan adds no package-manager install task and no new dependency, so the package-legitimacy gate has nothing to audit |
