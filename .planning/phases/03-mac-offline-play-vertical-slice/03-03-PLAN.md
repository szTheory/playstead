  <behavior>
    - A fresh download of a fixture blob commits an object whose SHA-256 equals the expected digest and whose path matches the CAS layout.
    - A download cancelled after N bytes leaves a partial file of exactly N bytes and no committed object.
    - Resuming that transfer issues `Range: bytes=N-` and `If-Range: "<sha256>"` and commits an object byte-identical to the uninterrupted result.
    - When a resumed request is answered 200 rather than 206, the partial file is truncated to zero and the transfer restarts.
    - A stream whose final digest differs from the expected sha256 commits nothing and the partial is quarantined rather than committed.

  <action>
`CASManager` mirrors the server's content-addressed layout from D-20: an object for digest `d` lives at `objects/<d[0..1]>/<d[2..3]>/<d>`. It exposes `objectURL(for:)`, `contains(_:)`, `commit(partialAt:sha256:)` implemented as an atomic same-volume rename after verification, and `quarantine(partialAt:reason:)` which moves a failed partial aside without deleting it.

`StreamingSHA256` wraps CryptoKit's incremental `SHA256` with `update(data:)` and `finalizeHex()`, plus a `resume(from:)` that re-reads an existing partial file from byte zero in bounded chunks. Per D-18 there is no serialized mid-stream hash state: a crash between a byte write and a state write would desynchronize the state from the disk, so the on-disk prefix is always the source of truth and is re-hashed on every resume. Re-hashing a large prefix at local disk speed is measured in a second or less and is the cheaper side of that trade.

`DownloadEngine` is a Swift `actor` running exactly one transfer at a time over the in-process `URLSession.bytes(for:)` API. Per D-18 it does not use a background session: background resume machinery ignores custom `Range` request headers, its resume data is opaque, and the system may purge its temporary files — none of which is acceptable when resume correctness is the requirement. Its `download(sha256:expectedSize:)` measures the existing partial's byte length, sends `Range: bytes=<len>-` and `If-Range` carrying the expected sha256 in double quotes when that length is greater than zero, and inspects the response status before writing a single byte.

Implement the 200-instead-of-206 guard as `RangeResumeDecision`: when a Range header was sent and the status is 200, the existing partial is truncated to zero length and hashing restarts from empty, because appending a full body onto an existing prefix produces a longer, corrupt file. When the status is 206, parse `Content-Range` and confirm its first byte position equals the partial's length before appending; a mismatch also restarts. A 416 means the client's notion of the size is wrong — discard the partial and restart. Retry on transport failure with exponential backoff and no attempt ceiling, since a queued-while-offline transfer is a normal state, not an error.

On stream completion, compare `finalizeHex()` against the expected digest. Only on equality call `CASManager.commit`; on inequality call `quarantine` and surface a `DownloadError.digestMismatch` carrying both digests.

`LaunchMaterializer.materialize(assetSet:members:)` builds `launch/<asset_set_id>/` and populates it from cache objects using `FileManager.copyItem(at:to:)`, which performs an APFS clone when source and destination are on the same volume and falls back to a full copy otherwise. Per D-20 it must never create a hard link: an emulator writing through a hard link would write through into the verified cache object and destroy the custody guarantee. Name each materialized file by its member's original filename so the emulator sees the layout it expects.

`PreflightChecker.check(assetSet:)` iterates the asset set's required members only and, for each, performs the cheap size, inode, and mtime comparison against the stored verify record, falling back to a full re-hash when that check does not match, and returning `ReadinessResult.blocked` with a `ReadinessBlocker` naming the specific member when a re-hash disagrees. Per CACH-04 this function issues no network request of any kind; the full remedy vocabulary is plan 03-09's work.

Write `DownloadResumeTests` and `MaterializationTests` against a local test HTTP server (or a `URLProtocol` stub) that can serve 206, 416, and a deliberate 200-on-resume, so every branch above is exercised without a live server.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server HTTP response → client disk | Response bytes and headers from a pinned but remote server are written to the local cache |
| cache object → emulator process | Verified bytes are handed to a third-party binary that may write back |
| pinned emulator binary → app | A separately signed external process is executed by the app |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-08 | Tampering | `DownloadEngine` commit path | high | mitigate | A partial is committed only after the full-stream SHA-256 equals the expected digest; a mismatch quarantines rather than commits; the 200-on-resume guard prevents a doubled-body corruption from ever reaching the hasher's success branch |
| T-03-09 | Tampering | `LaunchMaterializer` output | high | mitigate | Materialized files are clones or copies with distinct inodes, never hard links, so an emulator writing to its working file cannot alter the verified cache object; a test asserts inode distinctness and post-write digest stability |
| T-03-10 | Tampering | pinned emulator binary | high | mitigate | Digest re-verified against `AdapterPin.sha256` before every launch; the quarantine attribute is left intact so Gatekeeper evaluates the notarized third-party binary; the emulator is never embedded in the app bundle |
</threat_model>

<assumption_delta_decision>
Signals fired: `chosen` ("download only chosen verified content", "choose a game or collection for download") and `optional` ("without server, internet, metadata, achievements, or other optional services").

- **Noun now primary:** the *selected subset* of the library that exists locally, rather than the library as a whole.
- **Decision:** `promote`. The download selection is modelled as a first-class persisted row (the queue item and the CAS entry in plan 03-07), not as a filter over the catalogue. The catalogue mirror and the local cache are two separate stores from the tracer onward, and CACH-02's six states are derived from the relationship between them.
- **Rationale:** treating "cached" as a derived attribute of a catalogue row would collapse exactly the distinction CACH-02 requires the UI to show, and would leave nowhere to persist queue order, pin flags, or partial-transfer state.
- **Second signal (`optional`):** `promote`. The offline path is the primary path, not a degraded one — `PreflightChecker` is written network-free from the tracer forward rather than having network access removed later.
- **Suggested invariant test:** a preflight and launch test that runs with every network request stubbed to fail (already required by task 2's acceptance criteria).
</assumption_delta_decision>
