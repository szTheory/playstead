<objective>
Build the Mac client's sync engine and full library browse experience: a local read model kept converged with the server through the snapshot, journal, and cursor spine, and a typographic, controller-and-keyboard-navigable library over it.

Purpose: LIBR-01 requires the complete catalogue to be browsable on a newly paired Mac before any bytes exist locally, and LIBR-02 and LIBR-04 require finding things in it quickly without irrelevant surfaces in the way. Everything else in the client reads from this local model.
Output: `SyncEngine`, local catalogue and curation stores, and the library UI shell the download, curation, and readiness plans hang off.

Decisions implemented here: D-08 (the client consumes the new curation journal kind through the existing recovery spine), D-12 (typographic-first identity, landscape tiles, shelves plus sortable list, no fabricated artwork), D-13 (three-zone card, one status slot, strict priority ladder, safe-to-evict excluded from cards, no color-only state), D-14 (source-list order, per-shelf focus sections, shoulder cycling, filter-chip search on controller with no on-screen keyboard), D-15 (a newly paired Mac is not empty — full catalogue with cloud marks, one dismissible banner, nothing auto-downloads, show-all-systems with counts), D-16 (motion budget and reduced-motion behaviour, zero skeletons on synced views, lazy containers for 500-plus items), D-17 (this client and the console cite the same shared spec).
</objective>

  <behavior>
    - With an empty local store, sync fetches the snapshot, writes catalogue and curation rows, and stores the returned cursor.
    - With a stored cursor, sync calls the changes endpoint with it and applies only the returned entries.
    - An upsert entry inserts or updates one local row; a tombstone entry deletes it.
    - Applying the same entry twice leaves the row count and contents unchanged.
    - A cursor-expired problem response clears the local read model, refetches the snapshot, and ends with the server's row set and no duplicates.
    - A transport failure leaves the stored cursor unchanged and the previous read model intact.
    - A snapshot page indicating more pages continues from the returned continuation marker until exhausted.
  </behavior>
  <action>
Add migrations for `sync_cursor` (a single-row table holding the opaque cursor string and the last successful sync timestamp) and for the six curation tables mirroring the server's shapes from plan 03-04. `CatalogueStore` and `CurationStore` wrap reads and writes over these tables; all writes go through the `LocalStore` transaction helper so a partially applied page can never be observed.

`CursorStore` stores and returns the cursor verbatim. The cursor is signed and opaque by design; the client must never parse it, compare it, or synthesize one, because doing so would let a client fabricate an as-of position the server never issued and skip entries permanently.

`ChangesClient.fetch(after:)` calls the changes endpoint, decodes the entry array with entity kind, entity id, operation, payload, and sequence, and maps the cursor-expired problem code to a distinct `SyncError.cursorExpired` rather than a generic failure — this is the one error whose remedy is a reset rather than a retry.

`JournalApplier.apply(_:)` dispatches on entity kind. Catalogue entries update `CatalogueStore`; curation entries dispatch further on the payload's type field across favorite, collection, collection member, queue item, continue dismissal, and recent. An unknown entity kind or payload type is skipped and counted, not treated as an error, so an older client stays functional against a newer server. Every apply is written as an upsert keyed on entity id so replaying a page is a no-op, which matters because the client will replay after any interrupted apply.

`SyncEngine` is an actor with `syncNow()` that reads the stored cursor, bootstraps from the snapshot when there is none, otherwise pages the changes endpoint until caught up, and commits the new cursor only after the whole page has been applied. On `SyncError.cursorExpired` it clears the read model inside one transaction, refetches the snapshot, and stores the fresh cursor. It publishes a `SyncState` the UI observes, distinguishing never-synced, syncing, synced with a timestamp, and offline-since a timestamp. Being offline is a normal state and must read as one, not as a failure.

Cover every bullet of this task's `<behavior>` block in `SyncEngineTests` against a `URLProtocol` stub that can serve snapshots, change pages, a cursor-expired problem, and transport failures.
