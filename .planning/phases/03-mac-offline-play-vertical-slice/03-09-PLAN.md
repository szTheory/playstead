<objective>
Deliver PLAY-01, PLAY-02, PLAY-03, and CACH-04's gate: adapter installation and selection with an honest capability card, drag-in BIOS validation with no acquisition path anywhere, and a preflight state machine that blocks launch until every required condition is met and offers a concrete remedy for each one that is not — with zero network calls.

Purpose: the difference between a product that says "ready" and one that is actually ready is this state machine. It is also the only thing standing between a user and a launch that half-works.
Output: adapter catalog and installer, BIOS store, and the readiness engine with its remedy vocabulary.

Decisions implemented here: D-05 (download-on-demand from official upstream releases, version-pinned and digest-verified into an app-managed directory, with select-an-existing-install as a hash-badged secondary path, never bundled, never de-quarantined), D-06 (built-in high-level BIOS by default with the fidelity caveat displayed, drag-in validation by size and digest through the existing hash-match primitive, open replacements undeclared, no acquisition or distribution path anywhere), D-17 (a server-only entry's primary action is Download and Play appears only after verified preflight), D-23 (the completion hash is the authority; preflight trusts it through the cheap size, inode, and modification-time check with a full re-hash fallback and zero network calls, and corruption quarantines and redownloads with no-blame copy).
</objective>

`AdapterCatalog` exposes the single adapter this phase supports, sourced entirely from `AdapterPin`. Its descriptor carries the system, the emulator name, the exact version, the download URL, the expected digest, the content types it accepts, whether a BIOS is required, and the persistent-save support the spike recorded. No adapter fact is written as a literal anywhere in this plan's code: a restated version or flag would diverge from the spike's evidence the first time the pin is refreshed, and the capability matrix this product publishes has to stay true.

`AdapterInstaller` downloads the pinned release over HTTPS, computes its digest while streaming, refuses to install on any mismatch, expands it into `emulators/<emulator>/<version>/`, and records the installation in `adapter_installations` with its resolved executable path and digest. Installation into an app-managed directory rather than a downloads-style location is deliberate: a quarantined application run from certain locations can be relocated by the operating system, which breaks the relative paths the emulator resolves its own resources through.

Leave the quarantine attribute in place. The operating system's evaluation of a separately notarized third-party binary is the integrity gate that makes downloading an emulator defensible at all; removing the attribute programmatically would both defeat that gate and resemble the behaviour of the software this product is not.

Make installation idempotent: an existing installation whose digest matches the pin is reused, and two concurrent install requests serialise through the installer actor to one installation and one record.

Support selecting an existing installation the user already has. Compute its digest and record whether it matches the pin, and label it accordingly in the interface. A non-matching selection is allowed but is presented as unverified, with the concrete consequence stated, because the support matrix is a claim about a specific build and a different build is a different claim.

`AdapterCapabilityCard` renders the descriptor: system, emulator, version, digest, accepted content, BIOS posture including the fidelity caveat when the built-in high-level BIOS is in use, and persistent-save support. Where the spike recorded a limitation, the card states it.

`AdapterHost` gains its install state so it can refuse to launch against a missing or mismatched installation with a typed error rather than a failed process spawn.

  <behavior>
    - A dropped file of the expected byte length whose digest matches a known reference is accepted and copied into managed storage.
    - A dropped file of the correct length whose digest matches nothing is rejected with that reason and is not copied.
    - A dropped file of the wrong byte length is rejected before any digest is computed.
    - A dropped directory, symbolic link, or unreadable file is rejected without following the link or traversing the directory.
    - Dropping the same accepted file twice leaves exactly one managed copy.
    - An accepted file's managed copy is stored under a name derived from its digest, not from the dropped filename.
    - Removing a managed BIOS deletes only that managed copy and never the user's original file.
    - The original dropped file is never modified.
  </behavior>
  <action>
`BiosStore` validates a candidate by byte length first and then by digest against the adapter's known reference digests carried in the pin. This is deliberately the same shape as the import pipeline's digest-match verification rather than a bespoke format parser: a parser that claims to recognise a BIOS by inspecting its contents is a new attack surface and a new source of false confidence, whereas a length and a digest are exactly as much as anyone can honestly assert.

Treat the dropped path as untrusted. Resolve and reject symbolic links, directories, and unreadable files before opening anything; open the file read-only, compute the length and digest, and never execute, parse, interpret, or write to it. On acceptance, copy — never move — the bytes into managed storage under a name derived from the digest, so the user's original file stays exactly where and as it was.

Record accepted files in a `bios_files` table with the digest, byte length, and accepted-at timestamp. Removing a managed BIOS deletes only the managed copy.

The product provides no way to obtain a BIOS. There is no download action, no link, no filename hint, no vendor reference, and no guidance in any copy about where such a file might come from — the user either already has one or does not, and the product's job is to validate what they have and otherwise to work without it. Open replacements are not declared as supported in this phase.

When no BIOS is present and the adapter's built-in high-level implementation covers the system, the capability card states that fidelity may differ from the original hardware and that this is expected, so a user who later notices a difference recognises it rather than suspecting corruption.

  <action>
`ReadinessEngine.evaluate(assetSet:)` runs six checks — game assets, local cache verification, emulator, BIOS, controller and input, and persistent-save path — and returns an ordered list of `ReadinessCheck` results. Each result carries a kind, an outcome of ready, warning, or blocked, a plainly worded finding, and for anything blocking a `Remedy` with a title and an executable `RemedyAction` such as downloading the missing member, installing the adapter, opening the BIOS drop target, opening input settings, or repairing the save directory. A blocking result without an action is not shipped: telling a user something is wrong and leaving them to work out what to do about it is the failure mode this requirement exists to prevent.

The asset and cache checks consume the plan 03-03 preflight: the cheap size, inode, and modification-time comparison first, then a full re-hash only when that disagrees. On a genuine digest mismatch, quarantine the object, enqueue a redownload, and report it as a corrupted local copy that is being replaced — the bytes are safe on the server, so this is an inconvenience rather than a loss, and the copy should say so.

The engine performs no network request of any kind. Not a reachability probe, not a metadata lookup, not a token refresh: the promise is that a verified local game launches on a plane, and any network call on this path is a way for that promise to fail. Enforce it in tests by evaluating with every request stubbed to fail and asserting the result is unchanged.

Order results by a defined severity so the report is stable and the user's eye lands in the same place every time. Make evaluation pure with respect to disk except for the quarantine-and-redownload consequence of a genuine corruption, so running it twice is safe.

`ReadinessReportView` renders the report with one row per check, its outcome glyph and text label, and its remedy button. The report is also where adapter, BIOS, and controller settings surface, since that is the moment they are relevant. Play becomes available only when the report has no blocking result.

## Trust Boundaries
