  <action>
Register `range_not_satisfiable: {416, "Range Not Satisfiable"}` in `PlaysteadWeb.ErrorCodes`'s `@registry`, following the existing `{status, title}` tuple shape. The 416 response goes out through `PlaysteadWeb.Problem.send_problem/4` with that code — never a bare `send_resp` — and must additionally carry `Content-Range: bytes */#{size}` so a client learns the true size from the rejection itself.

Implement `parse_range/2` to accept only the `bytes=` unit. A header naming any other unit, a header containing a comma (multi-range), a syntactically malformed header, and a suffix-range form all resolve to the full-200 path — this collapse is deliberate per D-19 and keeps the frozen contract to exactly one shape a client must implement. An out-of-range first byte position is the only case that produces 416; clamp an over-long last byte position to the final byte instead of rejecting it.

Treat a zero-length object as a special case: no byte position is satisfiable, so any well-formed Range header yields 416 with `bytes */0`, while the unranged request yields 200 with an empty body.

Implement `If-Range` as a strong comparison against the same quoted ETag the response emits. A mismatch discards the Range and serves the full 200 body; this is precisely the branch the client detects to decide it must truncate its partial file and restart.

Add `head "/:sha256", BlobsController, :head_show` inside the existing `scope "/api/v1/blobs"` block with its unchanged `pipe_through [:api, :device_auth]`, with a one-line comment naming D-19 as the reason, matching the file's existing per-scope comment convention. `head_show/2` runs the identical `authorized?/2` and `playable?/2` gate, then responds with the same status and headers and no body.
