<objective>
Deliver CACH-01, CACH-02, and CACH-03 on the Mac: a persistent, user-visible download queue with per-item control and automatic resume, six honestly derived availability states, and a capacity policy that pins, blocks, and reclaims without ever deleting anything the user did not choose to delete.

Purpose: this is where the custody promise is either kept or quietly broken. A state column that drifts from disk, or a background eviction that frees space helpfully, would both make the product untrustworthy in exactly the way the project's constraints forbid.
Output: queue, coordinator, quota and pin policy, manual eviction with LRU-ordered suggestions, and the downloads and storage views.

Decisions implemented here: D-18 (the client's transfer mechanism stays the in-process range-resuming engine — the queue schedules it and never bypasses it), D-20 (the content-addressed cache layout under Application Support that eviction and verification key off), D-21 (fixed quota plus a free-space floor with the floor winning, no silent deletion, manual-only eviction with least-recently-used suggestions, pin meaning never-evict and download-first, and the six states derived at read time from queue row, partial file, cache entry, and pin flag rather than a stored enum), D-22 (a persistent, user-visible, ordered local queue with per-item pause, resume, cancel, and reorder, auto-resume on reachability, and queued-while-offline as a quiet normal state), D-23 (the completion hash is the authority, corruption quarantines and redownloads with no-blame copy, and no periodic scrub ships in this phase).
</objective>

Add migrations for `download_queue_items` (a client-generated identifier, asset set id, member sha256, byte size, a fractional position string, a state enumeration covering waiting, active, paused, and cancelled, an attempt count, and timestamps) and `cache_objects` (sha256, byte size, committed-at, last-used-at, and the cheap verify record of size, inode, and mtime). Order the queue by the fractional position so a reorder moves one row.

`AvailabilityState.derive(_:)` is a pure function from four facts — the game's queue rows, the presence and length of partial files, the presence of cache entries for its required members, and the pin flag — to one of the six states. It must be computed on read. A stored state column drifts the first moment a file is removed, restored, or corrupted outside the app, and a user who sees "verified" over content that is not there loses the only thing this product is selling. The safe-to-evict result is only meaningful in the storage view; the card asks for the badge-eligible subset and never receives it.

`DownloadQueue` wraps the table with enqueue, dequeue, pause, resume, cancel, reorder, and list operations, all inside transactions. Enqueue is idempotent per member: a unique index on the asset set and member digest converges a repeated request rather than duplicating it.

`DownloadCoordinator` is an actor that drives one transfer at a time through the existing `DownloadEngine`, selecting the next item by pin priority first and queue position second, marking it active, publishing progress, and on completion recording the cache object and its verify record. On a digest mismatch it re-enqueues the member with an incremented attempt count and a plainly worded, no-blame explanation — a corrupted local copy is a redownload, not an incident. It never opens a second transfer path of its own.

`Reachability` publishes network availability. Queued-while-offline is a normal state with its own calm copy, not an error banner; when reachability returns, the coordinator resumes on its own.

`DownloadsView` lists the queue with per-item pause, resume, cancel, and reorder, and an overall progress summary. `GameCardView` gains the determinate ring for the active member and the queued mark, sourced from `AvailabilityState`.

  <behavior>
    - The default policy is a 25 GB quota and a 10 GB free-space floor on the cache volume.
    - A transfer whose completion would exceed the quota does not start; the item pauses and a reclaim prompt appears.
    - A transfer whose completion would leave less free space than the floor does not start, even when the quota still has room.
    - When quota and floor disagree, the floor decides.
    - Raising the quota above what the floor allows is accepted but the floor still governs, and the settings view says so.
    - A pinned game is never returned as an eviction candidate.
    - A pinned queue item is selected before an unpinned one regardless of queue position.
    - Unpinning a game makes it eligible for eviction but deletes nothing by itself.
    - A quota of zero, and a cache already over quota when the policy is lowered, both block new transfers and delete nothing.
  </behavior>
  <action>
Add a `quota_policy` table holding the byte quota and the byte floor, defaulting to 25 gibibytes and 10 gibibytes, and a `pins` table keyed by asset set id.

`QuotaManager.verdict(forAdditional:)` measures the cache directory's total committed bytes and the containing volume's free space and returns an allow verdict or a blocked verdict naming which limit was hit and by how much. The free-space floor outranks the quota: the quota is a preference about how much of the disk the user wants to lend this app, while the floor is about whether the machine keeps working, and a user who set a generous quota months ago did not consent to filling their disk today.

`DownloadCoordinator` consults the verdict before starting each item. On a blocked verdict it pauses the item and surfaces `ReclaimPromptView`, which states the shortfall in bytes, offers to raise the quota where the floor permits, and offers to reclaim from an ordered candidate list. It does not delete anything. Nothing in this phase deletes cached content without the user choosing that specific content: automatic reclamation would mean the user's pinned-offline expectation and the app's behaviour could diverge silently, and there is no way to apologise for that after a flight.

`PinStore` exposes pin, unpin, and a query. One flag carries two meanings by design: pinned content is never an eviction candidate, and pinned queue items are downloaded first, because a user pins the thing they intend to rely on.

`QuotaSettingsView` lets the user set the quota, shows the current usage against it and against the floor, and states plainly that the floor governs when the two disagree.

  <behavior>
    - Candidates are unpinned, fully verified games, ordered by least recently used first.
    - A game that is not fully verified locally is not a candidate.
    - A cache object shared by two games is only reclaimed when both are selected.
    - An object with no corresponding server-side record is excluded and reported, because it could not be downloaded again.
    - Reclaiming a selected game deletes its unshared cache objects and leaves the game's library row present with a server-only mark.
    - The plan states the exact byte count that will be freed before anything happens.
    - Reclaiming zero selected games is a no-op with a calm message.
    - Cancelling the prompt deletes nothing.
    - Quarantined partials are listed separately and are individually removable.

  <action>
`EvictionPlanner.candidates()` returns unpinned, fully verified games ordered least-recently-used first, each with the byte count that reclaiming it alone would free. Objects shared between games count once and are only freed when every referencing game is selected, so the displayed total is the truth rather than an optimistic sum.

Exclude from candidacy any cache object with no corresponding member record in the local catalogue mirror: without a server-side record the bytes cannot be fetched again, and offering them for reclaim would be offering to destroy something. Report such objects in the storage view as unreferenced, with their size, so the user can decide about them explicitly.

`EvictionPlanner.plan(for:)` returns an explicit plan naming the objects and the total bytes; `execute(_:)` deletes exactly those objects and updates `cache_objects`. Eviction is manual only in this phase and is never scheduled, timed, or triggered by a threshold: the trust model has to be earned by the user watching it behave before the app is allowed to do it unattended.

After execution, the game's library row remains and crossfades in place to the server-only mark. An item that vanishes when a user reclaims space reads as data loss even when it is not, and the whole point of this surface is that reclaiming is safe.

`StorageView` shows the total cache size against quota and floor, the candidate list with per-game byte counts, the pinned set marked as protected, the unreferenced objects, the quarantined partials, and a plain statement that the server retains everything regardless of what is reclaimed here. Safe-to-evict lives here and nowhere else.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server blob bytes → local cache | Remote bytes are committed as trusted, launchable content |
| user reclaim selection → filesystem deletion | A user action becomes an irreversible local delete |
| external filesystem changes → availability answers | Files may change outside the application between reads |
