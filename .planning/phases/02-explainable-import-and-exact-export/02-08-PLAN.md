<objective>
Let an administrator bring their own reference data, so a library of "not yet identified" files becomes a library of named games — without Playstead ever shipping, fetching, or redistributing a reference pack, and without a single existing receipt being rewritten.

Purpose: this is the last plan in the phase and the deliberately droppable one. Everything before it works with no reference data at all, which is why the quiet not-yet-identified state was designed as a normal state rather than a defect. What this plan adds is an upgrade path: a provider behind the existing behaviour, matching on digests already computed at import time, appending evidence rather than editing it.

It is also the phase's largest untrusted-parser surface. A reference pack is an administrator-supplied XML document, and XML parsing is where external entity expansion and declared-size lies live. The parser is therefore streaming, entity-safe, capped, fuzzed, and unable to raise.

Output: the audited pinned dependency, the reference pack record with full provenance, the safe streaming parser, digest-based matching, and the console surface for supplying and reviewing packs.
</objective>

<scope_note>
## Package legitimacy and the zero-manual-verification standing preference

RESEARCH.md's Package Legitimacy Audit returns a verdict of approved for the one new dependency this phase adds, produced manually because the automated legitimacy tool covers only the npm, PyPI, and crates ecosystems and not this project's package registry. RESEARCH.md recommends gating the dependency addition behind a blocking human checkpoint on that procedural grounds.

The project owner's standing preference is that every checkpoint in this project must be automatable and no human verification step may be planned. This plan therefore substitutes an automated supply-chain gate for the recommended human checkpoint: the dependency is pinned to the exact audited version, and a test asserts that both the pinned version and its recorded lockfile checksum match the audited values, failing loudly if either changes. The manual audit itself — registry age, download volume, source repository, and maintenance activity — is already recorded in RESEARCH.md's audit table and is not re-performed here.

This is a recorded, deliberate deviation from the package-legitimacy protocol's default remedy, taken to honour the owner's preference. It is noted here so the substitution is visible rather than silent. No package with a suspicious or unverifiable verdict is introduced by this plan.
</scope_note>

  <action>
Create `Playstead.Recognition.ReferenceMatch` as an implementation of the existing recognition behaviour — the same three callbacks, dispatched through the same seam the header-evidence provider already uses. Adding reference data must not add a second recognition pipeline; that is precisely what the behaviour was created for in plan 02-03.

Match on digests already stored. Every blob carries its full digest plus the legacy digests, and the headerless-offset fingerprints were computed in the same single streaming pass at import time specifically because reference packs hash content without its header, so both forms are needed and both are already available. Matching therefore reads database rows and nothing else — it never re-opens a blob, which is what makes installing a pack over a large library cheap instead of a full re-read of the entire store.

A match appends an evidence row with exact confidence, the matched reference name, and the provider name and version, and promotes the asset's current identification state, updating the catalogue payload and emitting a catalogue journal entry for the assets whose state actually changed and for no others. What it must not do is touch the receipt. The receipt outcome is terminal by design: an asset that arrived unrecognized was unrecognized at that moment, and the honest presentation is the outcome recorded at import shown alongside what is now known — not a quietly rewritten past. A user override still outranks a reference match, and both the machine evidence and the correction remain permanently visible.

Only a reference match can make a variant claim certain. Header evidence alone supports a possible-variant reading and no more, and installing a pack is exactly the event that can promote it — so the promotion happens here and nowhere else.

Add re-identification over the existing library: for each unmatched or ambiguous asset, run the reference provider and apply the result. Resolve previously ambiguous attention items in place when a match settles them. Critically, do not create attention items for content that was quiet before and stays unmatched after — installing a pack must reduce the number of open questions, and a pack that turns three hundred quiet library entries into three hundred new tasks would be worse than no pack at all.

Removing a pack leaves every evidence row in place; evidence is a record of what a provider said at a moment, and deleting it to reflect a changed installation would destroy exactly the history that makes an identification auditable.
