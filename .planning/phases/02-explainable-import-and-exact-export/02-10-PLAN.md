<objective>
Close gap 2 and gap 1's second half from 02-VERIFICATION.md.

Gap 2: `Playstead.Blobs.BlobFingerprint` has a schema and a proven consumer, but a grep of `lib/` finds no producer.
`Playstead.Recognition.ReferenceMatch.match/2` reads headerless-offset digests correctly against manually-inserted
fixture rows, and `MultiHash.digest_from_offset/2` was written for exactly this purpose and is still uncalled — but a
real NES or SNES import writes zero fingerprints, so a DAT pack keyed to headerless hashes (the common case per
D-20's own rationale) cannot match a real headered ROM.

Gap 1's second half: `unrecognized{ambiguous}` has no detector. The cause is one line —
`ReferenceMatch.lookup_by/2` ends every digest query with `limit: 1`, so a digest matched by two conflicting
reference entries silently returns whichever row Postgres happened to order first. `Playstead.Attention.Derive`
already maps that reason to `:ambiguous_recognition` and `PlaysteadWeb.AttentionLive` already renders it; only the
detector is missing.

Plan 02-09 is a hard prerequisite for both halves: fingerprints are written from a header detection that only
exists once format bytes reach classification, and 02-09 also raises `Playstead.Formats`' read ceiling to 66,048
so an SNES HiROM image with a copier header is detectable at all.

**Deviations from the design brief, each justified by a read of the code:**

1. **A `digest_from_offset/2` callback on the store seam, not an `object_path/1` accessor.** The brief proposes
   exposing the adapter's object path so the writer can seek into it. `Playstead.Blobs.Store`'s whole purpose is to
   be the seam a future object-store adapter fits (D-12), and a filesystem path is the one thing such an adapter
   cannot supply. Asking the adapter for the digests of a blob from a byte offset keeps the seam storage-agnostic
   — `LocalDisk` answers it with the already-written `MultiHash.digest_from_offset/2`, and an object-store adapter
   would answer it with a ranged GET. It also keeps `Playstead.Blobs` the sole adapter caller without leaking
   `object_path/2` out of the adapter, which 02-VERIFICATION.md records as a verified key link.

2. **The D-20 "same pass" relaxation, stated plainly.** D-20 says the headerless fingerprints are computed in the
   same streaming pass as SHA-256 "once the header is seen". This plan computes them in a second, bounded
   seek-and-read after commit instead. The reason is architectural: the streaming pass lives inside the storage
   adapter, and teaching the adapter to recognize an iNES magic or an SNES checksum complement would push format
   knowledge across the seam D-12 exists to hold. The cost is one extra read of an NES or SNES object, which are
   small, and only for files where a header was actually detected. The default-on read-back verify (D-11) already
   re-reads every committed object once, so this is not a new class of work. Rated `costly` rather than `one-way`:
   the fingerprint rows are derived data reproducible from the bytes at any time, so moving the computation into
   the streaming pass later requires no migration and no backfill of anything but the rows themselves.

3. **Lazy backfill instead of an Oban worker.** Blobs imported before this plan have no fingerprints.
   `reidentify/2` already walks exactly the unmatched blobs a newly installed pack could identify, so computing a
   missing fingerprint there back-fills precisely the set that matters, at the moment it matters, with no new job,
   no queue, and no scheduling. A blob nobody ever tries to identify never pays the cost.

Purpose: make D-20's headerless matching work for a real ROM, and make an ambiguous digest a visible human decision
instead of a silent coin flip.
Output: a unique index, a production fingerprint writer on the import path, a lazy backfill on the reidentify path,
an ambiguous return shape, and the inbox item that shape produces.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| admin-supplied DAT pack → `reference_entries` → `ReferenceMatch` | Pack contents are supplied by the operator, never bundled (D-18), and their digests drive automated identification of the user's library. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-71 | Tampering | ambiguous reference match | high | mitigate | The whole point of task 2: a digest matched by two conflicting entries can no longer resolve to whichever row Postgres ordered first. `match/2` returns the conflict, `reidentify/2` refuses to promote, and the decision is escalated to the user with both candidate names shown. A malicious or careless pack can no longer silently relabel a user's game. |
| T-02-72 | Denial of Service | `lookup_by/2` row enumeration | medium | mitigate | The limit rises from one to two, not to unbounded. A pack crafted with ten thousand colliding entries makes the server read two rows, not ten thousand. The pack importer's existing size and entry caps still bound how many entries can be installed at all. |
| T-02-73 | Denial of Service | `digest_from_offset/2` re-reading a committed object | medium | mitigate | Runs only when a NES iNES header or an SNES copier header was actually detected, so only for small console ROM images; runs once per blob per kind thanks to the unique index, and never at all for archives, unknown files, or headerless ROMs. On the reidentify path the read is skipped entirely when a row already exists. The default-on read-back verify (D-11) already re-reads every committed object once, so this adds no new class of I/O. |
| T-02-74 | Tampering | committed objects under `objects/` | high | mitigate | `digest_from_offset/2` opens read-only through `MultiHash.digest_from_offset/2`, which uses `[:read, :binary, :raw]`, seeks, streams, and closes. The store behaviour's standing rule that no callback deletes, renames, truncates, or moves a committed blob is restated on the new callback, and the adapter's `object_path/2` does not leak across the seam (asserted by a grep in task 1). |
| T-02-75 | Tampering | duplicate or conflicting `blob_fingerprints` rows | medium | mitigate | The migration's unique index on `{blob_id, kind}` makes a second row impossible, and the writer uses `insert_all` with `on_conflict: :nothing` against that exact conflict target — so a re-import returning `:existing` from the CAS converges on one row without a raising insert that would abort the ambient import transaction. |
| T-02-76 | Information Disclosure | pack-supplied candidate names rendered in the evidence card | low | accept | The names come from an operator-installed pack, are stored in a JSON evidence map, and are rendered through the existing evidence card whose escaping is already exercised by `attention_live_test.exs`. `Playstead.Catalogue`'s control and bidirectional-override stripping (D-22) already governs display titles. Accepted at ASVS L1. |
| T-02-77 | Spoofing | crafted bytes forcing a fingerprint at a chosen offset | low | accept | The only two reachable offsets are 16 and 512, both fixed constants tied to a validated header, and the resulting row is derived data that can only ever cause a *reference lookup* to be attempted. A crafted file can at worst make the server compute one extra bounded digest of its own bytes. Accepted at ASVS L1. |
| T-02-SC | Tampering | npm/pip/cargo/hex installs | n/a | accept | This plan installs no packages. `mix.exs` and `mix.lock` are absent from `files_modified` and must not be modified; the package-legitimacy gate has nothing to audit. An executor reaching for a new dependency has misread the plan and should halt. |
