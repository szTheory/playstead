<objective>
Close the shared root cause behind both gaps in 02-VERIFICATION.md, then close gap 1's first half.

The verifier found that `unknown_system?` is hardcoded `false` and that `unrecognized{ambiguous}` has no producer. A
code trace found the cause underneath both: **no production call site passes `:format_bytes` into the import
pipeline.** `Playstead.Import.import_single/4` and `complete_staged_file/4` both read `Keyword.get(opts,
:format_bytes)`, and the only places in the repository that supply it are tests and
`test/support/browser_screens.ex`. The three production entries —
`PlaysteadWeb.Api.V1.ImportsController` (`imports_controller.ex:77`), `Playstead.Import.SessionWorker`
(`session_worker.ex:184` and `:217`), and `Playstead.Import.import_bag_member/3` (`import.ex:1046`) — all omit it.

So in production `format_result` is always `{:unknown, :none, %{}}`, `Catalogue.assign_system/3` always returns
`{:ok, extension_guess_or_unknown, :extension}`, and `unrecognized_reason_for/3` can only ever produce
`archive_not_opened` or `signature_mismatch`. Header evidence — D-16's entire recognition pipeline — never reaches
classification for a real import. Both verification gaps are downstream of this one omission, which is why wiring
it is task 1 and why plan 02-10 depends on this plan.

Task 2 then makes `unknown_system` live and gives the two quiet reasons real producers, replacing the rationale
comment at `import.ex:196-203`. That comment claims an unmapped extension with no header match is indistinguishable
from the no-reference-installed quiet state. With header evidence actually flowing, that is no longer true: a file
with a *supported* format and no pack installed is D-26's quiet `no_reference_installed` state, while a file with
neither an extension claim nor a header claim is D-26's inclusion case "unknown system". The comment's concern —
inbox flooding — is answered by grouping rather than by suppression.

**Deviations from the design brief, each justified by a read of the code:**

1. **One defaulting point inside `import.ex`, not three call-site edits.** The brief asks for `format_bytes:` at
   each of the three call sites while also asking for "one code path for all callers". These conflict. Resolving
   `format_bytes` inside `import_single/4` and `complete_staged_file/4` when the caller supplied none satisfies the
   stated intent, covers `import_bag_member/3` for free (it delegates to `import_single/4`), and cannot be defeated
   by a future fourth call site forgetting the option. Callers that *do* pass bytes (every existing test) keep
   passing them, so the option stays honoured and the test suite's explicit control is preserved.

2. **`Playstead.Formats`' read ceiling must rise to 66,048.** `Formats.identify/2` truncates its input with
   `bounded_bytes/1` at `@max_read` 65,536 before any validator sees it. `Playstead.Formats.Validators.Snes` probes
   a HiROM header at `512 + 0xFFC0` and requires `512 + 0xFFC0 + 0x20` = 66,016 bytes. An SNES HiROM image with a
   copier header is therefore *currently undetectable no matter what the caller passes* — a live bug this plan must
   fix, and a precondition for plan 02-10's SNES copier fingerprint. 65,536 + 512 is the smallest ceiling that
   admits it.

3. **`no_reference_installed` vs `no_match` is decided on whether the user has any pack installed, not on
   per-system coverage.** The brief proposes checking whether a pack covers the file's system. Neither
   `Playstead.Recognition.DatPack` nor `Playstead.Recognition.ReferenceEntry` carries a system column, so per-system
   coverage is not derivable from the schema. "Has this user installed any reference pack at all" is derivable,
   honest, and is the distinction D-26's library hint actually turns on.

4. **No new grouping key is needed.** The brief proposes `"unknown_system:" <> import_session_id`.
   `Playstead.Import.attention_grouping_key/1` already returns the session id for a staged file and
   `"single:<source_file_id>"` for a single import, and `Playstead.Attention.upsert_item/1` conflicts on
   `{user_id, grouping_key, reason}`. A session's unknown-system files therefore already collapse to one item and a
   single API upload already gets its own — the anti-flood mechanism exists and adding a prefix would only make the
   key differ from every other reason's for no behavioural gain.

**Expected blast radius.** Giving `no_reference_installed` a producer moves receipts that previously reported
`new_asset` to `unrecognized` with that reason whenever no pack is installed and the outcome was otherwise
`new_asset`. This is the correct D-25 reading and is what makes D-26's "Not yet identified" library badge
meaningful, but it will churn existing assertions across the suite. Duplicates, aliases, variants, patched, and
quarantined outcomes are untouched — the reason is only consulted when the base outcome is `new_asset`.

Purpose: make D-16's header-evidence pipeline reach production classification, and make two of D-26's outcome
distinctions real instead of dead code.
Output: a bounded blob read through the store seam, format bytes flowing at all three production entries, a live
`unknown_system?`, two new quiet reason producers, and behaviour tests for each.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-61 | Denial of Service | `Playstead.Blobs.read_leading/2` | medium | mitigate | The read is capped at 66,048 bytes by a module attribute, takes a single bounded read against a raw file handle, and closes in an `after` clause. It never streams the whole object, never allocates proportional to file size, and a multi-gigabyte blob costs the same as a 64 KiB one. |
| T-02-62 | Denial of Service | `Playstead.Formats` validators on a wider byte window | medium | mitigate | The ceiling rises by 512 bytes only, `bounded_bytes/1` still truncates every caller's input inside `Formats`, and the validators are already property-tested against arbitrary binaries with a rescue-to-`:no_match` contract. No validator's cost is superlinear in the window. |
| T-02-63 | Information Disclosure | committed blob bytes via the new read path | medium | mitigate | `read_leading/2` is called only from `Playstead.Import`'s own classification step with a digest the pipeline just committed; it is exposed on no route, no LiveView, and no API surface, and returns bytes to the caller rather than to a response. The blob-serving route's quarantine guard is unaffected because this path never serves bytes. |
| T-02-64 | Denial of Service | attention inbox flooded by `unknown_system` items | high | mitigate | `attention_grouping_key/1` plus `Playstead.Attention.upsert_item/1`'s `{user_id, grouping_key, reason}` conflict target collapse a session's unknown-system files into one item with an incrementing count; a thousand-file staged import raises one row, not a thousand. | T-02-65 | Spoofing | client-supplied filename influencing the unknown-system decision | low | accept | A crafted extension can only *suppress* an unknown-system item for the attacker's own file, in the attacker's own user-scoped inbox. The header axis is decided by the server from the bytes and always wins in `Catalogue.assign_system/3`; a filename can never fabricate a system claim that contradicts the bytes without producing a confirmation-needed item instead. Accepted at ASVS L1. |
| T-02-66 | Tampering | committed objects under `objects/` | high | mitigate | `read_leading/2` opens read-only and its behaviour docstring reaffirms the standing rule that no callback deletes, renames, truncates, or moves a committed blob. | T-02-67 | Denial of Service | extra per-import queries from `packs_installed?/1` and the reference lookup | low | accept | `packs_installed?/1` is one indexed existence query per import. The reference lookup runs only when a pack is actually installed and reads only `reference_entries` rows, never the object store. Accepted at ASVS L1. |
| T-02-SC | Tampering | npm/pip/cargo/hex installs | n/a | accept | This plan installs no packages. `mix.exs` and `mix.lock` are absent from `files_modified` and must not be modified; the package-legitimacy gate has nothing to audit.
