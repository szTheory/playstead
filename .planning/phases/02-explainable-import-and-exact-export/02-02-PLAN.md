Create `Playstead.Blobs.MultiHash` with `init/0`, `update/2`, and `finalize/1` computing SHA-256, SHA-1, MD5, and CRC32 from one pass over the bytes, per D-20 and RESEARCH Pattern 1. One accumulator belongs to one file and threads sequentially through that file's own chunks. RESEARCH Pitfall 1 is the trap: parallelism in this phase is across files, never across chunks within a file, because a hash context cannot be split — a chunk-parallel hash produces a wrong digest that only surfaces at the read-back check, or ships silently wrong when verification is disabled. Finalize to lowercase hexadecimal for all four values. Also expose the ability to compute a digest starting from a byte offset so the headerless-offset fingerprints D-20 requires can be produced in the same pass; store those in `blob_fingerprints` with a kind, an offset, and the CRC32/MD5/SHA-1 triple.

Define the `Playstead.Blobs.Store` behaviour in `lib/playstead/blobs/store.ex` with exactly the callbacks D-12 names: `open_write/1`, `write_chunk/2`, `commit/2` returning `{:ok, :stored}` or `{:ok, :existing}`, `abort/1`, `exists?/1`, `stat/1`, `stream/2` taking a hash and an optional byte range, `free_bytes/0`, `writable?/0`, and `delete/1`. Document in the moduledoc that `delete/1` is defined only for uncommitted temporary files and that no v1 code path deletes a committed blob — this is the seam a future S3 adapter must fit, so the contract has to state the restriction rather than leave it to convention.

Implement `Playstead.Blobs.Store.LocalDisk` as the sole v1 adapter, following D-11's write path exactly and in order. `open_write/1` first re-checks free space against the requested byte count using plan 02-01's required-space rule and returns a disk-full error if it does not fit — this check belongs here, per write, and not only at session start, because a long session can exhaust the margin after its initial preflight passed (RESEARCH Pitfall 3). It then opens a uniquely named partial file under the blob path's `tmp/` subdirectory. `write_chunk/2` writes and updates the multi-hash accumulator in the same step, using a chunk size of one mebibyte. `commit/2` fsyncs the file handle, closes it, then re-opens the file from disk and re-hashes it, comparing against the streamed digest — this read-back verification is on by default and is the moment the custody promise is actually made; honour `PLAYSTEAD_IMPORT_VERIFY` set to false as a documented operator escape for slow disks, and log clearly when it is disabled. On a match, rename the file into `objects/sha256/` split by the first two and next two hex characters of the hash. Both `tmp/` and `objects/` must live under the one blob path so the rename stays within one filesystem and stays atomic (RESEARCH Pitfall 2, surfaced by plan 02-01's readiness row).

Resolve the two collision cases exactly as D-11 states. When the content-addressed path already exists and a `blobs` row for that hash exists, trust the hash and the recorded size, do not compare bytes, and return `{:ok, :existing}`. When the path exists with no row — the crash-between-rename-and-commit case — re-hash the file on disk and adopt it if it matches, replacing nothing. Critically, the authority for "already exists" is the database unique constraint on `blobs.sha256`, not a prior `exists?/1` read: `exists?` followed by a conditional write is a check-then-act race that two concurrent identical imports will lose (RESEARCH Pitfall 4). Attempt the insert and treat a unique-constraint violation as the authoritative existing-blob signal.

Create `Playstead.Blobs` as the context and the only caller of the configured adapter, selected in `runtime.exs`. Nothing in the import or export pipeline may reference `Playstead.Blobs.Store` or `LocalDisk` directly — D-12 makes this the whole point of the seam.
