<objective>
Give a user one place to resolve the small number of things Playstead genuinely cannot decide alone — a game missing a disc, a file whose extension and header disagree, an oversized input set aside by policy, a batch of archives kept unopened — with the evidence in front of them and five safe, reversible, audited ways forward.

Purpose: IMPT-06's real design risk is not the resolutions, it is the inclusion rule. An inbox that collects every unidentified file turns a first adopter's three hundred imported ROMs into three hundred chores and teaches them to ignore the inbox permanently. The decision record draws the line precisely: unrecognized-but-fine content stays quietly in the library, and only genuine decisions arrive here. The second risk is destructiveness — so no resolution in this phase deletes a byte, and every one of them except retry can be undone.

Output: the attention item model with its derivation rule, quarantine as a processing state, the five audited resolutions, the cursor-paginated attention API, and the console inbox.
</objective>

  <action>
Create the `recognition_overrides` table and `Playstead.Recognition.Override` schema: user-scoped, referencing the asset set, carrying the corrected system or title, the audit entry identifier, and a timestamp. An override always outranks extension and header evidence, and it is additive — a correction never deletes or rewrites a machine-produced evidence row. That split is what keeps the history honest: the machine's reading and the user's correction are both permanently visible, so a later reference pack can be reconciled against both rather than against a record someone already overwrote.

Create `Playstead.Attention.Resolutions` with the five commands, each following the same discipline the idempotency module models — the effect and its audit entry are written inside one transaction, never with the audit written after the commit, because an audit entry lost in that gap is exactly the entry someone will later need.

Correcting the system or metadata inserts an override row and re-derives the display title. Attaching a missing companion either binds an existing blob the user already owns to the declared member slot at its ordinal, or opens a fresh import bound to that slot so the arriving bytes land in the right place; either way the set's status and member fingerprint are recomputed in the same transaction. Retaining as custom marks the content user-declared and, for policy-quarantined bytes, releases them as opaque content only — release makes bytes storable and exportable as-is, never inspectable-as-playable. Excluding sets the exclusion timestamp, emits a catalogue tombstone, and keeps every byte; the item remains restorable through an excluded filter, and the inbox reports the storage those excluded items hold so the user can see the cost of their choice without being pushed into deleting anything. Retrying re-enqueues inspection and recognition against bytes already stored and copies nothing.

No resolution deletes a byte. Physical reclaim is deliberately a later phase's work, sitting beside the backup story where a user can see what a deletion would cost before making it — so there is no reclaim path, no delete action, and no cleanup routine anywhere in this plan.

Every resolution except retry is undoable, and undo writes its own audit entry. Undo lives in the excluded filter and in the item's own history rather than in a transient notification, because a message that disappears is not a reversal mechanism.

Two clients resolving the same item at once must not double-apply. Resolve this at the database rather than by reading the item's state first: a conditional update guarded on the item still being unresolved makes exactly one attempt the winner and lets the other report that it was already resolved.

Add the endpoints on the device-authenticated pipeline: a cursor-paginated attention list scoped to the calling user, and a resolve endpoint running under the existing idempotency plug unchanged so a client retrying after a disconnect gets the original receipt rather than a second effect. An item belonging to another user is refused as not-found rather than forbidden, so the endpoint cannot be used to probe for another user's items.
