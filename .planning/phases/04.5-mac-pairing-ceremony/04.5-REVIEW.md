# Phase 04.5: Code Review Report

**Reviewed:** 2026-09-09
**Depth:** standard
**Files Reviewed:** 17
**Status:** issues_found

## Summary

This is a re-review of the same file set covered by the prior `04.5-REVIEW.md`,
after gap-closure plans `04.5-02` (fail-closed pinning, CR-02) and `04.5-03`
(generation-guarded cancellation, CR-01) landed. Both previously-reported
Critical findings are verified fixed in the current code, traced line by line
rather than taken on faith:

- **CR-01 (cancellation TOCTOU) — fixed.** `PairingCoordinator` now carries a
  monotonic `generation` counter, incremented first thing in `cancel()`
  (`PairingCoordinator.swift:150`). Every method-call frame that resumes from
  a suspending `await` — `start()`'s `createRequest` (line 130), `pollLoop()`'s
  `sleep` (line 172) and `pollStatus` (line 187), and `redeem()`'s `client.redeem`
  (line 233) — re-reads `generation` and abandons its result if it no longer
  matches the value captured before the `await`. Because `PairingCoordinator`
  is `@MainActor` and none of the synchronous code between a generation guard
  and the state/Keychain/pin mutation it protects contains a further
  suspension point (`KeychainStore.storeCredential`/`deleteCredential` and
  `PinnedCertificateCapture.writeCapturedCertificate` are all plain
  synchronous calls, not `async`), there is no residual TOCTOU window between
  a guard and the mutation it gates. `PairingCoordinatorTests` proves this
  directly with three gated-race tests
  (`testCancellingDuringAnInFlightRedeemWritesNoCredentialAndStaysIdle`,
  `testCancellingDuringTheCreateRequestDoesNotResurrectTheCeremony`,
  `testAPollThatApprovesAfterCancellationNeverRedeems`) that hold a stub
  response genuinely in flight on a background thread while the `@MainActor`
  test calls `cancel()`, then asserts no credential, no pin file, and no
  state resurrection follow.
- **CR-02 (silent unpinned success) — fixed.** `start()` now rejects any
  non-`https` scheme before generating a device code or making a request
  (`PairingCoordinator.swift:112-115`, `PairingError.insecureServerAddress`).
  `redeem()` now branches on `writeCapturedCertificate(to:)`'s boolean result
  when both `certificateCapture` and `pinnedCertificateURL` are configured
  (the production path): a failed or impossible pin write calls
  `keychain.deleteCredential()` to roll back the just-stored credential and
  ends in `.failed(.certificatePinFailed)` rather than `.paired`
  (`PairingCoordinator.swift:251-257`). `.paired` is therefore unreachable
  unless both the credential and the pin are durable, in the one
  configuration (test-only, `certificateCapture`/`pinnedCertificateURL`
  both `nil`) explicitly documented as unpinned by design.
  `testPairingFailsClosedAndRollsBackTheCredentialWhenTheAnchorCannotBePinned`
  exercises the rollback directly.

The three Warnings and the one Info item from the prior review that were not
addressed by either gap-closure plan are carried forward below, since the
underlying code is unchanged. One new Info item is added.

## Warnings

### WR-01: Test-only device-name override is still reachable in production builds

**File:** `playstead-mac/Playstead/Pairing/PairingCoordinator.swift:273-275`

**Issue:** Unchanged since the prior review:
```swift
nonisolated static func defaultDeviceName() -> String {
    ProcessInfo.processInfo.environment["PLAYSTEAD_UI_TEST_PAIRING_DEVICE_NAME"] ?? Host.current().localizedName ?? "Mac"
}
```
This is the default `deviceName` for every `PairingCoordinator` constructed
via `AppEnvironment.makePairingCoordinator()` (`PlaysteadApp.swift:907-919`),
the production pairing entry point. It is not gated behind `#if DEBUG` or
`#if UI_TESTING` the way every other environment-variable test hook in this
codebase is (contrast `XCTestHostBootstrap.isRequested()`, gated behind
`#if DEBUG`). A shipped, non-debug build still honors
`PLAYSTEAD_UI_TEST_PAIRING_DEVICE_NAME` if it is present in the launch
environment — a confused-deputy vector for spoofing the device name a human
sees and approves in the server's devices console. `PairingCeremonyTests`
itself now sets this exact variable in `launchEnvironment` for the live-server
proof (`PairingCeremonyTests.swift:85`), which is a legitimate test use, but
nothing in the source stops the same variable from being set for a shipped
binary launched by anything other than XCTest.

**Fix:** Gate the override behind `#if DEBUG` (or `#if UI_TESTING`, matching
the live-server harness's own launch surface), consistent with every other
test hook in the codebase:
```swift
nonisolated static func defaultDeviceName() -> String {
#if DEBUG
    if let override = ProcessInfo.processInfo.environment["PLAYSTEAD_UI_TEST_PAIRING_DEVICE_NAME"] {
        return override
    }
#endif
    return Host.current().localizedName ?? "Mac"
}
```

### WR-02: `PairingError.slowDown`'s user-facing message can never be reached from the poll loop it describes

**File:** `playstead-mac/Playstead/Pairing/PairingView.swift:113-114`, `playstead-mac/Playstead/Pairing/PairingCoordinator.swift:198-205`

**Issue:** Unchanged since the prior review. `pollLoop()` still catches
`PairingError.slowDown` internally and converts it to a backoff
(`interval = min(interval * 2, maxPollInterval); continue`) — it never
reaches `state = .failed(.slowDown)`. The only way `.failed(.slowDown)` can
actually occur is a 429 from `createRequest` or `redeem`, at which point
`PairingView`'s copy ("Polling too fast — slowing down automatically.")
describes a poll backoff that is not happening — the ceremony has already
dead-ended in `.failed`, and the user must click "Request pairing" again.

**Fix:** Give `.slowDown` a request/redeem-specific message ("The server is
rate-limiting this pairing attempt. Wait a moment and try again."), or split
it into two distinct error cases so the copy always matches the operation
that actually produced it.

### WR-03: `redeem()`'s Keychain-write failure path leaves the consumed `device_code` with no recovery other than a full restart

**File:** `playstead-mac/Playstead/Pairing/PairingCoordinator.swift:259-260`

**Issue:** Unchanged since the prior review. By the time
`keychain.storeCredential(credential)` runs, the server has already durably
consumed `device_code` (the redeem call succeeded). If the local Keychain
write then fails, `state = .failed(.keychainWriteFailed)` correctly informs
the user, but there is no way to retry storing the already-redeemed
credential — the only path forward is "Request pairing" again, starting an
entirely new ceremony. Likely an accepted limitation of the one-time-use
`device_code` design, but still undocumented at this call site, unlike every
other edge case in this file, which carries an explicit rationale comment.

**Fix:** Add a doc comment on this branch (or on `.keychainWriteFailed` in
`PairingClient.swift`) noting that the redeemed credential cannot be
recovered and a fresh ceremony is required, so a future reader does not "fix"
this by adding a retry that assumes `device_code` is still valid.

## Info

### IN-01: `throwIfNotSuccess`'s `(409, _)` fallthrough silently becomes `.invalidResponse` rather than a more specific signal

**File:** `playstead-mac/Playstead/Net/PairingClient.swift:244-250`

**Issue:** Unchanged since the prior review. A 409 with a `code` other than
the two known values (or no `code` at all) falls through to
`default: throw .invalidResponse`, rendered by `PairingView` as "The server
address is not valid, or it sent an unexpected response." — a plausible but
slightly misleading message for a 409 (which by definition reached a valid
server and endpoint). Every other status/code pair in the switch is
enumerated explicitly; this fallthrough reads as deliberate but is
undocumented as such.

**Fix:** A one-line comment above the `switch` noting unmapped `(status,
code)` pairs deliberately collapse to `.invalidResponse` removes the
ambiguity for a future reader extending this switch.

### IN-02: `redeem()`'s early-exit guard is unreachable in the current call graph but carries no generation check, unlike every real commit point in the same function

**File:** `playstead-mac/Playstead/Pairing/PairingCoordinator.swift:218-222`

**Issue:**
```swift
private func redeem() async {
    guard let baseURL, let requestID, let deviceCode else {
        state = .failed(.invalidResponse)
        return
    }
    let myGeneration = generation
    ...
```
`redeem()` is only ever called synchronously from `pollLoop()`, immediately
after `pollLoop()`'s own `guard myGeneration == generation else { return }`
(`PairingCoordinator.swift:187,192`) — with no `await` in between, so on the
MainActor `baseURL`/`requestID`/`deviceCode` cannot have been cleared by a
racing `cancel()` by the time this guard runs, and the branch is effectively
dead today. It is nonetheless the one `state` mutation in this file that
commits without any generation check, which weakens the "every commit point
compares against `generation`" invariant the file's own doc comment
(`PairingCoordinator.swift:51-56`) states as universal. If `redeem()` ever
gains a second caller (e.g. a manual retry affordance addressing WR-03), this
branch would silently become reachable with no cancellation guard.

**Fix:** Either move `let myGeneration = generation` above the `guard` and
add `guard myGeneration == generation else { return }` to this branch too
for consistency with every other commit point, or add a comment explaining
why this specific branch is exempt (unreachable given the sole current call
site) so a future caller doesn't inherit the gap unknowingly.
