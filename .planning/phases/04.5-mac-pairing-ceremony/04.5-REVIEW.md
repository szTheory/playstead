# Phase 04.5: Code Review Report

**Reviewed:** 2026-09-09
**Depth:** standard
**Files Reviewed:** 12
**Status:** issues_found

## Summary

This phase moves the `mac_ci` Phoenix fixture to TLS and installs a per-run
CA as a trusted root in the macOS System keychain for the duration of one
CI job. The review was weighted toward the trust-anchor lifecycle (install/
remove), private-key handling, command injection in the shell/python glue,
fail-open gates, and the `PairingCoordinator`'s cancellation-safety
invariant, per the phase's stated risk profile.

The implementation is unusually careful for this class of code. Specific
things verified as sound, not just assumed:

- **Trust/untrust ordering.** In both `local-live-server.sh` and
  `run-mac-verification.sh`, the `EXIT` trap that calls `untrust`
  (directly, or via `cleanup_native_services`) is armed *before* `issue`/
  `trust` run, and `CA_TRUSTED`/equivalent state is only set to true
  *after* `trust` returns 0 — so a `set -e` abort between `issue` and
  `trust`, or a mid-`start_native_services` death, always reaches a
  cleanup path, and never runs `untrust` against a CA that was never
  trusted. `cmd_untrust` in `mac-ci-tls.sh` never swallows a real
  `remove-trusted-cert`/`delete-certificate` failure — it independently
  re-checks presence by fingerprint before treating an already-absent
  certificate as success (see WARNING WR-01 below for the one gap in this
  logic).
- **Private-key permissions.** `mac-ci-tls.sh cmd_issue` creates
  `tls_root` with `mkdir -m 0700` (no window at a wider mode), generates
  all key material inside a `(umask 077 ...)` subshell, and the closing
  `chmod 0600 "$tls_root"/*` only tightens, never widens, permissions.
  `mac-ci-tls-test.sh` asserts both the directory and per-file modes.
  Nothing downstream re-`chmod`s the `tls/` directory more permissively.
- **Command injection.** All `python3 - ... <<'PY'` heredocs in every
  reviewed script use a quoted (`'PY'`) delimiter and pass all untrusted
  or path-shaped data through `sys.argv`, never through shell string
  interpolation into the heredoc body. Shell-side variable expansions
  (`"$server_root"`, `"$tls_root"`, `"$display_code"`, etc.) are
  consistently double-quoted. `security find-certificate -c` performs a
  substring match (confirmed against the local `security` man page), so
  the `Playstead Mac CI Root` prefix search in both `cmd_untrust` and
  `prove-pairing-ceremony.sh`'s teardown check correctly matches the
  actual per-run CN (`Playstead Mac CI Root <uuid>`).
- **Fail-open gates.** `verify_layer_result` and `verify_result` in
  `run-mac-verification.sh` both require `execution_count == 1`,
  `skipped == False`, and `outcome == "passed"` for every required test/
  canary, so a missing, skipped, or failed required node fails the gate
  rather than passing vacuously — matches what
  `pairing-ceremony-gate-test.sh` asserts (pass/failed/skipped/absent/
  anchor-count). `write_adoption_evidence` seeds
  `native_health.cleanup_complete: false`, and only
  `cleanup_native_services` (called strictly before `verify_result`)
  flips it to `true`, and only when cleanup actually succeeded — so a
  cleanup failure cannot be papered over by a later evidence write.
- **`PairingCoordinator`'s generation guard.** Traced the specific race
  the code's own comments call out (CR-01/VERIFICATION gap 2): a poll
  `Task` created by `startPolling()` but not yet scheduled when `cancel()`
  runs. `pollLoop`'s `while !Task.isCancelled` check runs before its
  `myGeneration` read is ever acted on, and `cancel()` calls
  `pollTask?.cancel()` on the exact `Task` reference before any new
  ceremony's `startPolling()` call can create a second one — so the
  cooperative-cancellation flag, not the generation read, is what
  actually prevents the abandoned task from doing anything, and it does.
  No exploitable double-poll/double-redeem path found. The `#if DEBUG`
  gate on `defaultDeviceName()`'s environment override is genuinely
  absent from the `#else` (Release) branch — confirmed by reading both
  branches, not just the `#if` line.

Two warnings and two info-level items remain, below.

## Warnings

### WR-01: `mac-ci-tls.sh cmd_untrust` can silently report success while leaving a trust anchor installed, if `ca.pem` is unreadable at untrust time

**File:** `playstead-mac/scripts/ci/mac-ci-tls.sh:105-133`
**Issue:** `cmd_untrust` computes `fp` once, at the top, via
`fp="$(fingerprint_of 2>/dev/null || true)"`. `fingerprint_of` reads
`$tls_root/ca.pem`; if that file is missing, unreadable, or corrupt at the
moment `untrust` runs, `fp` is silently empty (the `2>/dev/null || true`
swallows the `openssl` failure by design, per the earlier `fingerprint_of`
comment).

With `fp` empty:
- The primary removal path, `security remove-trusted-cert -d
  "$tls_root/ca.pem"`, also fails (no file to identify the cert by), so
  the script falls into the `else` branch at line 114.
- That branch's verification guard is `[ -n "$fp" ] && ... | grep -qi
  "$fp"` — with `fp=""`, the `[ -n "$fp" ]` short-circuits to false, so
  the "was it actually removed?" check is **skipped entirely**, not
  failed.
- The same pattern repeats for the `delete-certificate -Z "$fp"` step
  at lines 122-130: with `fp=""`, `delete-certificate -Z ""` is never
  even attempted (`[ -n "$fp" ]` guards it), and the verification
  fallback is skipped for the same reason.
- The function falls through to `printf 'mac-ci-tls: untrusted %s\n'
  "$fp"` and returns 0 — reporting success with an empty fingerprint,
  even though nothing was verified removed and the CA may still be a
  trusted System root.

This directly contradicts the script's own stated invariant in its header
comment: "`untrust` never swallows a real failure -- a leftover trusted
root on a machine is the worst outcome this script can produce." A
missing/unreadable `ca.pem` at untrust time is exactly the "can't tell if
the trust anchor is gone" case that invariant is supposed to cover, and
right now it resolves to silent success instead of a hard failure.

Current call sites (`cleanup_native_services`'s `[ -d "$server_root/tls"
]` guard, `local-live-server.sh`'s `CA_TRUSTED` guard) don't appear to
delete or corrupt `ca.pem` before calling `untrust`, so this is not known
to be hit today — but nothing prevents it (a future change to teardown
ordering, a partial `rm -rf` racing a signal, a disk issue), and the
failure mode when it is hit is exactly the one this script exists to
prevent.

**Fix:** Treat a missing/unreadable `ca.pem` at untrust time as a hard
failure rather than an empty-`fp` no-op, e.g.:
```bash
cmd_untrust() {
  sudo -n true 2>/dev/null || { printf 'mac-ci-tls: passwordless sudo unavailable\n' >&2; exit 1; }
  if [ ! -f "$tls_root/ca.pem" ]; then
    printf 'mac-ci-tls: no CA at %s -- cannot verify removal, treating as failure\n' "$tls_root/ca.pem" >&2
    exit 1
  fi
  local fp
  fp="$(fingerprint_of)" || { printf 'mac-ci-tls: could not compute CA fingerprint -- cannot verify removal\n' >&2; exit 1; }
  ...
}
```

### WR-02: `verify_layer_result`'s failure-stage allowlist embeds `live-server.sh`'s stage vocabulary a third time, unenforced

**File:** `playstead-mac/scripts/ci/run-mac-verification.sh:641-647`
**Issue:** `allowed_live_stages` in the `verify_layer_result` python block
re-lists the same nine stage names that `live-server.sh`'s
`write_failure_stage` case statement (line 35) and
`run-mac-verification.sh`'s own `print_live_server_failure_stage` case
statement (lines 936-941) already enumerate. `pairing-ceremony-gate-test.sh`'s
anchor-count check (property 5) only verifies the ceremony test
identifier string is anchored twice in `run-mac-verification.sh` — it does
not check that these three stage-name lists stay in sync with each other
or with `live-server.sh`. A future stage renamed in `live-server.sh` (e.g.
splitting `redeem-pairing` into two finer stages) would silently stop
appearing in `verify_layer_result`'s `FAILURE_STAGE` output and in
`print_live_server_failure_stage`'s recognized-token case, with no test
failing to flag the drift — it would just quietly fall through to the
`invalid-token`/no-print branch.

**Fix:** Not urgent to fix in this phase, but worth a follow-up: derive
the three lists from one source (a shared file, or a self-test that diffs
the `case` patterns in `live-server.sh` against `allowed_live_stages` and
the two case statements in `run-mac-verification.sh`), matching this
phase's own stated preference for enumeration over hand-kept lists (see
`run_contract_self_tests`'s comment on the same file).

## Info

### IN-01: `PairingCoordinator.start()`'s scheme check is redundant with itself

**File:** `playstead-mac/Playstead/Pairing/PairingCoordinator.swift:97-115`
**Issue:** Lines 99-100 already guard `let scheme = url.scheme, !scheme.isEmpty`
before the URL is accepted, then lines 106-115 separately re-derive and
re-check `url.scheme?.lowercased() == "https"`. The first guard's `scheme`
binding is never used after being checked non-empty (only `host` from
that `guard` is later relevant, and only implicitly via `url`). This isn't
a bug — both checks independently pass for `https://...` — but the first
guard's scheme-non-empty check does no useful work once the second guard
requires an exact `"https"` match; a non-empty non-https scheme would be
rejected by the second guard anyway, and an empty scheme fails
`URL(string:)`'s own parsing for most inputs before `.scheme` would ever
be empty in practice.

**Fix:** Optional simplification — drop the `!scheme.isEmpty` clause from
the first guard (keep the `let scheme =` binding only if `scheme` is used
elsewhere) since the `https`-exact-match guard immediately below already
subsumes it.

### IN-02: `write_complete_verification_evidence` reads exactly four layer files with no existence check

**File:** `playstead-mac/scripts/ci/run-mac-verification.sh:1198-1201`
**Issue:**
```python
layers = [json.loads((root / f"{name}-tests.json").read_text(encoding="utf-8")) for name in ("unit", "rendering", "ui", "live-server")]
```
Unlike the `layers.json` writer a few lines below (line 1373-1375), which
tolerates a missing per-layer file (`{"layer": name, "missing": True}`
fallback), this list comprehension will raise `FileNotFoundError` — an
uncaught Python exception, not the script's usual `SystemExit(f"...")`
pattern — if any of the four `-tests.json` files is absent (e.g. one
layer's `run_test_layer` never produced a summary because the xcresult
bundle itself never materialized). The resulting traceback is bare Python
output, not one of this script's sanitized `die`/`SystemExit` messages,
and it isn't routed through the diagnostic-sanitization path the rest of
this file goes out of its way to maintain (see the `print_live_server_fixture_diagnostic`
comment on why raw output must not reach the job log). In practice this
function is only called when `aggregate == 0` (all four layers already
reported success, implying their summaries exist), so it's unlikely to
fire in the failure case — but if it ever does, the failure mode is an
unsanitized stack trace rather than a clean diagnostic.

**Fix:** Match the tolerant pattern already used at line 1373-1375, or at
minimum wrap the read in a `try/except` that raises `SystemExit` with a
bounded message naming which layer's summary was missing.
