# Phase 04.5: Code Review Report

**Reviewed:** 2026-09-09T00:00:00Z
**Depth:** standard
**Files Reviewed:** 29
**Status:** issues_found

## Summary

This phase wires trust-on-first-use certificate pinning into the pairing
ceremony (`PinnedCertificateCapture` → `PairingCoordinator.redeem()` →
`AppPaths.pinnedCertificate` → `APIClient`'s `PinningDelegate`), plus the
CI/live-server infrastructure that proves it end-to-end. The final wiring
commit (write target and read target sharing one `AppPaths.pinnedCertificate`
URL) is correct and is proven by live-object-equality tests
(`PinnedTrustWiringTests`), and `PinningDelegate.disposition(for:)` itself is
correctly falsified against a same-subject, different-key CA
(`PinnedTrustEvaluationTests`) — a real improvement over a transport-level
test that a system-trusted CI CA could pass vacuously.

Three problems undercut the pinning/observability guarantees this phase
exists to deliver: (1) `PinningDelegate` cannot distinguish "not yet paired"
from "was paired, pin file now missing/corrupted," so it silently falls back
to default trust in both cases — the exact fail-open shape a pinning
mechanism must not have once a device is paired; (2) the fail-closed rollback
in `PairingCoordinator.redeem()` discards the result of the Keychain deletion
it depends on, so a failed pin write can leave a live, usable credential
behind while reporting failure to the user; and (3) `PairingCeremonyTests`'s
own fixture-failure reporting throws away the granular stage diagnostic this
codebase went to considerable trouble to plumb through for every other
live-server test, reproducing a documented, previously-fixed "opaque hosted
failure" defect for the one test this whole phase is about.

## Critical Issues

### CR-01: Pinning fails open once a paired device's pin file is missing, unreadable, or corrupted

**File:** `playstead-mac/Playstead/Net/APIClient.swift:257-276` (`PinningDelegate.disposition(for:)`)
**Issue:** `disposition(for:)` treats "no pinned certificate exists yet" (the
pre-pairing state, where falling back to default trust is correct and
intentional) and "a pinned certificate should exist but the file is missing,
unreadable, empty, or fails to parse" (a post-pairing state) as exactly the
same case: both fall through the `guard` to `.performDefaultHandling`. There
is no way for `PinningDelegate` — or anything upstream of it — to tell these
two situations apart, because the only signal it has is "does a readable,
parseable certificate exist at this URL right now."

Once a device is paired, a stored credential exists in the Keychain and
`APIClient.send` will happily use it against whatever trust the delegate
allows. If `pinned-ca.der` is ever lost after a successful pairing — deleted
by the user, corrupted by a crash mid-write, wiped by disk pressure despite
the backup-exclusion flag, or removed by anything with local write access —
the very next request silently reverts to the platform's default trust store
instead of refusing to connect. That default trust store is exactly what
`PinnedTrustEvaluationTests`'s own doc comment identifies as attacker-
reachable: "the CI harness's own CA is separately installed as a
System-trusted root" — i.e. any locally-trusted rogue or compromised CA can
now MITM an already-paired device merely by causing the pin file to
disappear, with no user-visible signal that pinning has been silently
downgraded.

**Fix:** Give `PinningDelegate` (or its caller) a way to know "this client
believes it is paired" (e.g. pass in whether a credential currently exists,
or track "was ever paired" as a separate durable flag) and refuse the
connection (`.cancelAuthenticationChallenge`) rather than falling back to
default trust when a credential exists but the pin cannot be read/parsed:

```swift
func disposition(for serverTrust: SecTrust?, hasStoredCredential: Bool) -> URLSession.AuthChallengeDisposition {
    guard let serverTrust else { return .performDefaultHandling }
    guard
        let pinnedCertificateURL,
        let pinnedData = try? Data(contentsOf: pinnedCertificateURL),
        let pinnedCertificate = SecCertificateCreateWithData(nil, pinnedData as CFData)
    else {
        // A paired device with no readable pin must refuse, not downgrade.
        return hasStoredCredential ? .cancelAuthenticationChallenge : .performDefaultHandling
    }
    ...
}
```

### CR-02: Certificate-pin rollback ignores Keychain deletion failure, can leave a live credential with no pin

**File:** `playstead-mac/Playstead/Pairing/PairingCoordinator.swift:254-260`
**Issue:**
```swift
if let certificateCapture, let pinnedCertificateURL {
    guard certificateCapture.writeCapturedCertificate(to: pinnedCertificateURL) else {
        keychain.deleteCredential()
        state = .failed(.certificatePinFailed)
        return
    }
}
```
`keychain.deleteCredential()` returns `Result<Void, KeychainError>`
(`KeychainStore.swift:272`, `@discardableResult`), and its result is
discarded here. The whole point of this rollback (documented in the
surrounding comment and covered by
`testPairingFailsClosedAndRollsBackTheCredentialWhenTheAnchorCannotBePinned`)
is the invariant "a stored credential never exists without its pin." If the
delete itself fails for any reason (`errSecInteractionNotAllowed`, a
concurrent Keychain access, disk/IO failure, etc.), the just-stored
credential remains valid in the Keychain while the UI reports
`.certificatePinFailed` ("Pairing was undone… Try again"). The user believes
pairing failed; in fact the device is now paired with a live, usable
credential and *no* pinned certificate — precisely the state CR-01 shows is
dangerous, and the one state this rollback exists to make unreachable.

The existing test only exercises the case where deletion succeeds (a real,
healthy scoped Keychain), so this gap is untested.

**Fix:** Check the result and escalate distinctly when the rollback itself
cannot be completed, rather than reporting the same `.certificatePinFailed`
either way:

```swift
guard certificateCapture.writeCapturedCertificate(to: pinnedCertificateURL) else {
    if case .failure = keychain.deleteCredential() {
        state = .failed(.credentialRollbackFailed) // new, distinct terminal state
        return
    }
    state = .failed(.certificatePinFailed)
    return
}
```

### CR-03: `PairingCeremonyTests` discards its fixture's failure diagnostic, reproducing a previously-fixed opaque-CI-failure defect

**File:** `playstead-mac/PlaysteadUITests/PairingCeremonyTests.swift:254-282`
**Issue:** `runFixture` captures the `live-server.sh` invocation's stderr into
a `Pipe`, then throws it away:
```swift
let diagnostics = Pipe()
process.standardOutput = FileHandle.nullDevice
process.standardError = diagnostics
try process.run()
process.waitUntilExit()
guard process.terminationStatus == 0 else {
    _ = diagnostics.fileHandleForReading.readDataToEndOfFile()   // read, then discarded
    recordFixtureFailure(action: action, status: process.terminationStatus)
    return false
}
```
and `recordFixtureFailure` emits only `"pairing-ceremony-fixture-failed
action=pair-provision"` or `action=pair-approve` — never the granular
sub-stage (`provision-domain`, `request-pairing`, `approve-pairing`, etc.)
that `live-server.sh` already writes to
`PLAYSTEAD_LIVE_SERVER_STAGE_FILE` via `write_failure_stage`/`enter_stage`
for exactly this purpose.

This is the identical failure mode `live-server.sh`'s own comments describe
as previously blinding a hosted run ("Hosted run 34264338508 failed exactly
this way and said nothing about why"), and the fix already exists in this
codebase: `LiveServerSnapshotTests.swift` (`recordFixtureFailure(stage:
action:status:)`, `LiveServerSnapshotTests.swift:335-389`) reads
`PLAYSTEAD_LIVE_SERVER_STAGE_FILE` and emits one of eleven distinct, literal
`XCTAssertEqual(status, 0, "live-server-stage=<stage> action=<action>")`
messages so `run-mac-verification.sh`'s bounded diagnostic extractor
(`live_stage_pattern`, `run-mac-verification.sh:636`) can recover which
sub-stage failed from the sanitized xcresult JSON alone, with no raw stderr
ever crossing the CI artifact boundary. `PairingCeremonyTests` was added in
the same phase as that mechanism but does not use it: a hosted failure in
`testAHumanCanPairAFreshMacEntirelyFromInsideTheAppAgainstTheRealServer`'s
`pair-provision`/`pair-approve` fixture calls will report only "action=X",
with the actual reason unrecoverable from CI evidence — for the one test
this whole phase's ROADMAP criterion is about.

This gap is not caught by the existing topology self-test: `verify_four_layer_topology`/`four-layer-topology-test.sh` only checks `LIVE_SERVER_TEST="${MAC_ROOT}/PlaysteadUITests/LiveServerSnapshotTests.swift"` (`four-layer-topology-test.sh:15`) for the elevent `live-server-stage=` literals — it never looks at `PairingCeremonyTests.swift`.

**Fix:** Mirror `LiveServerSnapshotTests`'s pattern: read
`PLAYSTEAD_LIVE_SERVER_STAGE_FILE` after a non-zero exit and emit one of the
allowlisted `live-server-stage=<stage> action=<action>` literals (adding
`pair-provision`/`pair-approve` to `allowed_live_actions` in
`run-mac-verification.sh`, see WR-02 below), instead of the current bespoke,
stage-blind `"pairing-ceremony-fixture-failed action=…"` message.

## Warnings

### WR-01: `PinnedCertificateCapture` assumes the server always sends its self-signed root last in the chain

**File:** `playstead-mac/Playstead/Pairing/PinnedCertificateCapture.swift:47-59`
**Issue:** The capture pins `chain.last` from
`SecTrustCopyCertificateChain`, and the CI fixture (`mac-ci-tls.sh:81-83`)
goes out of its way to guarantee that shape ("CA MUST be last:
PinnedCertificateCapture pins chain.last"). Real-world TLS servers (Nginx,
Caddy, most managed certificate services) commonly send only the leaf plus
intermediates and never include the self-signed root at all — in that case
`chain.last` is an intermediate, not a durable root, and:
- pinning breaks the moment that intermediate is rotated (which happens on a
  schedule for most CAs, independent of the leaf's own renewal), forcing a
  re-pair the user has no reason to expect;
- if the server sends only its leaf (chain length 1), the capture pins the
  leaf itself, so the very next certificate renewal (even from the same CA,
  same key) breaks pinned trust.

This is invisible in this phase's own tests and CI fixture because the
fixture is deliberately constructed to present the ideal chain shape; it is
a real production fragility for any server operator who does not control
their chain assembly as precisely as `mac-ci-tls.sh` does.

**Fix:** At minimum, document this precondition prominently on the pairing
server's operational requirements (chain must end in the issuing root, sent
explicitly). Consider instead pinning the *actual issuing CA's public key or
SPKI hash* looked up independently (e.g. via `SecTrustCopyCertificateChain`
combined with `SecCertificateCopyKey`/pin against a known-good intermediate
set), or documenting that operators must pin at the leaf and accept the
renewal-triggered re-pair as expected behavior, rather than silently
depending on chain ordering that most TLS deployments will not produce.

### WR-02: `run-mac-verification.sh`'s diagnostic allowlist doesn't include the pairing ceremony's own fixture actions

**File:** `playstead-mac/scripts/ci/run-mac-verification.sh:647`
**Issue:** `allowed_live_actions = {"prepare", "second", "verify", "unknown"}`
does not include `"pair-provision"` or `"pair-approve"`, the two actions
`PairingCeremonyTests` actually invokes `live-server.sh` with
(`PairingCeremonyTests.swift:72,115`). Even after CR-03 is fixed to emit
`live-server-stage=<stage> action=pair-provision`/`action=pair-approve`
literals, the extractor at `run-mac-verification.sh:759` (`if stage in
allowed_live_stages and action in allowed_live_actions`) would silently drop
that diagnostic, because the `action` half of the tuple never matches.

**Fix:** Add `"pair-provision"` and `"pair-approve"` to `allowed_live_actions`
alongside fixing CR-03.

### WR-03: `APIClient.send`'s header-dictionary construction can crash on a case-colliding duplicate header

**File:** `playstead-mac/Playstead/Net/APIClient.swift:220-223`
**Issue:**
```swift
let headerDict = Dictionary(uniqueKeysWithValues: http.allHeaderFields.compactMap { key, value -> (String, String)? in
    guard let k = key as? String, let v = value as? String else { return nil }
    return (k.lowercased(), v)
})
```
`Dictionary(uniqueKeysWithValues:)` traps with a fatal error if two entries
lowercase to the same key. `HTTPURLResponse.allHeaderFields` can contain
multiple header fields differing only in case (most notably `Set-Cookie`,
which Foundation deliberately does not fold into a single comma-joined
entry). Since this pinned client's requests occur both before pairing
(default trust) and after (pinned trust that, per CR-01, can silently
degrade to default trust), any response — including one from an
on-path attacker exploiting the CR-01 gap, not only the legitimate server —
that returns two case-differing header names of the same lowercased spelling
will crash the app (a denial-of-service, not a memory-safety issue, but a
real crash reachable from response contents this client does not fully
control).

**Fix:** Fold duplicates rather than requiring uniqueness, e.g.:
```swift
var headerDict: [String: String] = [:]
for (key, value) in http.allHeaderFields {
    guard let k = key as? String, let v = value as? String else { continue }
    headerDict[k.lowercased(), default: ""] += headerDict[k.lowercased()] == nil ? v : ",\(v)"
}
```
or simply keep the last value per lowercased key with `reduce(into:)`.

## Info

### IN-01: Unused `host` binding in `PairingCoordinator.start(baseURLString:)`

**File:** `playstead-mac/Playstead/Pairing/PairingCoordinator.swift:100-104`
**Issue:**
```swift
guard
    let url = URL(string: baseURLString.trimmingCharacters(in: .whitespacesAndNewlines)),
    let scheme = url.scheme, !scheme.isEmpty,
    let host = url.host, !host.isEmpty
else { ... }
```
`host` is bound only to be checked non-empty and is never referenced again
(the actual base URL used downstream is `url`, not a reconstructed
scheme+host). This is a harmless but avoidable "value was never used"
compiler warning.

**Fix:** `guard ..., let host = url.host, !host.isEmpty else { ... }` →
`guard ..., !(url.host ?? "").isEmpty else { ... }`, or keep the binding but
silence intentionally with `_ = host`.

### IN-02: `PinnedCertificateCapture.writeCapturedCertificate` has a brief non-atomic permission window

**File:** `playstead-mac/Playstead/Pairing/PinnedCertificateCapture.swift:67-76`
**Issue:** The certificate is written with `Data.write(to:options: .atomic)`
and then `chmod`ed to `0o600` as a *separate* filesystem call. Between those
two calls the file briefly exists with the process's default umask
permissions (typically `0644`), readable by other local accounts on a
shared/multi-user Mac. This is a narrow, low-severity TOCTOU window, not
exploitable remotely, but worth closing given the file's contents (a trust
anchor) are otherwise treated as sensitive.

**Fix:** Write to a temp file with restrictive permissions set before the
atomic move, e.g. `open(O_WRONLY | O_CREAT | O_EXCL, 0o600)` plus
`rename(2)`, or set `NSFileProtectionKey`/`posixPermissions` as part of the
write's resource values rather than as a follow-up `setAttributes` call.
