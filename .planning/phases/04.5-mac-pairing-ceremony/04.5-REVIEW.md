# Phase 04.5: Code Review Report

**Reviewed:** 2026-09-08
**Depth:** standard
**Files Reviewed:** 16
**Status:** issues_found

## Summary

The plaintext `device_code` and the redeemed credential are handled correctly
at the transport layer: neither ever appears in a URL, a log statement, or a
user-visible error message (`PairingError.transport` carries only
`localizedDescription`, never a request body). `PairingClient` maps server
`code` values to typed errors rather than propagating free text, and
`PairingCoordinatorTests`/`PairingCeremonyTests` genuinely exercise a real
scoped Keychain rather than mocking it.

The real defect is structural, not lexical: `PairingCoordinator.cancel()` is
purely cooperative — it flips `state` and clears local fields, but does
nothing to stop a `Task` that is already suspended inside an in-flight
network `await` (`createRequest`, `pollStatus`, or `redeem`). Because that
`Task` is never actually interrupted, and because none of `start()`,
`pollLoop()`, or `redeem()` re-check cancellation or a fresh generation
token after resuming from a network `await`, a user who cancels the
ceremony (closing the sheet, which calls `cancel()` from `onDisappear`) can
still have the coordinator silently write a credential to the Keychain and
flip its state back to `.paired` moments later, overwriting the `.idle`
state `cancel()` just set. The same class of bug lets a stale, already-
cancelled poll or create-request response drive further ceremony steps.
Compounding this, a failed or impossible TOFU certificate capture (e.g. a
non-`https` server URL) is silently ignored — pairing still reports success
to the user with no pinned certificate on disk.

## Critical Issues

### CR-01: `cancel()` does not stop an in-flight network operation — a cancelled ceremony can still write a credential to the Keychain and resurrect `.paired` state

**File:** `playstead-mac/Playstead/Pairing/PairingCoordinator.swift:113-199`

**Issue:**
`cancel()` only mutates local state:
```swift
func cancel() {
    pollTask?.cancel()
    pollTask = nil
    state = .idle
    deviceCode = nil
    requestID = nil
    baseURL = nil
}
```
`pollTask?.cancel()` sets Swift's cooperative cancellation flag, but nothing
in `pollLoop()` or `redeem()` checks `Task.isCancelled` *after* an `await`
resumes with a result. Concretely:

- `pollLoop()` checks `case .awaitingApproval = state` and `Task.isCancelled`
  **before** calling `await client.pollStatus(...)`, but not after it
  returns. If `cancel()` runs while that network call is in flight (e.g. the
  user closes the pairing sheet — `PairingView.onDisappear` calls
  `coordinator?.cancel()`), the poll result is still processed when it
  arrives: a `.approved` result still triggers `await redeem()`.
- `redeem()` (`PairingCoordinator.swift:173-199`) captures `baseURL`,
  `requestID`, `deviceCode` as local constants *before* its own network
  `await`, so a concurrent `cancel()` cannot invalidate the in-flight call.
  When `client.redeem(...)` returns, `redeem()` unconditionally calls
  `keychain.storeCredential(credential)` and sets
  `state = .paired(deviceID:)` — even though `cancel()` may have already set
  `state = .idle` and the view presenting this coordinator may already be
  gone.
- The same pattern exists in `start()`: `cancel()` during the in-flight
  `await client.createRequest(...)` clears `baseURL`/`deviceCode`/`state`,
  but the call still completes and overwrites `state` back to
  `.awaitingApproval` and starts a brand-new poll loop (`startPolling`),
  reviving a ceremony the user just cancelled.

Nothing keeps the coordinator instance itself from surviving past `cancel()`
either: `pollLoop`/`redeem` are ordinary (non-weak) method-call frames, so
the object stays alive for the duration of the call regardless of the
view's `@State` lifetime. The net effect: a user who dismisses the pairing
sheet mid-ceremony can still end up with a credential silently written to
the Keychain with no user-visible confirmation, in a coordinator instance
whose UI has already vanished — and the credential IS the durable secret
this ceremony exists to protect. `PairingCoordinatorTests
.testCancellingStopsThePollLoop` only exercises cancellation while polling
is `.pending` (no in-flight network call to race against), so this path is
untested.

**Fix:** Add a monotonically increasing "ceremony generation" token (or an
explicit `isCancelled` flag) that every mutation of `state`/Keychain write
checks immediately before committing, e.g.:
```swift
private var generation = 0

func cancel() {
    generation += 1
    pollTask?.cancel()
    pollTask = nil
    state = .idle
    deviceCode = nil
    requestID = nil
    baseURL = nil
}

private func redeem() async {
    let myGeneration = generation
    guard let baseURL, let requestID, let deviceCode else { ... }
    state = .redeeming
    do {
        let redeemed = try await client.redeem(...)
        guard myGeneration == generation else { return } // cancelled meanwhile
        switch keychain.storeCredential(credential) { ... }
    } ...
}
```
Apply the same guard immediately after every `await` in `start()` and
`pollLoop()` before committing `state` or performing the Keychain write.

### CR-02: A failed or impossible TOFU certificate capture is silently ignored — pairing reports success with no pinned certificate

**File:** `playstead-mac/Playstead/Pairing/PairingCoordinator.swift:186-190`, `playstead-mac/Playstead/Pairing/PinnedCertificateCapture.swift:55-65`, `playstead-mac/Playstead/Pairing/PairingCoordinator.swift:85-92`

**Issue:** After a successful Keychain write, the coordinator does this:
```swift
if let certificateCapture, let pinnedCertificateURL {
    certificateCapture.writeCapturedCertificate(to: pinnedCertificateURL)
}
state = .paired(deviceID: redeemed.deviceID)
```
`writeCapturedCertificate(to:)` is `@discardableResult` and returns `false`
whenever nothing was captured or the write failed — and here the return
value is discarded. Two realistic paths produce exactly that outcome:

1. `start(baseURLString:)` (`PairingCoordinator.swift:85-92`) validates only
   that the URL has a non-empty scheme and host — it does not require
   `https`. If a user (or a MITM performing a protocol downgrade) pairs
   against a plain `http://` server, no TLS handshake ever occurs, so
   `PinnedCertificateCapture.urlSession(_:didReceive:)` never fires and
   `capturedCertificateData` stays `nil` for the entire ceremony.
2. Even over `https`, a disk-full or permissions failure in
   `writeCapturedCertificate`'s `data.write(to:options:.atomic)` is caught
   and converted to a silent `false`.

In both cases, `state` still becomes `.paired`, `PairingView` renders "This
Mac is paired," and the user has no indication that the certificate pin —
the entire point of the TOFU capture this ceremony performs — was never
established. Every subsequent `APIClient` request is left to whatever trust
policy applies when no pin exists on disk, silently weakening (or entirely
defeating, depending on that policy) the pinning guarantee the pairing flow
is supposed to set up.

**Fix:** Require `https` in `start()`'s URL validation (reject non-`https`
schemes the same way an empty scheme/host is rejected today), and surface
`writeCapturedCertificate`'s boolean result as part of the terminal state —
either a new `PairingError` case (e.g. `.certificatePinFailed`) that routes
through `.failed`, or a distinct successful-but-unpinned message in the
`.paired` case, rather than treating it as unconditionally successful:
```swift
guard let certificateCapture, let pinnedCertificateURL,
      certificateCapture.writeCapturedCertificate(to: pinnedCertificateURL) else {
    state = .failed(.certificatePinFailed) // new case
    return
}
state = .paired(deviceID: redeemed.deviceID)
```

## Warnings

### WR-01: Test-only device-name override is reachable in production builds, unlike every other test hook in this codebase

**File:** `playstead-mac/Playstead/Pairing/PairingCoordinator.swift:203-205`

**Issue:**
```swift
nonisolated static func defaultDeviceName() -> String {
    ProcessInfo.processInfo.environment["PLAYSTEAD_UI_TEST_PAIRING_DEVICE_NAME"] ?? Host.current().localizedName ?? "Mac"
}
```
This is the default `deviceName` used by every `PairingCoordinator`
constructed via `AppEnvironment.makePairingCoordinator()`
(`PlaysteadApp.swift:907-919`), which is the production pairing entry
point — it is not gated behind `#if DEBUG`/`#if UI_TESTING` the way every
other test-only environment override in this codebase is (contrast
`XCTestHostBootstrap.isRequested()`, gated behind `#if DEBUG`, or the
`UI_TESTING`-gated branches in `PlaysteadApp`/`AppEnvironment`). A shipped,
non-debug build of Playstead.app will still honor
`PLAYSTEAD_UI_TEST_PAIRING_DEVICE_NAME` if it happens to be set in the
launch environment, letting anyone who can control the app's environment
(e.g. a malicious launch wrapper) spoof the device name shown to whoever
approves the pairing request in the server's devices console — a
confused-deputy vector for social-engineering an approval intended for a
different, legitimately-named device.

**Fix:** Gate the override behind the same compilation condition every
other test hook in this codebase uses:
```swift
nonisolated static func defaultDeviceName() -> String {
#if DEBUG
    if let override = ProcessInfo.processInfo.environment["PLAYSTEAD_UI_TEST_PAIRING_DEVICE_NAME"] {
        return override
    }
#endif
    return Host.current().localizedName ?? "Mac"
}
```

### WR-02: `PairingError.slowDown`'s user-facing message can never be reached from the poll loop it describes

**File:** `playstead-mac/Playstead/Pairing/PairingView.swift:113-114`, `playstead-mac/Playstead/Pairing/PairingCoordinator.swift:156-162`

**Issue:** `pollLoop()` catches `PairingError.slowDown` internally and turns
it into a backoff (`interval = min(interval * 2, maxPollInterval); continue`)
— it never reaches `state = .failed(.slowDown)`. The only way
`.failed(.slowDown)` can occur is if `createRequest` or `redeem` (not the
poll) happen to return a 429, at which point `PairingView`'s message
("Polling too fast — slowing down automatically.") is describing a poll
backoff that isn't actually happening — the ceremony is dead-ended in
`.failed` and the user must click "Request pairing" again, nothing backs
off automatically. The copy is misleading for the two call sites that can
actually produce it.

**Fix:** Either give `.slowDown` a request/redeem-specific message ("The
server is rate-limiting this pairing attempt. Wait a moment and try
again."), or split it into two distinct error cases so the copy always
matches the operation that actually failed.

### WR-03: `redeem()`'s Keychain-write failure path leaves the consumed `device_code` with no recovery other than a full restart

**File:** `playstead-mac/Playstead/Pairing/PairingCoordinator.swift:173-199`

**Issue:** By the time `keychain.storeCredential(credential)` is evaluated,
the server has already durably consumed `device_code` (the redeem call
succeeded). If the local Keychain write then fails, `state = .failed(.keychainWriteFailed)`
correctly tells the user their credential wasn't saved — but there is no
way to retry storing the *already-redeemed* credential; the only path
forward the UI offers is "Request pairing" again, which starts an entirely
new ceremony. This is consistent with the one-time-use `device_code`
design and is likely an accepted limitation, but it is undocumented in this
file (unlike every other edge case here, which carries an explicit
rationale comment) and worth either a comment explaining it's intentional
or a short-lived in-memory retry affordance.

**Fix:** Add a doc comment on `.keychainWriteFailed` in `PairingClient.swift`
or on this branch noting that the redeemed credential cannot be recovered
and a fresh ceremony is required, so a future reader doesn't try to "fix"
this by adding a retry that assumes `device_code` is still valid.

## Info

### IN-01: `throwIfNotSuccess`'s `(409, _)` fallthrough silently becomes `.invalidResponse` rather than a more specific signal

**File:** `playstead-mac/Playstead/Net/PairingClient.swift:227-242`

**Issue:** A 409 with a `code` other than the two known values (or no
`code` at all) falls through to `default: throw .invalidResponse`, which
`PairingView` renders as "The server address is not valid, or it sent an
unexpected response." — a plausible but slightly misleading message for a
409 (which by definition reached a valid server and a valid endpoint). Not
incorrect, but worth a comment noting the fallthrough is deliberate rather
than an oversight, since every other status/code pair here is enumerated
explicitly.

**Fix:** A one-line comment above the `switch` noting unmapped `(status,
code)` pairs deliberately collapse to `.invalidResponse` would remove the
ambiguity for a future reader extending this switch.
