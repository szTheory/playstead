# Phase 04.5 Plan 01: Mac Pairing Ceremony Summary

**A human can now pair a fresh Mac from inside the app — enter a server URL, watch the display code render, have it approved, and land with a real credential in the Keychain — via `PairingClient`/`PairingCoordinator`/`PairingView`, reachable from both the empty-state button and a new app-menu command.**

## Performance

- **Duration:** 95 min
- **Tasks:** 6
- **Files modified:** 18 (7 created, 11 modified)

## Accomplishments

- `PairingClient`: an unauthenticated actor covering `createRequest`/`pollStatus`/`redeem`, mapping RFC 9457 `code` values to a typed `PairingError` (`expired`, `alreadyRedeemed`, `notApproved`, `slowDown`, `notFound`, `denied`) so the coordinator branches on a value, never a message string.
- `PairingCoordinator`: the whole ceremony (`idle -> requesting -> awaitingApproval -> redeeming -> paired/failed`) as a directly constructible, independently testable type — honors the server's `poll_interval`, doubles (capped) on `slow_down`, stops at `expires_at`, and is cancellable.
- `PinnedCertificateCapture`: records the server's trust anchor during the handshake and writes it to `AppPaths.root/pinned-ca.der` strictly after the credential is durably stored, matching `APIClient`'s existing trust-on-first-use contract.
- `PairingView`, shaped after `AdapterSetupView`, reachable from `LibraryShellView`'s long-standing "Pair with your Playstead server" empty-state string (which finally has a real action behind it — WINDOWS #54) and from a new "Pairing" app-menu command for re-pairing.
- 19 new automated tests across two levels (10 coordinator unit tests + 5 reachability tests + 1 live-server test authored/registered/compiled, plus 2 new server-side mix-task tests and 2 registration/safety-guard passes).

## Decisions Made

- Reused `LibraryShellView`'s existing `ShellSurface`/sheet mechanism for pairing rather than a bespoke presentation path.
- Added a CI-fixture-only `approve-sole` mix task variant (identifies the sole pending request by display code + device label) instead of touching any production pairing route/controller/rate limit — the live-server proof's app-driven request creation has no way to learn the server-generated request id the existing `approve` task requires.
- `AppEnvironment` now threads a `pairingKeychain` alongside `apiClient` so pairing always writes into the exact Keychain the paired client reads from in every launch mode (production, live-server harness), while staying `nil` (and thus never constructing a real `KeychainStore`) for every deterministic UI-testing profile.
