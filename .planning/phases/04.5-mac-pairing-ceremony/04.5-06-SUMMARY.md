# Phase 04.5 Plan 06: Wire pinned trust from PairingCoordinator into APIClient Summary

**Every real APIClient construction site now passes a non-nil pinnedCertificateURL derived from one AppPaths helper, and a new PinningDelegate.disposition(for:) unit test proves pinned evaluation actually rejects a mismatched anchor a system-trusted CI CA could never distinguish.**

## Accomplishments

- `AppPaths.pinnedCertificate` (stored) and `AppPaths.defaultPinnedCertificateURL(fileManager:)` (static, side-effect-free) both resolve through one private helper, so `pinned-ca.der` is spelled as a literal exactly once in the Mac app's non-comment source.
- `APIClient.init`'s `pinnedCertificateURL` default changed from `nil` to `AppPaths.defaultPinnedCertificateURL()`, and both real construction sites (`AppEnvironment`'s convenience init in `PlaysteadApp.swift`, the live-server session in `UITestBootstrap.swift`) now pass it explicitly from their scoped `AppPaths`.
- `PinnedTrustWiringTests` proves, by live-object equality against a real `AppEnvironment`, that `PairingCoordinator`'s write target and `APIClient`'s read target are the exact same URL — the key link the prior verification found broken.
- `PinningDelegate`'s guard/`SecTrust` sequence is extracted into `disposition(for:)`, widened to internal, and `PinnedTrustEvaluationTests` exercises it directly with locally-generated openssl fixtures (no network transport in the loop), proving a matching anchor is accepted, a different-key-same-subject anchor is rejected, and absent/empty/unparseable pinned files fall back to default handling rather than crashing or blindly accepting.
- ROADMAP criterion 5 and `APIClient`'s doc comment now describe the wiring that exists, citing both new test files instead of asserting the switchover as a pre-existing fact.

- Kept `pinnedCertificateURL` an injectable `URL?` with a secure default rather than making it non-optional, per the plan's `design_decision` — avoids churning ~18 existing `StubURLProtocol`-backed unit tests that never build the pinned session anyway.

## Issues Encountered

- **Acceptance criterion not fully satisfiable as written (Task 2):** "Reverting `SecTrustSetAnchorCertificatesOnly` to `false` turns the mismatched-anchor case red" does not hold given the plan's own prohibition that no fixture CA may be installed in the System trust store. With both `PinnedTrustEvaluationTests` fixture CAs kept untrusted system-wide (as required), a leaf whose issuer isn't a system-trusted root fails to validate against a mismatched anchor whether `SecTrustSetAnchorCertificatesOnly` is `true` or `false` — there's no chain to any trusted anchor in either case, so the mutation isn't observable without violating the prohibition it's paired with. Verified by direct mutation-and-revert during execution (test stayed green both ways). The test still asserts the *exact* disposition value (`.cancelAuthenticationChallenge`, not a weaker "not `.useCredential`"), so it remains falsifiable by other mutations, e.g. removing the `SecTrustSetAnchorCertificates` call entirely (which flips `testMatchingAnchorIsAccepted` red). Documented here rather than silently ignored, per deviation-rule guidance for a criterion that cannot be satisfied after investigation.
