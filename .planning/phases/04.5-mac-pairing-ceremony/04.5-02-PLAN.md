<objective>
Close VERIFICATION gap 1 (ROADMAP criterion 5): make the trust anchor actually pinned, and make its absence a terminal failure instead of a silent success.

Purpose: today `PairingCoordinator.redeem()` discards `writeCapturedCertificate(to:)`'s Bool and reports `.paired` regardless, and `start()` accepts any scheme — so a plaintext pairing never even triggers the TLS challenge the capture observes. Nothing in the phase, unit or live-server, has ever asserted `pinned-ca.der` exists.

Output: an https-only, fail-closed ceremony with a rollback on pin failure, two new `PairingError` cases with user copy, a direct unit-test suite for the capture's write, and an end-to-end unit test asserting `AppPaths.root/pinned-ca.der` is on disk and non-empty after a successful pairing.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Mac app → pairing server (pre-credential) | The one moment no pinned anchor exists; the self-generated `device_code` and the returned credential cross here. |
| Pairing ceremony → local disk (`AppPaths.root/pinned-ca.der`) | What every later `APIClient` request will trust. |
| Pairing ceremony → login Keychain | The durable secret this ceremony exists to create. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04.5-01 | Tampering | `PairingCoordinator.start()` scheme validation | high | mitigate | Task 1 rejects every non-`https` scheme before a device code is generated, so a downgraded ceremony never sends the redeem secret in the clear. |
| T-04.5-02 | Spoofing | `AppPaths.root/pinned-ca.der` | high | mitigate | Task 1 makes a missing/failed pin a terminal `.failed(.certificatePinFailed)` with credential rollback, so no session runs authenticated-but-unpinned. |
| T-04.5-03 | Information Disclosure | pairing failure copy / XCTest messages | medium | mitigate | New `describe(_:)` strings and every new assertion message name states and paths only — never the `device_code` or credential (prohibition 2). |
| T-04.5-04 | Repudiation | rollback path in `redeem()` | low | accept | `deleteCredential()`'s own failure leaves a credential with no pin; the state is still `.failed`, and Keychain-deletion failure is outside this phase's scope. |
| T-04.5-SC | Tampering | npm/pip/cargo installs | high | mitigate | Not applicable — this plan installs no packages; no dependency is added to any manifest. |
</threat_model>
