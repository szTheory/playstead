# Phase 04.5 Plan 2: Fail-closed trust-anchor pinning for the Mac pairing ceremony Summary

**Pairing now refuses plaintext addresses before any network call and rolls back the Keychain credential if the server's trust anchor can't be pinned to disk — closing VERIFICATION gap 1 (ROADMAP criterion 5).**

## Performance

- **Duration:** 42 min
- **Started:** 2026-09-09T09:40:00Z
- **Completed:** 2026-09-09T10:22:00Z
- **Tasks:** 3
- **Files modified:** 7 (1 created, 6 modified)

## Accomplishments
- `PairingCoordinator.start(baseURLString:)` requires `https` before generating a device code or making any network call, ending `.failed(.insecureServerAddress)` otherwise.
- `PairingCoordinator.redeem()` no longer discards `writeCapturedCertificate(to:)`'s result: a failed pin write rolls back the just-stored Keychain credential via `KeychainStore.deleteCredential()` and ends `.failed(.certificatePinFailed)` — `.paired` is reached only after both the credential and the pin are durable.
- Two new `PairingError` cases (`.insecureServerAddress`, `.certificatePinFailed`) each get distinct, actionable copy in `PairingView.describe(_:)`.
- `PinnedCertificateCapture` gains a test-only `init(capturedCertificateData:)` seam; production construction (`PlaysteadApp.makePairingCoordinator()`) is unchanged.
- New `PinnedCertificateCaptureTests` proves the capture's write directly: correct bytes, `0600` permissions, `false` (never a throw) on empty capture or a missing destination directory.
- `PairingCoordinatorTests` gained 5 new tests covering the pin tracer proof, the plaintext refusal, the empty-address refusal, the fail-closed rollback, and re-entrant `start()`.
- `PairingCeremonyTests` (live-server, still not executed) now pairs over `https` and asserts `pinned-ca.der` exists and is non-empty after success — the first version of this test that could ever observe criterion 5, with a doc comment naming the TLS-on-4010 precondition still blocking a hosted run.
