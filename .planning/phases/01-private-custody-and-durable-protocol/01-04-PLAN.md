<objective>
Build the pairing ceremony and the device credential that every future Playstead client authenticates with — an RFC 8628-shaped, two-code flow where the security property is a human comparing one code on two screens.

Purpose: PROT-01 and PROT-02 are the identity spine of the protocol. The Mac client in Phase 3 consumes exactly what this plan publishes, so the API shape and its contract tests are the real deliverable.

Output: the pairing domain and state machine, the `/api/v1/device-pairing` endpoints, one-time credential issuance, header-only device authentication, use-activated rotation, and revocation with tombstones — all under contract test.
</objective>

Claimed fields are stored under names that make their untrusted provenance obvious at every read site; observed fields (`requesting_ip`, `inserted_at`, `display_code`) are not.

`Playstead.Pairing.DisplayCode` generates the human-readable code: 8 characters from a fixed 20-letter consonant alphabet, drawn with `:crypto.strong_rand_bytes/1` using rejection sampling so the distribution is uniform, formatted as two groups of four separated by a hyphen. This code is only ever compared visually — it is never an input to any authorization decision.

`Playstead.Pairing` implements the persisted state machine: `pending` transitions to `approved`, `denied`, or `expired`; `approved` transitions to `redeemed` exactly once. All state lives in Postgres; RESEARCH.md's anti-pattern list names LiveView process state as the specific wrong home for pairing facts because LiveView re-runs mount on reconnect.

`create_request/1` takes the client's self-reported claims plus the client-generated `device_code`, stores only the SHA-256 hash of that code, mints a display code, sets `expires_at` 10 minutes out, and records a `pairing_requested` audit entry. Before inserting, enforce the small fixed pending-queue cap by evicting the oldest pending request inside the same transaction — eviction is explicit, audited as `pairing_request_evicted`, and never silent.

`get_request_status/1` is the poll endpoint's backing function. It re-derives expiry from `expires_at` on every call so a request that has aged past its window reports `expired` without depending on a background sweep. Also add `expire_stale_requests/0` as an Oban job for housekeeping, but never let correctness depend on it.

`approve/2` and `deny/2` take a `%Scope{}` and re-check expiry server-side, bound to the specific request ID and its display code, before transitioning. Approval is always an explicit owner action; there is no code path that auto-approves, including when exactly one request is pending — D-07 forbids it, and the whole security property is the human comparison.

Add `PlaysteadWeb.Plugs.ClientIp` deriving the requesting IP from the trusted proxy hop only (the Caddy container on the compose network), ignoring arbitrary client-supplied forwarding headers.

Expose two endpoints in the unauthenticated `/api/v1` pipeline: `POST /device-pairing/requests` returning the request ID, display code, poll interval, and expiry; and `GET /device-pairing/requests/:id` returning the status. The poll endpoint advertises the interval and, when a client polls faster than that interval, returns the `slow_down` code per RFC 8628 rather than silently tolerating it. Rate-limit request creation per IP through `PlaysteadWeb.Plugs.Throttle`. Neither endpoint accepts the display code as an input — there is no guessable-code surface.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Unpaired client → pairing request endpoints | Fully untrusted; anyone who can reach the server can create a request |
| Unpaired client → redemption endpoint | Untrusted, but must present the `device_code` it generated |
| Paired device → authenticated `/api/v1` | Credential-bearing; every request is authorized by the Authorization header |
| Owner console → approve/deny/revoke | Authenticated, scope-bound, sudo-gated commands |
| Caddy proxy hop → app | The only source of a trustworthy requesting IP |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-21 | Elevation of Privilege | Display-code guessing | critical | mitigate | The display code is never an authorization input; redemption requires the separate 256-bit `device_code`, so no unauthenticated endpoint accepts a code guess (D-08, tasks 1 and 2) |
| T-01-22 | Elevation of Privilege | Auto-approval of a lone pending request | critical | mitigate | No code path transitions a request to approved without an explicit `%Scope{}`-bound owner action; the "sole pending request" convenience is forbidden outright (D-07, task 1) |
| T-01-23 | Elevation of Privilege | Concurrent redemption | high | mitigate | `redeem/2` runs in one `Ecto.Multi` with a unique constraint on the redeemed transition; the loser receives 409 and no second credential exists (task 2) |
| T-01-24 | Tampering | Approving an expired request | high | mitigate | Expiry is re-derived server-side on every poll and re-checked at approval time, bound to the request ID and its display code; the client countdown is presentation only (D-12, task 1) |
| T-01-25 | Information Disclosure | Credential leakage into logs or URLs | high | mitigate | The credential is delivered once, stored hashed, accepted only from the Authorization header, excluded from parameter logging, and never rendered in an error body; the console sees only a fingerprint prefix (D-10, task 2) |
| T-01-26 | Spoofing | Forged requesting IP on the evidence card | medium | mitigate | `PlaysteadWeb.Plugs.ClientIp` takes the IP only from the trusted Caddy hop and ignores arbitrary client-supplied forwarding headers (D-09, task 1) |

| T-01-28 | Repudiation | Pairing lifecycle | medium | mitigate | Every transition — requested, evicted, approved, denied, expired, redeemed, revoked — writes an append-only audit entry (D-12, tasks 1-3) |
| T-01-29 | Elevation of Privilege | Cross-scope device access | high | mitigate | `list_devices/1`, `rename_device/3`, and `revoke_device/2` are all `%Scope{}`-bound and tested against a foreign scope (task 3) |
