# Phase 1 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope of this contract:** the Phoenix LiveView console only — first-run setup wizard, login screen, Devices page (pairing approval queue, device list, browser-sessions list), and sudo-mode re-authentication. The native Mac client's UI is out of scope for this phase (Phase 3); where the pairing ceremony has a Mac-side surface, this contract only binds the console side and must remain consistent with the Mac's future large-code display per CONTEXT.md D-07..D-12.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — this is a Phoenix LiveView project, not a React/Next.js/Vite app; the shadcn gate does not apply |
| Preset | not applicable |
| Component library | Phoenix 1.8 CoreComponents (`core_components.ex`) + Tailwind CSS utility classes — no React component library |
| Icon library | Heroicons (outline for default state, solid for active/selected state) — bundled with Phoenix 1.8 generators |
| Font (UI) | `Inter, ui-sans-serif, system-ui, sans-serif` — clean, high-legibility console face; no custom webfont license needed (self-hostable via `vendor/`) |
| Font (codes) | `"JetBrains Mono", ui-monospace, "SFMono-Regular", monospace` — used ONLY for: setup token, pairing display code, recovery codes, device credential fingerprint. Monospace is a correctness requirement here, not a style choice — the owner must visually compare codes character-by-character (D-07, D-09). |

Rationale: greenfield Elixir/Phoenix app (`playstead-server/` currently contains only a README). No existing tokens, components, or Tailwind config to inherit. This contract establishes the console's design baseline from scratch, tuned to the "beautifully designed game console that happens to respect ordinary files" ethos (EXPERIENCE-ETHOS.md) applied to an admin/operator surface — closer to Grafana/Portainer/Vaultwarden in density and tone than to a consumer app.

## Spacing Scale

Declared values (must be multiples of 4), Tailwind default scale:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps, badge inline padding |
| sm | 8px | Compact element spacing (form field to helper text) |
| md | 16px | Default element spacing (form field groups, card internal padding) |
| lg | 24px | Section padding (wizard step container, card padding) |
| xl | 32px | Layout gaps between major page regions (Devices page: queue vs. device list) |
| 2xl | 48px | Major section breaks (between wizard steps' visual "beat") |
| 3xl | 64px | Page-level spacing (top of centered auth/wizard card from viewport edge) |

Exceptions:
- Icon-only buttons (approve/deny/revoke/rename glyph buttons on Devices page) use a 44×44px minimum touch/click target even though the visible icon is 20px — accessibility floor (QUAL-01), not a spacing-scale violation since the extra area is padding, not a new token. **Label-fallback strategy (mandatory, no exceptions):** every icon-only button carries an accessible name via the Phoenix CoreComponents idiom — an `aria-label` on the `<button>`/`<.icon_button>`, or an `sr-only` span inside it, matching the button's action verb exactly (e.g. `aria-label="Approve device"`, `aria-label="Deny pairing request"`, `aria-label="Revoke [device name]"`, `aria-label="Rename [device name]"`). This is never optional and never satisfied by `title` alone. A visible tooltip (on hover/focus, using the same copy as the accessible name) is a nice-to-have on top of this, not a substitute for it.
- The pairing display code and setup token render at a deliberately oversized type scale (see Typography — Display role) with generous letter-spacing; this is a typography decision, not a spacing exception.

## Typography

**Font-size budget: 5 sizes, formally exceeding the standard 4-size constraint by one documented exception.** The 4-role UI hierarchy below (Body/Label/Heading/Display) uses exactly 4 sizes, satisfying the constraint on its own. The 5th size — 40px — is reserved exclusively for the pairing display code and exists as a separately-justified security exception, the same pattern already used for the 44px touch-target exception in the Spacing Scale section above. This is a constraint upgrade, not a violation: declaring it explicitly here is what makes it self-justifying and re-check-safe.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 (regular) | 1.5 |
| Label | 14px | 600 (semibold) | 1.5 |
| Heading | 20px | 600 (semibold) | 1.2 |
| Display | 28px | 600 (semibold) | 1.2 |

Only 2 weights exist in the system: 400 regular and 600 semibold. Never introduce a 500 or 700 weight.

**Code role (monospace font, separate from the 4 roles above — used only where D-07/D-09 require visual code comparison):**

| Element | Size | Weight | Letter Spacing |
|---------|------|--------|-----------------|
| Pairing display code (`MKTV-QRZC`) — **5th size, exception** | 40px | 600 | 0.08em |
| Setup token / recovery codes | 20px | 600 | 0.04em |
| Device credential fingerprint (SHA-256 prefix) | 14px | 400 | normal |

**Typography exception — pairing display code at 40px (5th font size):**
- **Why it exists:** D-07 requires the owner to instantly and reliably compare the display code shown on the console against the code shown on the Mac from across a room. This is a security property, not an aesthetic preference — a code that is easy to misread or skim past defeats the pairing ceremony's purpose.
- **Why it can't fold into the 4-role Display size (28px):** 28px is tuned for the console's ordinary heading hierarchy (readable at desk distance, sitting alongside body copy). The pairing code has a materially different reading distance and error-tolerance requirement — it must be legible and comparable at a glance from further away, and misreads have a real security cost. Shrinking it to 28px to preserve a 4-size budget would weaken the exact property D-07 exists to protect.
- **Scope of the exception:** exactly one element (the pairing display code), one screen (the pairing approval card / evidence card), never reused elsewhere. It does not open the door to arbitrary additional sizes — any other new size request must still fit inside the 4-role budget or be rejected.
- **Reinforcement, not replacement:** dominance is also carried by letter-spacing (0.08em, widest in the system), accent color (`#38BDF8`, reserved for exactly this + primary CTAs), and layout placement — size alone is not asked to do all the work.

The pairing display code is the single largest text element in the entire console — it is the whole security property (D-07) and must dominate the approval card visually over every "claimed" field (device name, platform, IP).

## Color

Dark-surfaced console (matches the cited precedents Grafana/Portainer/Vaultwarden and the "game console" ethos), single theme for Phase 1 — light/dark toggle is explicitly deferred, not part of this contract.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#0F172A` (slate-900) | Page background, wizard/login page canvas |
| Secondary (30%) | `#1E293B` (slate-800) | Cards (approval cards, device rows, session rows), nav rail, wizard step container |
| Accent (10%) | `#38BDF8` (sky-400) | Reserved exclusively for: primary CTA buttons (Continue, Finish setup, Approve), active/focused nav item, focus rings, the pairing display-code text itself |
| Destructive | `#EF4444` (red-500) | Reserved exclusively for: Revoke device, Deny pairing request, Regenerate recovery codes (invalidates old ones) — never for generic warnings |
| Success | `#4ADE80` (green-400) | Readiness-summary "OK" rows only (DB migrated, volumes persistent, HTTPS valid) — never a generic "all good" badge on unrelated UI |
| Warning | `#FBBF24` (amber-400) | Readiness-summary non-blocking warnings only (e.g., plain-HTTP/self-signed via `PLAYSTEAD_PROXY=external`, anonymous-volume detection) — never blocks wizard completion (D-04) |
| Text primary | `#F1F5F9` (slate-100) | Body copy, headings on dark surfaces |
| Text muted | `#94A3B8` (slate-400) | Helper text, timestamps, last-seen, claimed-but-unverified fields (platform/app version/IP on approval card) |
| Border/divider | `#334155` (slate-700) | Card borders, table row dividers |

Accent reserved for: primary call-to-action buttons, active navigation state, keyboard focus rings, and the pairing display code text. Accent is never used for informational badges, links in body text, or decorative elements — this keeps the 10% genuinely scarce so the eye is drawn to the one action that matters per screen (e.g., the Approve button, never also a matching-colored "beta" badge nearby).

| Primary CTA — setup wizard intermediate steps | "Continue" |

| Empty state heading — pairing approval queue | "No pairing requests" |
| Empty state body — pairing approval queue | "When a Mac requests to pair, its code will appear here for you to approve. Nothing to do right now." |
| Empty state heading — device list (before any Mac has ever paired) | "No devices paired yet" |
| Empty state body — device list | "Pair a Mac from its Settings screen, then approve the request here." |
| Error state — login (bad credentials) | "That password didn't match. Try again, or use the recovery option below if you're locked out." |
| Error state — expired pairing request | "This request expired before it was approved. Ask the Mac to request pairing again." |
| Error state — capability incompatible (surfaced via LiveView flash, keyed off `code` per D-22) | "{who_must_act} needs to update before this device can connect. {detail}" — copy is derived from the structured `remedy` object, never hardcoded per-endpoint strings |
| Error state — generic server error (RFC 9457 fallback) | "Something went wrong on the server. Your data is safe — nothing was changed. Correlation ID: {correlation_id}" |
| Destructive confirmation — revoke device | "Revoke [device name]? This device will lose access immediately. Its downloaded games and saves stay on it and remain playable offline — only syncing with this server stops." (mirrors D-11 microcopy exactly) |
| Destructive confirmation — deny pairing request | "Deny this pairing request? The Mac will need to request pairing again." |
| Destructive confirmation — regenerate recovery codes | "Regenerate recovery codes? Your existing codes will stop working immediately. Save the new codes somewhere safe — they are shown only once." |
| Sudo-mode re-authentication prompt | "Confirm it's you — enter your password to continue." (shown for device revocation, credential change, recovery-code regeneration per D-06) |
| Backup nudge (wizard final step, one line, never implies a backup exists) | "Your library lives in this server's storage. Set up a backup destination soon — a copy on the same disk is not a backup." |
| Readiness summary — pairing evidence card micro-copy | "Only approve if this code matches the one on your Mac's screen." (verbatim, D-09) |
| Revoked-device redirect copy (Mac-side text, console must match tone) | "This Mac's access was removed from the server. Your downloaded games and saves are still here and playable offline. To reconnect, pair again from Settings." (verbatim, CONTEXT.md Specific Ideas) |
