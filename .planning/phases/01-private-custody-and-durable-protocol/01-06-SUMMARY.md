# Phase 01 Plan 06: Capability Negotiation and Idempotency-Key Layer Summary

**Range-check capability negotiation (`POST /api/v1/hello`, structured remedy) plus a transactional Idempotency-Key receipt layer on `PATCH/POST /api/v1/devices/me*`, backstopped by client-generated UUIDv7 natural keys so a post-receipt-expiry outbox replay still converges to one effect.**

## Accomplishments

- `Playstead.Protocol.Negotiation.verdict/2` compares client-declared ranges against the server's `Capabilities.supported_client_ranges/0` by range overlap (never version equality); `protocol` is the only required namespace, so a mismatch on any of the other five degrades to `compatible_with_limits` rather than a hard failure — a table-driven test covers client-newer, server-newer, exact-overlap, no-overlap-in-both-directions, optional-unsupported, and unknown-key cases
- `Playstead.Protocol.Remedy.build/3` derives `who_must_act`/`side_too_old`/`minimum_required`/`detail_url` from the same two ranges both sides already have, so the "each side blames the other" deadlock cannot occur by construction
- `POST /api/v1/hello` stores/refreshes a per-device `capability_declarations` row via an `on_conflict` upsert unique on `device_id` — a repeat or concurrent hello converges to exactly one row — and an `incompatible` verdict never blocks `GET /api/v1/capabilities` or the device's own `/me` record
- `Playstead.Idempotency.execute/4` is the single write path for a receipt: one `Ecto.Multi` inserts the in-flight marker, runs the effect, and completes the receipt with the serialized response, so there is no window for a receipt and its effect to land in separate transactions
- `PlaysteadWeb.Plugs.Idempotency` requires `Idempotency-Key` on mutating `/api/v1` routes, replays a matching complete receipt verbatim without touching the controller, 422s a fingerprint mismatch, and 409s + `Retry-After`s a request racing an in-flight original; receipts are scoped per `{device_id, idempotency_key}` and pruned daily past ~90 days
- New `PATCH /api/v1/devices/me` (device self-report refresh) and the existing `POST /api/v1/devices/me/rotate` are both wired through the idempotency pipeline — the phase's two canonical mutating endpoints
- `Playstead.CommandId.valid_v7?/1`/`cast/1` validate client-supplied UUIDv7 strings; the server never mints its own (RESEARCH.md's Open Question 1, confirmed — no UUID dependency added). `device_credentials.command_id` is a unique-constrained natural key that `rotate_credential/2` upserts on, so a rotation command replayed after its idempotency receipt has expired still converges to one credential row instead of minting a second secret
- `Playstead.Pairing.RotationAuditWorker` gives credential rotation the audit-log entry every other lifecycle event already had (a gap this plan found and closed — Rule 2), enqueued with Oban's `unique` option keyed on `command_id` so a replayed enqueue converges to one job

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `on_conflict: :nothing` cannot detect convergence for binary_id primary keys**
- **Found during:** Task 3, writing the command_id convergence test
- **Issue:** Ecto generates `binary_id` (UUID) primary keys client-side before the `INSERT` runs, so a struct returned from `Repo.insert(on_conflict: :nothing, returning: true)` has its `id` populated identically whether the row was actually inserted or the insert was a genuine no-op conflict. Worse, Postgres's `DO NOTHING` returns zero rows via `RETURNING` on a real conflict, so Ecto has no DB-returned data to fall back on either — the initial implementation's `is_nil(attempted.id)` check never fired, and a naive `token_hash == hash` check was equally useless since the returned struct on conflict still carries the *attempted* (never-persisted) values, not the DB's actual row.
- **Fix:** Switched to `on_conflict: {:replace, [:updated_at]}`, which forces Postgres to always return the row that now genuinely exists (the pre-existing row on conflict, the fresh row on insert) via `RETURNING`, making `credential.token_hash == hash` a reliable signal.
- **Files modified:** playstead-server/lib/playstead/pairing.ex
- **Verification:** `test/playstead/command_id_test.exs#replaying the same command_id after deleting the idempotency receipt still converges to one effect row` passes; caught by an actual second-call reproduction, not by reasoning alone
- **Committed in:** e43467f (Task 3 commit)

**2. [Rule 1 - Bug] Pre-existing rotate test broke once Idempotency-Key became required**
- **Found during:** Task 2, running the full suite after wiring `POST /api/v1/devices/me/rotate` through the idempotency pipeline
- **Issue:** `test/playstead_web/controllers/api/v1/devices_controller_test.exs`'s existing rotate test predates this plan and sent no `Idempotency-Key` header, now correctly rejected with `idempotency_key_missing`.
- **Fix:** Added a generated `Idempotency-Key` header to that test's request.
- **Files modified:** playstead-server/test/playstead_web/controllers/api/v1/devices_controller_test.exs

**3. [Rule 2 - Missing Critical] Credential rotation had no audit-log entry**

- **Fix:** Added `Playstead.Pairing.RotationAuditWorker`, an Oban job (unique per `command_id`) that records `credential_rotated`. Only fires when a `command_id` is supplied (task 3's code path), since that's also this plan's designated Oban-uniqueness demonstration site.
