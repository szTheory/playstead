<objective>
Give a client that has been disconnected — for an hour or for a month — a way to arrive at exactly the state a fresh client would have, over ordinary HTTPS reads, with no persistent socket and no possibility of a silently-skipped change.

Purpose: PROT-05 is the recovery spine every Playstead client's sync engine implements. It is the last of the roadmap's three contract-gate proofs, and the one whose failure mode is silent: a lost update looks exactly like nothing happening.

Output: the HMAC-signed opaque cursor, the compacted tombstoned change journal, the `/changes` feed with 410 semantics, the transactional snapshot endpoint, and the missed-every-notification convergence contract test.
</objective>

<scope_note>
## Entity kinds and the phase boundary

ROADMAP success criterion 4 names catalogue, job, transfer, and save state as what a reconnecting client must reconstruct. Those four domains are created in Phases 2, 3, and 4 — no catalogue row, transfer row, or save revision exists yet, which is a dependency constraint, not a scope reduction.

This plan therefore delivers the whole PROT-05 contract now and registers all six entity kinds — `device`, `pairing`, `catalogue`, `job`, `transfer`, `save` — in the published vocabulary in this phase, so the wire contract is frozen here and later phases attach producers without a protocol change. The kinds that have data in Phase 1 (`device`, `pairing`) are wired as real producers and carry the convergence proof. Each later phase's plans are responsible for appending journal entries for the kinds they create; that obligation is recorded in this plan's summary so it is not lost.
</scope_note>

Create `change_journal_entries`: `seq` (a monotonic, gapless-on-commit sequence — use a database sequence or an identity column that is assigned inside the writing transaction so ordering matches commit order), `user_id` foreign key for per-owner partitioning, `entity_kind`, `entity_id`, `operation` (upsert or tombstone), `payload` (a map, empty for tombstones), and `inserted_at`. Index on `{user_id, seq}`.

Commit-order fencing is the subtle correctness property: a reader must never observe sequence N+1 while sequence N is still uncommitted, or a client resuming from N+1 permanently loses N. Implement the read side so it only returns entries up to the highest contiguously-visible sequence — do not naively `SELECT WHERE seq > cursor ORDER BY seq`, which is exactly the cursor-gap lost update D-21 rules out. Document the mechanism chosen in the summary.

`Playstead.Sync.EntityKind.all/0` registers exactly six kinds: `device`, `pairing`, `catalogue`, `job`, `transfer`, `save`. Registering all six now freezes the vocabulary in the published contract even though only the first two have producers in this phase; the schema validates against this list so a later phase cannot silently introduce an unregistered kind.

`Playstead.Sync.Cursor` builds the opaque token: encode the sequence as a fixed-width big-endian integer, append an HMAC-SHA256 of that value computed with a secret derived from the application's signing secret, and URL-safe base64-encode the pair without padding. `decode/1` verifies the HMAC in constant time before trusting the sequence. A cursor encodes position only — never identity and never authorization, so tampering with it can at most produce an invalid or expired cursor, never access to another owner's feed. Reject invalid cursors with `cursor_invalid`.

Do not adopt a generic Ecto cursor-pagination library. RESEARCH.md Pitfall 4 is explicit: those libraries solve stable list pagination, not change-feed convergence, and have no concept of a stale-versus-exhausted cursor — which would make the 410 semantics in task 2 unwritable. Take the opaque-signed-cursor pattern, implement the journal semantics directly.

Wire the first producers: every mutation in `Playstead.Pairing` that changes a device or pairing request appends a journal entry inside the same transaction as the mutation, and revocation appends a tombstone. Appending in the effect's transaction is the same discipline the idempotency receipt follows and for the same reason — a journal entry written after commit can be lost in the gap.

The load-bearing property is transactional consistency: run the page query and the as-of sequence read inside one `Repo.transaction` with an isolation level that gives a consistent snapshot, so the returned cursor is exactly the position the returned data reflects. ## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Paired device → `/changes` and `/snapshot` | Credential-bearing, but the cursor is a client-supplied opaque token |
| Cursor payload → journal query | Attacker-controlled bytes reach a position decision |
| Journal partition → per-owner reads | The isolation boundary between owners' change feeds |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-44 | Tampering | Cursor forgery to read another owner's feed | high | mitigate | The cursor is HMAC-SHA256 signed and verified in constant time before use, and encodes position only — authorization and per-owner partitioning are enforced independently of cursor contents, so even a valid cursor cannot cross owners (task 1) |
| T-01-45 | Information Disclosure | Cross-owner journal leakage | high | mitigate | `read_after/3` filters by the authenticated scope's `user_id` on every query, tested directly with a foreign owner's valid cursor (task 1) |
| T-01-46 | Tampering | Cursor-gap lost update | high | mitigate | Commit-order fencing on the read path plus a snapshot whose as-of cursor is read inside the same transaction as its pages; offset pagination is absent from the sync path entirely (tasks 1 and 3) |
| T-01-47 | Information Disclosure | Tombstone payload leakage | medium | mitigate | Tombstone entries carry the entity kind and identifier only, with an empty payload, so a deletion reveals nothing about the deleted content (task 1) |
| T-01-48 | Denial of Service | Unbounded journal growth | medium | mitigate | Horizon-bounded compaction as a scheduled job, with the boundary sequence preserved so the 410 decision stays exact (task 2) |
| T-01-49 | Denial of Service | Expensive snapshot reads | medium | accept | Phase 1 snapshots cover only device and pairing rows on a personal single-owner server, so the read is small; snapshot cost is revisited when the catalogue producer lands in Phase 2 |
