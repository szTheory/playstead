<objective>
Stand up the Playstead server as a deployable, HTTPS-reachable Phoenix application with the versioned `/api/v1` boundary and its error spine in place. This is the tracer slice for the whole phase: one path runs from `docker compose up -d` through Caddy TLS, into the Phoenix app, into Postgres, and back out as a versioned API response — plus the LiveView console route that later plans fill in.

Purpose: every later plan in this phase (setup wizard, pairing, capability negotiation, idempotency, cursor sync) attaches to this spine. Proving the whole stack end-to-end on the first commit means an architectural dead-end surfaces now, not after ten committed layers.

Output: a running `playstead-server/` Phoenix 1.8 application, a one-file Docker Compose deployment with Caddy TLS and named persistent volumes, `/healthz`, `GET /api/v1/capabilities`, the RFC 9457 problem+json error layer, boot-time migrations with secret and version gates, and the deployment/upgrade documentation.

Hand-build the RFC 9457 layer. RESEARCH.md Pitfall 2 confirms there is no shipped Plug/Phoenix library for this — do not search for or add one.

`PlaysteadWeb.ErrorCodes` owns the stable machine-code registry as data: a single function returning the code-to-{status, title} mapping. Seed it with the codes named in D-22 and D-11 that this phase will use across all plans — `capability_incompatible`, `idempotency_key_conflict`, `idempotency_key_mismatch`, `cursor_expired`, `device_revoked`, `pairing_request_expired`, `pairing_request_already_redeemed`, `unauthorized`, `not_found`, `rate_limited`, `internal_error`. Titles are English strings for humans; the code is the contract. Clients key microcopy off `code` only.

`PlaysteadWeb.Problem.send_problem/5` takes conn, status, code, detail, and an extras map; it generates a fresh random `correlation_id` with `:crypto.strong_rand_bytes/1` base32- or base64url-encoded, sets `content-type: application/problem+json`, sets the `x-correlation-id` response header to the same value, and sends a body containing `type` (`about:blank` unless a specific type URI is registered), `title` from the registry, `status`, `detail`, `code`, `correlation_id`, and any extras such as the structured `remedy` object. The correlation ID generator must be random per response — never a hash of the request path, params, filenames, or any credential.

`PlaysteadWeb.Api.V1.FallbackController` handles the expected application error tuples (`{:error, :not_found}`, `{:error, :unauthorized}`, `{:error, %Ecto.Changeset{}}`, `{:error, {code, detail}}`) by delegating to `Problem.send_problem/5`.

`PlaysteadWeb.Plugs.ApiProblemHandler` closes the framework-level gap. Use `Plug.ErrorHandler` so an unhandled exception raised anywhere beneath the `/api` scope is caught and rendered as problem+json, and configure the endpoint's `render_errors` for the API scope to the same formatter, so a 404 from an unmatched `/api` route is also problem+json. Both paths matter: RESEARCH.md warns that a fallback-controller-only implementation passes its own tests while still leaking Phoenix's HTML error page in production.

Add a `:dev`- and `:test`-only route under `/api/v1` that deliberately raises, so the forced-500 contract test has a real target. Gate it so it is not compiled into a production release.

Add `PlaysteadWeb.ApiCase` in test support: a JSON-oriented `ConnCase` variant that sets `accept: application/json`, carries no session cookie, and provides an assertion helper that asserts a response is a well-formed problem+json document with an expected code. This is the Wave 0 test-infrastructure item VALIDATION.md lists.
