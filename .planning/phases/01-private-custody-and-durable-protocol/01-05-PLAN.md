<objective>
Give the owner the trusted surface of the pairing ceremony: a queue where a request is approved only after a human compares one code on two screens, and a device list where any Mac can be revoked without touching the others.

Purpose: D-07 inverts RFC 8628's verification onto the trusted surface, which means this console screen *is* the security property. Its visual hierarchy — observed facts loud, client claims muted — is not styling; it is the mitigation.

Output: the Devices page with the pairing approval queue and evidence card, the device list with rename, sudo-gated revoke and rotation, revoked tombstones, and the root-CA fingerprint display for client pinning.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client-claimed request fields → console rendering | Attacker-controlled strings reach the owner's screen |
| Owner console → pairing commands | Authenticated, scope-bound, sudo-gated |
| Caddy CA volume → console fingerprint display | The trust anchor a Mac will pin |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-30 | Spoofing | Approval evidence card | critical | mitigate | Claimed fields render muted, labelled, truncated, and bounded so they can never impersonate observed facts or crowd the display code; the code comparison remains the whole security property (D-09, task 1) |
| T-01-31 | Tampering | Client-side expiry countdown | high | mitigate | The countdown is presentation only; `approve/2` re-derives and re-checks expiry server-side bound to the request ID and code, so a drifted or manipulated client clock cannot approve a stale request (D-12, task 1) |
| T-01-32 | Elevation of Privilege | Device revocation via a hijacked console session | high | mitigate | Revocation and rotation pass through the existing sudo-mode gate, requiring a fresh password even inside an authenticated session (D-06, task 2) |
| T-01-33 | Information Disclosure | Credential exposure in the console | high | mitigate | Only a SHA-256 fingerprint prefix is ever rendered; no template reads or displays a credential value (D-10, task 2) |
| T-01-34 | Tampering | Adversarial claimed device name | medium | mitigate | Names are escaped by HEEx, truncated, length-bounded on rename, and rendered inside a container that cannot overflow into the display-code region (task 1 and task 2) |
| T-01-35 | Spoofing | CA fingerprint substitution | high | mitigate | The fingerprint is computed server-side from the Caddy CA root on its volume, displayed only to the authenticated owner, and presented alongside an honest statement of the active transport state (D-13, task 1) |
| T-01-36 | Repudiation | Console-issued pairing commands | medium | mitigate | Approve, deny, revoke, and rotate all flow through `Playstead.Pairing`, which writes audit entries — the console issues the same commands an API caller would, never a private path (tasks 1 and 2) |
</threat_model>
