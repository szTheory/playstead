## Assumption-Delta Checkpoint (advisory — recorded, non-blocking)

The detector fired on the `pluralization` family, matching "another" in the phase goal's "a client can retry a mutation without creating **another** effect."

- **Noun now primary:** the *command*, not the *request*. Until this phase, an HTTP request and the effect it produces were the same thing; PROT-04 breaks that identity — one command may arrive as many requests, and the effect must be keyed to the command.
- **Decision:** `promote`. The client-generated command identifier becomes a first-class, unique-constrained natural key on every effect this phase and every later phase creates, alongside the per-device `{device_id, idempotency_key}` receipt. The effect's identity is the command ID; the request is merely a delivery attempt.
- **Rationale:** demoting the command ID to a transport-level detail would make receipt expiry (90 days) a correctness cliff — after expiry an outbox replay would have nothing to converge against and would duplicate. Promoting it makes convergence structural rather than time-bounded.
- **Related signal, no change:** D-01's single-owner-to-household `user_id` shape is an `add-alongside` already decided in CONTEXT.md and implemented in plan 01-02; nothing here changes it.
- **Invariant test:** task 3 encodes the generalized intent — an effect replayed after its receipt has been deleted converges to the existing row rather than creating a second one.
</assumption_delta_decision>

Extend `Playstead.Protocol.Capabilities` so the six namespaces it already publishes each carry an explicit supported range and a required-or-optional flag. Use only the vocabulary REQUIREMENTS names — `protocol`, `app`, `cache`, `transfer`, `adapter`, `save`. Do not add keys for unbuilt features; a capability key is a contract declaration, never a runtime feature toggle or a kill switch.

`Playstead.Protocol.Negotiation.verdict/2` takes the client's declaration and the server's envelope and returns one of three results:
- `compatible` when every required namespace's client range overlaps the server's;
- `compatible_with_limits` when the required namespaces overlap but the client declared optional capabilities the server does not support, listing those capabilities by name so the client can degrade knowingly;
- `incompatible` with a remedy when a required namespace has no overlap.

Decide overlap by comparing ranges, never by comparing versions for equality. RESEARCH.md names version-lockstep as the specific anti-pattern: a Mac that auto-updates while its server stays pinned for months must keep working while the ranges still meet.

Both sides run this same range comparison over the same exchanged data, which is what makes the mutual-deadlock impossible: the verdict is a function of the two ranges, so the client and the server always agree on which side is older. `Playstead.Protocol.Remedy.build/3` encodes that agreement as `who_must_act` (the user for a client-too-old case, the server admin for a server-too-old case), `side_too_old`, `minimum_required` (the version the older side must reach), and `detail_url`. The remedy rides as an extension member on the RFC 9457 body under the `capability_incompatible` code. Clients key their microcopy off the code and the remedy fields; contract tests assert codes and remedy fields, never English strings.

Ignore unknown keys on both sides. An unrecognized capability in a hello is dropped, not rejected — this is the forward-compatibility property that lets a newer client talk to an older server at all.

Add `POST /api/v1/hello` on the device-authenticated pipeline. On each hello, store or refresh the device's capability declaration in `capability_declarations`, keyed uniquely per device so a repeat hello updates rather than accumulates and two concurrent hellos converge to one row. Pairing already recorded the initial declaration in `claimed_capabilities`; the hello is the per-session refresh.

Critically, an `incompatible` verdict is informational, not a lockout. `GET /api/v1/capabilities` stays unauthenticated and always reachable, and the device's own record and revocation surface stay reachable with its credential. A client that cannot negotiate must still be able to learn why and still be revocable.

Create `idempotency_receipts`: `id`, `device_id` foreign key, `idempotency_key`, `request_fingerprint`, `response_status`, `response_body`, `state` (in-flight or complete), `expires_at`, and timestamps, with a unique index on `{device_id, idempotency_key}`. `Playstead.Idempotency.fingerprint/1` computes a stable hash over the request method, path, and canonicalized body so a genuinely different payload under a reused key is detectable. `fetch/3` looks up by device and key.

`Playstead.Idempotency.execute/4` is the single entry point every mutating handler goes through. It builds one `Ecto.Multi` that inserts the in-flight receipt, runs the effect, and updates the receipt to complete with the serialized response — one transaction, one commit. RESEARCH.md Pitfall 3 names the exact failure this forbids: writing the receipt in an after-commit hook or a separate `Repo.insert` leaves a window in which a retry re-executes. There must be no code path in this module that writes a receipt outside the effect's transaction.

`PlaysteadWeb.Plugs.Idempotency` attaches to the mutating routes of the authenticated `/api/v1` pipeline. It requires the `Idempotency-Key` header and rejects its absence with `idempotency_key_missing`. On a complete receipt whose fingerprint matches, it halts and replays the stored response verbatim — same status, same body — without touching the controller. On a complete receipt whose fingerprint differs, it returns 422 with `idempotency_key_mismatch`. On an in-flight receipt, it returns 409 with `idempotency_key_conflict` and a `Retry-After` header.

Wire the first two mutating endpoints through it: `PATCH /api/v1/devices/me`, where a client updates its self-reported name and app version, and `POST /api/v1/devices/me/rotate` from plan 01-04.
