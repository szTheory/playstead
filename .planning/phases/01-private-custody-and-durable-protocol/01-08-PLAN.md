<objective>
Close the single blocking gap in 01-VERIFICATION.md: `docker compose build` fails at `RUN mix compile` with
`** (File.Error) could not read file "/app/docs/RECOVERY.md": no such file or directory`, because the Dockerfile's
builder stage stages `priv`, `lib`, `assets`, `config/runtime.exs` and `rel` but never the repository's `docs`
directory, while `PlaysteadWeb.RecoveryDocsController` (added in plan 01-03, after plan 01-01 wrote the Dockerfile)
embeds `docs/RECOVERY.md` at compile time. This falsifies Roadmap SC1 / OPER-01 — the phase's foundational
deliverable — even though all 292 tests pass.

**Chosen fix (option (a) from VERIFICATION.md's `missing:` list), with rationale:**
Stage the docs directory in the builder stage. Rejected alternatives, deliberately:
- Option (b), moving RECOVERY.md under `priv/`: the file is first-class self-hoster documentation living beside
  DEPLOY.md and UPGRADE.md, is referenced as `docs/RECOVERY.md` by plan 01-03's SUMMARY and by D-05, and burying
  an operator runbook inside `priv/` to satisfy a build-context omission trades a one-line fix for a permanent
  documentation-layout wart.
- Option (c), reading at runtime: strictly worse here. The final runner stage copies **only** the compiled release,
  so a runtime read would need the file in `priv/` anyway (i.e. option (b) plus a fallback code path), and would
  introduce a failure mode — a 500 or a degraded fallback on the "Locked out?" link — precisely when a self-hoster
  is locked out. The controller's existing comment already states this reasoning; the compile-time embed is the
  right design, it was simply never staged.

The fix is one COPY line, but the plan does three things, because the one-line fix alone would leave the phase
exactly as fragile as it was: the regression slipped through because `mix compile`/`mix test` succeed against a
git checkout (where the working directory contains `docs/`) and no plan after 01-01 re-ran the Docker smoke test.

Purpose: make the documented deployment path work, make its failure mode detectable by `mix test`, and physically
re-run the OPER-01 evidence path that this regression escaped.
Output: a buildable image, a hardened controller, a generic build-context regression guard, a route test, and a
human-run compose smoke + UI-SPEC walkthrough record.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| repository build context → Docker builder image | Files staged by COPY cross into the image that compiles and links the release; anything staged here is readable by every subsequent build step and by anyone who can inspect the builder layer. |
| builder stage → final runner image | Only `/app/_build/prod/rel/playstead` crosses; the raw source tree, including the docs directory, does not reach the runtime image. |
| unauthenticated browser → `GET /docs/recovery` | Public route in the `[:browser]` pipeline serving operator recovery documentation with no session required. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-51 | Denial of Service | Docker builder stage (`RUN mix compile`) | high | mitigate | Stage the docs directory before the compile step (task 1) so the documented deployment path can produce an image at all; add the ExUnit build-context guard (task 2) so the same omission for any future compile-time resource fails `mix test` instead of only failing a Docker build nobody re-ran. |
| T-01-52 | Information Disclosure | build context → builder image (`COPY docs docs`) | medium | mitigate | Only the three self-hoster markdown runbooks (DEPLOY, RECOVERY, UPGRADE) live under the staged directory — no secrets, keys, or `.env` material. The final runner stage copies only the compiled release, so the raw directory never reaches the shipped image; `.dockerignore` continues to exclude `.git` history, test, build, and dependency trees (task 1 verifies the ignore file does not need widening). |
| T-01-53 | Tampering | `/docs/recovery` served content | medium | mitigate | Declaring the markdown as an external resource (task 1) forces recompilation when its contents change, closing the stale-content path in which a self-hoster is served superseded recovery instructions at the exact moment they are locked out; the route test (task 2) compares served bytes to the file's bytes. |
| T-01-54 | Information Disclosure | unauthenticated `GET /docs/recovery` | low | accept | The runbook documents only procedures gated on host shell access (`docker compose exec` on the machine the self-hoster owns) and on single-use, short-lived reset tokens. Publishing the text grants an unauthenticated reader no capability they did not already need root-equivalent host access to use, and gating it behind login would make it unreachable precisely when it is needed. Accepted at ASVS L1; unchanged from plan 01-03's original disposition. |
| T-01-SC | Tampering | npm/pip/cargo/hex installs | n/a | accept | This plan installs no packages. `mix.exs` and `mix.lock` are not in `files_modified` and must not be modified; no new dependency is introduced, so the package-legitimacy gate has nothing to audit. If an executor finds itself reaching for a new dependency, that is a signal the plan has been misread — halt instead. |
</threat_model>
