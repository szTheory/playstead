# Phase 03.5: Code Review Report

**Reviewed:** 2026-09-03T02:22:41Z
**Depth:** standard
**Files Reviewed:** 81
**Status:** issues_found

## Summary

This phase builds a large, carefully layered hosted macOS verification harness: four serial
XCTest plans behind one build, an evidence sanitizer with a Python allowlist validator, and
Keychain/credential isolation gated by `#if UI_TESTING`/`#if DEBUG` compile flags. The core
security boundaries hold up under adversarial reading:

- `KeychainStore`'s search/add scoping (`scopedMatchQuery`/`scopedAddQuery`) is applied
  consistently, and `APIClient.unpairedForUITesting()` / `UITestBootstrap` never construct a
  login-Keychain-backed client for deterministic profiles.
- `PlaysteadApp.swift` confirms the UI-testing bootstrap path, the deterministic-profile
  environment, and the whole `UITesting/` directory are wrapped in `#if UI_TESTING` nested
  inside `#if DEBUG` — a Release build genuinely does not compile any of this code, matching
  the plan 03.5-03 decision and `ReleaseHookAbsenceTests`'s intent.
- `sanitize-evidence.sh` is a real allowlist (not a blocklist): every JSON evidence file has an
  exact permitted-key schema, failed/required-test records are bounded and canonicalized, and
  anything outside the allowlisted file set, size caps, or JSON schema causes the whole sanitize
  step to fail closed (`raise SystemExit`).
- `run-mac-verification.sh`'s hosted-run and layer-result verifiers require exact
  discovered/execution-count/non-skipped/passed for every named canary and reject vacuous or
  duplicate identifiers, so a required test silently not running does fail the gate.
- `SQLiteConnection.swift` uses parameterized `sqlite3_bind_*` throughout; no string-interpolated
  SQL was found in this file.

No BLOCKER-tier issues were found: nothing lets a normal CI/local run reach the developer's
login Keychain, nothing in the sanitizer's structured-evidence path fails open, and no command
injection or SQL injection was found in the reviewed shell/Python/Elixir/Swift code. The findings
below are quality and defense-in-depth gaps: a genuinely orphaned CI artifact, an unpinned
supply chain for third-party GitHub Actions, an unwired evidence validator that can rot silently,
and a couple of latent regex/allowlist gaps in the log-sanitization path that are not reachable
today but would fail open if a future change exercises them.

## Warnings

### WR-01: Compiled Python bytecode committed to the repository, and `__pycache__`/`*.pyc` are not gitignored anywhere

**File:** `playstead-mac/scripts/ci/tests/__pycache__/test_validate_phase_3_uat_evidence.cpython-314.pyc` (tracked in git)
**Issue:** This is a build artifact, not source — it embeds a CPython 3.14 bytecode dump of the
adjacent `.py` test file, including local absolute file paths from whatever machine produced it,
and it will silently go stale relative to the `.py` source it was compiled from (Python does not
re-validate `.pyc` freshness by content, only by mtime/hash heuristics that a fresh git checkout
can defeat). Neither the repo-root `.gitignore` nor `playstead-mac/.gitignore` excludes
`__pycache__/` or `*.pyc`, so every future `pytest`/`python3 -m` invocation against this
directory on a contributor's machine risks re-adding more of these, and nothing currently stops
it.
**Fix:**
```bash
git rm --cached playstead-mac/scripts/ci/tests/__pycache__/test_validate_phase_3_uat_evidence.cpython-314.pyc
```
Add to `playstead-mac/.gitignore`:
```
# Python bytecode cache
__pycache__/
*.pyc
```

### WR-02: Third-party GitHub Actions are pinned to mutable major-version tags, not commit SHAs

**File:** `.github/workflows/ci.yml:44,46,52,57,75,142,158,161`; `.github/workflows/mac-snapshot-refresh.yml:17,27`
**Issue:** `actions/checkout@v4`, `erlef/setup-beam@v1`, `browser-actions/setup-chrome@v1`,
`actions/cache@v4`, `actions/upload-artifact@v4`, `dorny/paths-filter@v3`,
`docker/setup-buildx-action@v3`, and `docker/build-push-action@v6` are all referenced by mutable
tag. A compromised or force-pushed tag on any of these third-party actions (all outside
`actions/*`/`docker/*`'s first-party trust boundary except those two orgs) would execute
arbitrary code inside this workflow — which has `contents: read` and, on `push` to `main`, runs
with the repository's default `GITHUB_TOKEN` and reaches the native Postgres/Phoenix fixture. The
`mac-verification` job in particular runs unconditionally on every push/PR with no path filter
(by design, per the workflow's own comment), so this is the widest-blast-radius job in the
pipeline.
**Fix:** Pin every third-party (non-`actions/*`, non-`docker/*`) action to a specific commit SHA,
e.g.:
```yaml
- uses: erlef/setup-beam@11ba62ab9f4b930b1feffea5b0ef2f9f6e0e0906  # v1.20.4
```
and keep them current via Dependabot/Renovate action-version tracking.

### WR-03: `validate-phase-3-uat-evidence.py` is not invoked from any CI workflow or from `run-mac-verification.sh`

**File:** `playstead-mac/scripts/ci/validate-phase-3-uat-evidence.py` (whole file); confirmed absent from `.github/workflows/ci.yml`, `.github/workflows/mac-snapshot-refresh.yml`, and `run-mac-verification.sh`
**Issue:** This is a genuine fail-closed validator (frontmatter/section/mapping checks with
`ContractError`), but it is reachable only via `.planning/phases/.../tools/complete-task3.sh`, a
one-off planning artifact. Once `.planning/phases/03-mac-offline-play-vertical-slice/03-UAT.md`
or `.planning/ROADMAP.md` drift after this phase closes (e.g. a later phase renumbers checkpoints
or edits the Phase 3.5 success-criterion wording this validator pins verbatim), nothing will
catch it — the validator that exists specifically to prevent that drift never runs again. This
matches the project's own known failure mode ("CI gates rot unnoticed" — gates go unreachable and
silently stop protecting).
**Fix:** Either wire it into `run-mac-verification.sh` (e.g. a `--verify-phase-3-uat-evidence`
mode invoked from a CI step) or explicitly document in the script's header that it is a one-time,
phase-closure-only tool not intended to run in CI, so a future reader does not mistake its
existence for ongoing protection.

### WR-04: `sanitize-evidence.sh`'s log-line redaction regex is a denylist that can fail open for credential formats it does not anticipate

**File:** `playstead-mac/scripts/ci/sanitize-evidence.sh:70-76,197-204`
**Issue:** `sensitive_text` only redacts a line when it matches one of a fixed set of literal
shapes: `authorization\s*[:=]`, `bearer\s+<token>`, `database_url\s*=`, `secret_key_base\s*=`,
`.keychain(-db)?`, `.env`, `credential[-_ ]?handoff`, an `objects`/`partials` path segment, a
64-hex-char content id, or a handful of ROM extensions. A credential rendered in any other common
shape — e.g. `DATABASE_URL: ecto://user:pass@host/db` (colon, not `=`), a stack trace containing
a raw bearer token with no `Bearer` prefix, or a connection string embedded mid-sentence in an
exception message — passes through `sanitize_log` (and the identical post-sanitization re-scan at
lines 251-257, which reuses the same regex and therefore cannot catch what the first pass missed)
untouched. This log path (`evidence/logs/app.log`, `evidence/logs/server.log`) is allowlisted in
the sanitizer but is not currently populated by `run-mac-verification.sh` (grep confirms no
caller writes to `$FOUR_LAYER_EVIDENCE/logs/`), so the gap is latent rather than exploitable
today — but it is exactly the kind of untested code path that fails open the day someone wires a
log capture into it without re-auditing the regex.
**Fix:** Either remove the `logs/app.log`/`logs/server.log` allowlist entries until a producer
exists and is covered by `sanitizer-test.sh` fixtures that exercise realistic Postgres/Phoenix
log lines, or broaden the redaction to a structural check (e.g. redact any line containing `://`
with embedded `user:pass@` credentials, and any `KEY: value`/`KEY=value` pair whose key matches
the sensitive-key vocabulary regardless of separator).

### WR-05: `mac_ci.exs` ships a hardcoded `secret_key_base`, and the loopback-only Postgres cluster uses `--auth=trust`

**File:** `playstead-server/config/mac_ci.exs:33`; `playstead-mac/scripts/ci/run-mac-verification.sh:1386` (`initdb -D "$PGDATA" --auth=trust`)
**Issue:** `secret_key_base: "wave0-native-phoenix-only-not-a-production-secret-key-base-0000000000000000"` is a hardcoded credential-shaped string committed to source control, and while the comment and surrounding isolation (loopback-only, ephemeral, CI-only Postgres cluster torn down every run) make this low-risk in the current design, it is exactly the pattern a naive secret scanner (and this review's own `quick`-depth grep patterns) would flag, and it would become a real problem if this config file were ever reused as a template for a longer-lived or externally-reachable environment. `--auth=trust` for the ephemeral Postgres cluster is consistent with "no real secret to protect" but should not be copy-pasted into a less-isolated context.
**Fix:** No change required for this ephemeral CI-only path, but add an explicit comment at the
top of `mac_ci.exs` (not just inline on the one line) warning that this file must never be reused
as a starting point for a config that binds beyond loopback or persists beyond the CI job, and
consider generating the value at runtime (e.g. `mix phx.gen.secret`-style, or
`:crypto.strong_rand_bytes` like `mac_ci_fixture.ex` already does for its owner password) so the
pattern-matching risk disappears entirely rather than relying on a comment.

## Info

### IN-01: `keychain-prompt-safety-test.sh` asserts app-entry composition via fragile substring splitting rather than a real Swift parser

**File:** `playstead-mac/scripts/ci/tests/keychain-prompt-safety-test.sh:30-40`
**Issue:** The test locates code regions with `app.split("struct PlaysteadApp: App", 1)[1]...`
and similar chained `.split(...)[1]` calls. If `PlaysteadApp.swift` is refactored (e.g. the struct
declaration reformatted across lines, or the marker strings renamed), the script does not
degrade gracefully to a weaker check — it throws an uncaught `IndexError`, which `set -euo
pipefail` correctly turns into a hard failure. That is fail-closed behavior (good), but it means
this specific safety contract is coupled to exact source text rather than to a durable AST-level
property, so a purely cosmetic refactor of `PlaysteadApp.swift` will break this CI gate for
reasons unrelated to the property it's meant to verify.
**Fix:** Low priority given the fail-closed behavior; if this file is touched again, consider
replacing the string-split heuristic with a small `SourceKitten`/regex-based structural check
that survives reformatting, e.g. matching `#if UI_TESTING` region boundaries with a multiline
regex instead of literal struct-name substrings.

### IN-02: `sanitize-evidence.sh`'s `required_tests` schema allows an empty list at the sanitizer layer

**File:** `playstead-mac/scripts/ci/sanitize-evidence.sh:181-183`
**Issue:** `validate_test_evidence` requires `required_tests` to be a list (`isinstance(required, list)`) but does not require it to be non-empty. In isolation this would let a `{name}-tests.json` with `"required_tests": []` pass sanitizer validation — i.e. the sanitizer alone does not prevent a vacuous "zero required tests" evidence file from being staged as failure evidence. In practice this is not exploitable today because `verify_layer_result` in `run-mac-verification.sh` (line 590: `[ -s "$required_file" ] || die "layer $layer requires at least one --required-test"`) and `verify_complete_hosted_run`'s Python (line 484-486: `if not isinstance(required, list) or not required: raise SystemExit(...)`) both independently enforce non-emptiness upstream/downstream of the sanitizer. This is defense-in-depth only, but the sanitizer is the one component whose job description is explicitly "prevent vacuous evidence," and it is currently the one layer of the three that doesn't check this property.
**Fix:** Add `if not required: raise SystemExit(...)` to `validate_test_evidence` alongside the existing list-type check, so the sanitizer's own contract matches its stated purpose independent of what the other two verifiers currently guarantee.

### IN-03: `DeterministicProfileFixture.queueSequence` is a mutable `static var` with no synchronization

**File:** `playstead-mac/Playstead/UITesting/DeterministicProfile.swift:106,356-359`
**Issue:** `nextQueueID()` increments and reads a `private static var queueSequence` with no lock
or actor isolation. Every call site in the reviewed files runs on the main actor (fixture
construction happens synchronously during app/session bootstrap), so this is not currently a
data race, but nothing in the type system enforces that — a future caller from a background
queue (e.g. a parallelized XCTest target) would silently corrupt or duplicate generated queue IDs
with no compiler warning, since the property is not marked `@MainActor` or backed by an atomic
primitive.
**Fix:** Mark the property and `nextQueueID()` `@MainActor` explicitly (matching the rest of the
UI-testing surface, which is already main-actor-affine), or replace the counter with
`OSAllocatedUnfairLock`/`ManagedAtomic<Int>` if cross-actor use is ever intended.
