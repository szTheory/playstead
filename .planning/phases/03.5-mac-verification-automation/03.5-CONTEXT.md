# Phase 3.5: Mac Verification Automation - Context

**Gathered:** 2026-08-31
**Status:** Ready for planning

<domain>
## Phase Boundary

Automate the five objective Phase 3 Mac verification gaps that currently require an interactive app session: the real app rendering a server snapshot before any game-byte download; the locked library/UI contract; Downloads, Quota, Reclaim, and Storage interaction; curation shelves plus settled drag reorder; and keyboard/live-accessibility-tree behavior. The recurring gate runs on a pinned GitHub-hosted macOS/Xcode environment on every push and pull request, produces reviewable failure evidence, and re-records only genuinely proven Phase 3 UAT claims as automated.

This phase may fix concrete reachability, focus, keyboard-operation, and testability defects exposed by the new harness. It does not add new product capabilities. Physical controller behavior, a real emulator plus real game bytes, Developer ID signing/notarization, and experiential VoiceOver quality remain unproven. Phase 3 remains `partial`; its deliberate availability-filter scope decision also remains blocked.

</domain>

<decisions>
## Implementation Decisions

The owner requested and approved a single recommendation set produced through separate CI/SRE, macOS/Xcode, SwiftUI/rendering, Phoenix/pairing, security, accessibility, design-system, product, OSS-maintainer, and adversarial research passes.

### CI Test Topology

- **D-01:** Add one unfiltered, required GitHub Actions macOS job on every push and pull request. Pin a numbered `macos-*` image and an explicit installed Xcode version; assert `sw_vers`, runner architecture, and `xcodebuild -version` before testing. Missing/drifted toolchains fail loudly rather than silently selecting a new environment.
- **D-02:** Build the Mac app once with `build-for-testing`, then run independent `test-without-building` layers for: (1) all existing `PlaysteadTests`, (2) deterministic render/snapshot tests, (3) fixture-driven XCUITest interaction plus live accessibility, and (4) one focused real-server pairing/snapshot spine. Rendering and UI layers run serially. Aggregate exit codes so later evidence still runs after an earlier layer fails; do not add automatic retries.
- **D-03:** Every UAT-mapped test must be named explicitly and proven discovered, executed, non-skipped, and passed. Use expectation-based waits, exact identifiers and postconditions, and nonempty state guards; fixed sleeps, percentage-only screenshot checks, and "test target exited zero" without test-discovery proof are prohibited.
- **D-04:** Standard GitHub-hosted macOS runners cannot run the existing Docker Compose stack. Preserve the existing Linux `compose-smoke` job as the deployment-topology proof, and start PostgreSQL plus the real Phoenix application natively beside XCUITest in the macOS job for the client/server behavior proof. Clarify Phase 3.5 success criterion 4 to state this split explicitly. Do not require a paid Intel larger runner, secret-dependent cross-job tunnel, or externally exposed transient service. — **Reversibility:** costly — switching to paid/self-hosted Compose-capable Mac infrastructure changes the public CI administration, trust, cost, and maintenance model.
- **D-05:** Upload failure-only `.xcresult` bundles, screenshots, snapshot reference/actual/diff images, environment fingerprints, redacted accessibility-tree dumps, focus traces, and sanitized app/server logs with short retention. Do not cache DerivedData across runs; a fresh VM builds once. Only lockfile-backed dependency downloads may be cached later.

### Pairing and Deterministic Test State

- **D-06:** The focused live proof uses production setup/import/pairing domain functions and real HTTP endpoints. Create the owner through the real setup context, seed one deterministic synthetic non-ROM catalogue sentinel through custody/import contexts rather than raw SQL, create and redeem the pairing request through the public API, and automate trusted-owner approval through the production pairing context. Approval must assert the exact request ID, returned display code, unique claimed device label, and the sole expected pending request. Existing browser tests remain the proof of the human Devices approval UI.
- **D-07:** Give every test a unique application-support root and disposable Keychain. A compile-gated UI-test bootstrap reads a redeemed credential from a mode-`0600` temporary file, deletes the file, stores the credential through the real `KeychainStore`, and then requires the app to authenticate through the normal `KeychainStore.loadCredential` path. Credential overrides, launch-argument secrets, shared login-Keychain mutation, `security -A`, and silent fallback after Keychain failure are prohibited.
- **D-08:** Add a release guard proving the credential bootstrap, deterministic profile loader, their environment keys, and their symbols are absent when the UI-testing compilation condition is disabled. Test-only behavior must fail closed and must not create a production pairing bypass. — **Reversibility:** costly — a leaked test hook would be a release-security defect and require removing every call site plus auditing shipped binaries.
- **D-09:** Deterministic profiles are a finite compile-gated enum covering only the required states: empty library, populated library/curation/reorder, paused/active download queue, quota block/reclaim, and storage. Profiles seed via `LocalStore`, curation, queue, pin, quota, and CAS APIs with fixed synthetic IDs, bytes, digests, positions, and timestamps. Arbitrary JSON execution, arbitrary SQL, copied production databases, copyrighted ROMs, and proprietary BIOS data are prohibited.
- **D-10:** The live snapshot proof is non-vacuous only when it asserts the sentinel's exact title and asset-set ID in the real app, at least one rendered library row, a nonempty stored cursor, sanitized server evidence of a successful `/api/v1/snapshot`, zero `/api/v1/blobs/` requests, and empty `objects/` and `partials/` directories. Clear the local mirror and relaunch without the handoff file after adding a second server sentinel; the second sentinel must appear, proving the credential survived in Keychain and the first SQLite mirror did not fake success.
- **D-11:** Serialize the live Keychain/server spine and clean up through a fail-safe trap. Never attach credentials, Keychain dumps, mode-`0600` handoff files, `.env`, databases, raw pairing responses, ROM filenames/hashes, or unredacted logs to CI evidence.

### Rendering and Snapshot Contract

- **D-12:** Use an exactly pinned, test-target-only Point-Free `SnapshotTesting` dependency behind one project-owned `PlaysteadSnapshot` wrapper. Validate the selected version on the pinned runner, including an intentional mismatch that must produce an ordinary failed assertion plus reviewable artifacts. Do not make `ViewInspector` the primary harness and do not build a project-owned PNG decoder/comparator unless the chosen dependency fails the validation spike.
- **D-13:** Pixel snapshots prove only genuinely visual claims: the rendered 280×158 card, two-line title behavior, three-zone anatomy, all seven status glyph/shape/color treatments, absence of a cover-art surface, representative populated and empty library/curation states, and Downloads/Quota/Reclaim/Storage presentation. Prefer focused components/contact sheets plus a small number of representative shells over giant whole-window snapshots.
- **D-14:** Exact semantic XCTest assertions prove the complete sidebar order, registry-ordered nonempty systems and conditional Unidentified-last rule, equality with the complete seven-status set, every priority combination, exactly one selected status slot, locked labels/copy, empty-shelf hide/show behavior, 280×158 point constants, disjoint system/status token vocabularies, and a title-independent presentation seam. Pixel similarity never substitutes for these domain assertions.
- **D-15:** Every fixture asserts its exact nonzero item count and expected state set. Every render asserts exact pixel dimensions plus a nonempty/nonuniform content bounding box. Comparator self-tests must prove a meaningful visual mutation fails and calibrated antialiasing noise passes. Tolerances may not be loosened merely to make CI green.
- **D-16:** Render with fixed synthetic data, clock, UTC, `en_US_POSIX`, active state, animations disabled, standard Dynamic Type, explicit light/dark appearance, 2× scale, and SDR 8-bit sRGB on the asserted runner/Xcode/architecture fingerprint. Add targeted Large-text and long-Unicode/title cases. Do not baseline ambient system appearance, every locale, or every scale before those become supported contracts.
- **D-17:** CI always runs with snapshot recording disabled and fails on missing references. Baseline refresh is a manual workflow on the same pinned environment that emits candidate artifacts only. A maintainer reviews named side-by-side diffs and commits intentional baselines with the corresponding source/test change; the workflow never commits, auto-accepts, or mass-records snapshots.

### Keyboard, Live Accessibility, and Reorder Proof

- **D-18:** Add stable namespaced accessibility identifiers to every surface root and interactive control. Identifiers never depend on labels, game titles, filenames, paths, hashes, credentials, or coordinates. Maintain an independently authored inventory covering the library/sidebar, every curation shelf, collections/detail, queue, search/filter/list, Downloads, Quota, Storage, Reclaim, readiness, adapter, BIOS, and controller-settings surfaces. A meta-test fails when a documented surface has no production route.
- **D-19:** On the pinned runner, enable and verify macOS full-keyboard navigation. For each settled state, XCUITest asserts a nonempty, unique expected-ID sequence; exactly one expected element has focus after each forward and reverse keypress; focus order and wrap behavior are exact; labels, roles, values, selected states, and frames are valid; and activating the control produces the expected state change. Expected order must be authored independently from the queried tree.
- **D-20:** Run the public live accessibility audit for all supported categories after every surface settles. An exclusion is allowed only for an exact audit type, exact element identifier, pinned OS/Xcode fingerprint, and documented rationale; blanket handlers are prohibited. Toolbar sheets must be opened by keyboard, contain focus, close by Escape or a focused Done/Cancel control, and restore focus to the opener.
- **D-21:** Keep one real XCUITest element-to-element drag using three distinctly identified collection/queue rows. Assert exact initial order, exact final order, durable order after relaunch, and exactly one resulting mutation/outbox effect. Separately add visible Move Up/Move Down controls or equivalent ordinary keyboard commands with boundary-disabled states and focus retained on the moved row; `.onMove` alone does not meet the locked keyboard-parity contract.
- **D-22:** The harness is expected to expose and the phase must repair current Phase 3 reachability defects: several documented search/filter/card components have no `LibraryShellView` production route; no shared production focus-ring implementation backs the documented focus contract; and the existing manifest audit derives expected and actual order from the same arrays. These are defects in already-scoped Phase 3 behavior, not new capabilities.
- **D-23:** Split Phase 3 UAT checkpoint 10 rather than claiming its broad wording passed. The automated portion covers keyboard reachability/operation and machine-checkable live accessibility-tree labels, roles, state, hierarchy, focus, and audits. Physical-controller d-pad/shoulder behavior remains blocked, while VoiceOver pronunciation, rotor behavior, sentence quality, and comprehension remain explicitly unclaimed. Checkpoints 8 and 9 remain physical-device blocked, and Phase 3 remains `partial`.

### UAT Evidence and Scope Integrity

- **D-24:** Phase 3.5 may re-record checkpoints 2, 3, 5, and 6 as `source: automated` only after their named covering tests pass with the guards above. Checkpoint 10 is split and only its keyboard/live-tree portion becomes automated. Every UAT entry names the exact test and evidence boundary; no evidence is inferred from a neighboring test.
- **D-25:** Checkpoint 4 remains blocked by the deliberate 03-05 availability-filter scope decision. Checkpoint 7 remains blocked on a real emulator plus real game bytes; checkpoints 8 and 9 remain blocked on physical hardware; checkpoints 14 and 15 remain blocked on Developer ID membership/signing/notarization. Phase 3 must not be marked complete merely because it has no pending checkpoints.

### the agent's Discretion

- Exact Swift file/test helper names, Xcode test-plan grouping, fixture enum case names, CI shell-helper boundaries, timeout values, artifact retention duration, and the selected numbered macOS/Xcode pair, provided research validates current availability and all decisions above remain true.
- Exact snapshot tolerance after mutation/noise calibration; it must be recorded centrally in `PlaysteadSnapshot` and never tuned per failing image without a written reason.
- Whether the native macOS server spine uses a dedicated Mix environment or existing test/dev configuration, provided it executes real application/domain/API paths and does not expose a test-only network bypass.

## Existing Code Insights

### Reusable Assets

- `AppEnvironment` already accepts injectable paths, API client, reachability, and download session. Phase 3.5 can extend this composition seam without replacing production services.
- `AppPaths`, `LocalStore`, `CatalogueStore`, `CurationStore`, `DownloadQueue`, `PinStore`, `QuotaManager`, and `CASManager` provide production APIs for finite deterministic profiles.
- `APIClient`, `KeychainStore`, `SyncEngine`, and the Phase 1 pairing contexts provide the real pairing-to-snapshot spine.
- Existing pure status, navigation, copy, and geometry functions remain useful semantic assertions alongside rendered snapshots.
- The existing Linux `compose-smoke` job already proves the documented Docker deployment and must stay separate from the Mac behavior job.

### Established Patterns

- Tests turn UAT criteria into objective named checks and carry non-vacuity guards; Phase 3.5 follows the same pattern as the browser coherence/keyboard tests.
- `SUMMARY.md` coverage blocks are the source for classifying automated versus human-needed evidence. New tests must update the Phase 3 UAT records honestly rather than overriding the classification by assertion.
- Swift production dependencies are composed once in `AppEnvironment`; deterministic testing uses injection/isolated roots rather than duplicated fake application architectures.
- Security-sensitive evidence is privacy-safe: no ROM names, hashes, paths, credentials, save bytes, or raw authorization artifacts in default logs or attachments.

### Integration Points

- `.github/workflows/ci.yml` gains the required macOS job and failure-artifact publishing.
- `Playstead.xcodeproj` gains a shared scheme/test plan, UI-test target, and exactly pinned test-only snapshot dependency.
- `PlaysteadApp`/`AppEnvironment` gain compile-gated test bootstrap/profile composition while Release builds retain only production initialization.
- SwiftUI surfaces gain stable identifiers, production routes, focus behavior, keyboard reorder alternatives, and live-tree-compatible accessibility structure.
- Phase 3 UAT entries 2, 3, 5, 6, and the split machine-checkable portion of 10 gain exact named automated evidence after the tests pass.

</code_context>

<specifics>
## Specific Ideas

- Name the live synthetic catalogue fixture something unmistakable such as `CI Snapshot Sentinel`; use fixed public synthetic bytes that are neither a ROM nor proprietary BIOS material.
- The macOS CI job should print its complete environment fingerprint before building so snapshot changes are attributable to either source or environment migration.
- Snapshot failure artifacts should be reference/actual/diff triplets; accessibility failures should include a redacted tree dump and ordered focus trace.
- Keep a deliberate snapshot-mutation test and an independently-authored focus-order test so the two most likely vacuous-harness failures cannot silently return.

</specifics>
