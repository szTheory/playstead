<objective>
Ship the Mac client's pairing ceremony, so a human can pair a Mac.

Purpose: the server side has been complete since Phase 1 -- request, approve, poll, redeem, plus the devices console -- and the client calls none of it. `APIClient.swift:57` says so outright ("this tracer plan does not yet ship the pairing ceremony"). `LibraryShellView.swift:474` tells the user to "Pair with your Playstead server", naming an action that exists nowhere in the app. 03.5-08 proved the ceremony only by driving it from `live-server.sh` and handing a credential to a test build; the human path was never built. Discovered 2026-09-08 when the owner tried to run CP7-SAVE-C and had no way to pair, and worked around for one Mac only by driving the production endpoints by hand and writing the credential into the login Keychain.

Consequence today: every human checkpoint requiring a paired Mac is unperformable, and `PROT-01` -- "an authenticated owner can approve a Mac device-pairing request **and the Mac client stores the resulting scoped credential in Keychain**" -- is marked complete in REQUIREMENTS.md while its second clause has no user-reachable implementation. This plan is what makes that requirement true rather than merely claimed.

Output: a pairing surface reachable from the empty state that already advertises it, a coordinator that owns the ceremony and can be tested without SwiftUI, trust-on-first-use certificate capture into the file `APIClient` already watches for, and a live-server-layer proof that the whole ceremony completes against the real server.
</objective>

<tasks>

## Task 1 — `PairingClient`: the unauthenticated half of the protocol

`APIClient` cannot be reused: it attaches a bearer token from the Keychain and throws `.notPaired` without one. Add a small actor covering exactly the three unauthenticated endpoints, sharing `PinningDelegate` so pairing and every later request agree on the trust anchor.

- `createRequest(baseURL:deviceCode:deviceName:platform:appVersion:) async throws -> PairingRequestHandle` (`id`, `displayCode`, `pollInterval`, `expiresAt`)
- `pollStatus(baseURL:requestID:) async throws -> PairingStatus` (`.pending`, `.approved`, `.denied`, plus `.slowDown` surfaced as a typed error, not a status)
- `redeem(baseURL:requestID:deviceCode:) async throws -> RedeemedCredential` (`deviceID`, `credential`, `fingerprintPrefix`)

Decode RFC 9457 problem+json into the existing `APIError` and map `code` to a typed `PairingError` — `expired`, `alreadyRedeemed`, `notApproved`, `slowDown`, `notFound` — so the coordinator branches on a value, never on a message string.

`deviceCode`: 32 bytes from `SecRandomCopyBytes`, base64url-encoded, generated once per ceremony and held only in memory.

## Task 2 — `PairingCoordinator`: the ceremony as a testable type

Owns the state machine and nothing else. No `URLSession`, no SwiftUI, no Keychain construction of its own — all three injected.

```
idle -> requesting -> awaitingApproval(displayCode, expiresAt) -> redeeming -> paired(deviceID)
                                                                            \-> failed(PairingError)
```

- Polls at the server-advertised `pollInterval`, never faster; on `.slowDown`, doubles the interval for the next attempt (capped) rather than retrying immediately.
- Stops on `expiresAt` with `.expired` rather than polling a dead request.
- On `.approved`, redeems once, writes through `KeychainStore.storeCredential`, and only then reports `.paired`.
- Cancellable: the user closing the sheet must stop the poll loop.

## Task 3 — Certificate capture

`PinnedCertificateCapture` records the server's trust anchor during the pairing handshake and, on a successful redeem, writes it to `AppPaths.root/pinned-ca.der` with `0600`. Written **after** the credential is stored, so a failed pairing never leaves a pin behind that would break a later attempt against a re-issued certificate.

Trust-on-first-use is the security model here and the plan should say so plainly: the ceremony trusts the certificate presented at pairing time and pins it from then on.

## Task 4 — `PairingView` and its two reachable call sites

A sheet, shaped after `AdapterSetupView`: server URL field, "Request pairing" button, then the display code rendered large with an instruction to approve it in the server's devices console, then a success or a typed failure.

Reachable from:
1. `LibraryShellView`'s empty state — the `ContentUnavailableView` at :469-477 gains a real action button. This is the string that has been lying since Phase 3.
2. The app menu, so a user who is already paired can re-pair against a new server.

Add `AccessibilityIdentifiers.Surface.pairing = "playstead.surface.pairing"` and register it in `Surface.all`, which is what the cross-layer allowlist anchors check.

## Task 5 — Tests at three levels

- **Unit** (`PairingCoordinatorTests`, unit layer): the full state machine against `StubURLProtocol`. Every one of the four server refusals reaches a distinct terminal state. Poll cadence honours `pollInterval` and backs off on 429. A cancelled ceremony stops polling. The credential is written exactly once.
- **Reachability** (`PairingReachabilityTests`, unit layer): source-level, in the shape this codebase already uses for #37/#45/#46 — `LibraryShellView` presents `PairingView`, and the empty state's description string and its action button are in the same view. A pairing surface nothing opens is this window all over again.
- **Live server** (`PairingCeremonyTests`, live-server layer): the real ceremony against the real Phoenix. The fixture approves the request server-side (`live-server.sh` already knows how); the app under test drives request, poll, redeem, and Keychain write; the test asserts a subsequent authenticated call succeeds. Promote it to a `--required-test` **only after it has genuinely executed and passed once** — a required test that has never run is the exact mistake #58 recorded.

Register every new test in the matching `.xctestplan`; the test-plan-registration guard fails otherwise.

<risks>
- **Certificate capture is the least-proven step.** `URLSessionDelegate` gives the server trust chain at challenge time, but which anchor to persist depends on the deployment (Caddy internal CA vs. a public certificate). If capture cannot be made reliable within budget, ship the ceremony without it and record the pin as a separate window rather than writing a file `APIClient` will then trust wrongly.
- **The live-server test needs an approval step**, which is normally a human clicking in the console. `live-server.sh` already performs it programmatically; reuse that, do not add a test-only bypass to the server.
- **Sheet focus and text reading.** Both known macOS traps in this codebase; budget for them rather than discovering them in a 30-minute hosted run.
</risks>
