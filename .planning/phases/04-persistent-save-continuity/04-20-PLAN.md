<objective>
Make a locally-captured save a first-class local object: its bytes in the CAS, and permanently off the reclaim menu.

Purpose: 04-19 made capture run, but the promoted bytes never enter the CAS. `bytesLocal` is therefore false for every save this Mac captured itself, so restore-from-history cannot materialize a revision the user created on this very machine until it round-trips through the server. Same-device continuity still works (the live `.sav` persists), so this is a history/restore hole rather than a data-loss one — but it is the last place where a save the app captured is not really local.

Output: capture bytes committed to the CAS at promotion, and an eviction path that structurally cannot offer a save blob for deletion.
</objective>

<task id="1" title="Protect save blobs from the reclaim menu — BEFORE they enter the CAS">
<action>
Do this task first. The ordering is deliberate: committing save bytes into the CAS while `unreferencedObjects()` still treats them as unreferenced would, for the duration of one commit, present a user's only save copy in StorageView as removable junk.

Give `EvictionPlanner` a `SaveStore` and have `unreferencedObjects()` exclude any sha that appears as a `blobSHA256` on a save revision. Update both construction sites (`PlaysteadApp.swift:496`, `UITesting/DeterministicProfile.swift:263`).

Leave `plan(for:)` and `candidates()` untouched — both select only catalogue-required member SHAs, so save blobs are already structurally outside them. Say so in a comment rather than adding a redundant filter.
</action>
<acceptance>
- `EvictionPlannerTests` covers: a sha backing a save revision does not appear in `unreferencedObjects()`; a genuinely orphaned sha still does.
- `plan(for:)`'s output is unchanged for an existing test fixture.
</acceptance>
</task>

<task id="2" title="Commit capture bytes into the CAS at promotion">
<action>
Give `SaveSessionCoordinator` a `CASManager` and, at the point it persists a promoted (and baseline) capture, commit that capture's bytes via `CASManager.commit(partialAt:sha256:)` using the digest the poller already computed — never recomputed here.

Commit before `SaveStore.insertRevision`, so a revision row never exists claiming bytes the CAS does not have. A commit failure must be handled the same way 04-19 handles a capture failure: recorded via `SaveCaptureBlockedState`, never thrown to the Play path, and never fatal to the launch.

A digest already present in the CAS is a no-op, not an error — the same bytes can legitimately arrive twice (a replayed session, a byte-identical capture).
</action>
<acceptance>
- `grep -n "casManager" playstead-mac/Playstead/Saves/SaveSessionCoordinator.swift` returns the property and the commit call.
- A test drives capture-then-end and asserts `casManager.contains(promotedDigest)` is true.
- A test asserts that a CAS commit failure leaves the launch unaffected and is recorded as blocked.
</acceptance>
</task>
