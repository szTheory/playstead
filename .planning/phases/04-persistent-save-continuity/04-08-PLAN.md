Fill Phase 2's reserved `saves` export slot with the deterministic revision layout and the readable manifest PORT-01 asks for.

Purpose: Phase 2 already cut the socket — `layout.ex` computes `saves_path`, both sidecars carry the reserved `saves` key, and `sanitize.ex` already guards a member literally named `saves` with a passing test. </objective>

  <behavior>
    - Given one linear line of three revisions, the plan names them `000001-<digest8>.sav`, `000002-…`, `000003-…` in `recorded_at` order.
    - Given a fork, revisions on each branch carry a branch letter derived from a stable `branch_key`, and the letters are the same across two independent planning runs.
    - Renaming the origin device between two planning runs produces identical filenames.
    - Appending a fourth revision and replanning leaves the first three revisions' names and sequence numbers unchanged.
    - A linear slot's plan includes a drop-in entry `saves/{stem}.sav` whose stem is the primary member's original basename.
    - A diverged slot's plan includes no drop-in entry.
    - A revision with `save_kind` other than the system-save kind produces no drop-in entry.
    - Planning the same inputs twice produces equal plan structs — the module makes no database, filesystem, or clock call.
    - A set with zero revisions produces a plan with an empty entry list and no error.
    - A member literally named `saves` is routed through the existing `Sanitize.reserved_saves_name?/1` rename path.
  </behavior>
  <action>
Add `Playstead.Export.SavesPlan` as a pure planner modelled on `Layout.plan_set/2`: it takes already-loaded revision and branch data plus the set's member information and returns a plan struct. It performs no `Repo` call, no file I/O, and reads no clock — the caller loads the data and passes it in. The `Export → Saves` coupling exists at the context boundary only, and `Layout` never aliases the saves context.

Filenames follow `{seq:06}[-{branch}]-{digest8}.{ext}`. `seq` is allocated in server `recorded_at` order and is stable under append: a previously assigned sequence number is never reused or shifted when new revisions arrive. The optional branch letter is derived from a stable, fork-inherited `branch_key` — never from a device name, because renaming a Mac must not rewrite a past export. `digest8` is a fixed-length prefix of the revision's raw artifact sha256 (the raw digest, not the manifest digest). The `ext` comes from the artifact, not from the display title.

A drop-in `saves/{stem}.sav` copy is produced for a linear slot, named from the primary member's original basename rather than the display title — naming it from the title reproduces a documented save-loss bug in another emulator front-end. The drop-in name is defined only for the system-save kind, so a save state can never earn one; a drop-in name is a portability claim. A diverged slot gets no drop-in copy at all: silently picking a side is last-write-wins performed by the export tool.

Route any member name that collides with the reserved `saves` folder through the shipped `Sanitize.reserved_saves_name?/1` guard. Write no new sanitize code — the guard already exists with a passing test; this module is simply its new caller.

Write `saves_plan_test.exs` covering the ten behaviours above.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| database content → filesystem paths | Revision digests, branch keys, and member basenames become file and folder names |
| exported bag → external verification | Users are told to run `sha256sum -c` against the exported manifest |
| export job re-enqueue → plan reconstruction | An Oban retry must not silently produce a different export |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-08-01 | Tampering | path traversal or collision via member/branch names in export paths | high | mitigate | All names route through the shipped `Sanitize.component/1` and `reserved_saves_name?/1`; no new path-building or sanitizing code is written |
| T-04-08-02 | Repudiation | a diverged history exported as one file | high | mitigate | `branches` is always present in the sidecar even when linear, and a diverged slot gets no drop-in copy — the export tool never picks a side |
| T-04-08-03 | Tampering | an incomplete bag that fails the user's own verification | high | mitigate | Missing revision bytes are named in the sidecar and deliberately kept out of `fetch.txt`, so `sha256sum -c` still succeeds; a test asserts it |
| T-04-08-04 | Repudiation | a re-run export silently differing from the first | medium | mitigate | `saves_scope` is persisted on `ExportRecord` and read by the worker; determinism is asserted as plan purity plus write reproducibility plus append-only stability, with the three exceptions enumerated |
| T-04-08-05 | Information Disclosure | export filenames leaking device identity | medium | mitigate | Branch letters derive from a stable fork-inherited `branch_key`, never a device name, so a rename cannot rewrite a past export and no device name reaches the filesystem |
| T-04-08-06 | Denial of Service | export of a very large revision history | low | accept | Accepted: revision artifacts are bounded at 8 MiB by plan 04-03 and the per-user backstops from plan 04-05 surface pressure before an export becomes pathological |
| T-04-08-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package-manager install occurs in this plan; RESEARCH.md's Package Legitimacy Audit records that this phase installs no external packages |
</threat_model>
