# Phase 4 Code Review — Mac/Swift

**Scope note:** Of the 42 files listed in `/tmp/gsd-scope-mac.txt`, this pass gave full-line-by-line attention to the 20 files most load-bearing for save-data safety per the review priorities (SaveCapturePoller, SaveSessionRecovery, SavePlanExecutor, LaunchSaveEnvironment, LaunchSaveContextBuilder, LaunchSavePlanner, SaveIntent, GameRowView, SaveStore, Migrations, SaveUploadLane, QuotaManager, AppPaths, AdapterHost, JournalApplier, SaveCompatibilityGate, SaveConflictResolver, UUIDv7, SaveArtifactSet, OnlyCopyEscalation). The remaining files in the list (ConflictComparisonSheet, SaveHistorySheet, SaveRollup, SaveStateModel, SaveVocabulary, SaveCaptureBlockedState, SaveAttentionSource, AdapterPin, APIClient, Outbox, SyncEngine, ReadinessCheck/Engine/Sheet/Remedy, ReclaimPromptView, StatusSlotView, StorageView, PlaysteadApp, UITesting/*) were not opened in this pass; findings below should not be read as clearing them.

## Summary

The launch path (`LaunchSavePlanner` → `SavePlanExecutor` → `LaunchSaveEnvironment`, wired into `AdapterHost.launch` via `GameRowView.play()`) is the strongest code in this set. It matches D-44's governing invariant closely: `LaunchSavePlanner.plan` is a pure function of already-local facts, the diverged case (`heads.count > 1`) is checked before ancestry is ever consulted, the only overwrite path (`fastForward`) requires the on-disk digest to be a proven ancestor, and `SavePlanExecutor` re-hashes unconditionally and never writes in place (stage → fsync → rename → fsync-directory, matching D-06/D-47 exactly). `AdapterLaunchMutex` correctly spans prepare→spawn→exit with a `releaseOnReturn` flag that prevents double-release once ownership transfers to the termination handler, and `executeSavePlan` runs strictly before `proc.run()`, with a throw aborting the whole launch — no path found where the emulator can spawn over an incomplete or unverified save write. `AppPaths`'s D-63 fix (clear stale root exclusion, then exclude only the five reconstructable directories, never `root`/`saves/`) is implemented correctly and appears idempotent.

No CRITICAL findings were confirmed: I did not find a reachable path that overwrites, corrupts, or silently discards save bytes, nor a network call on the launch path, nor a hole in the per-assetSetID mutex. The WARNINGs below are provenance/lineage-integrity and retry-correctness issues that either (a) don't lose bytes but can misattribute or discard *metadata* about a save's history, or (b) are non-atomic-write regressions in a lower-stakes rolling file, or (c) are unverified interactions with server-side idempotency semantics that the sibling Elixir review should confirm or rule out. Given the project's explicit priority on data safety, I'd rather flag these at WARNING with an honest "needs confirmation" than either bury them or inflate them to CRITICAL without proof.

## Critical Issues

None confirmed in the files read. (See Warnings — one item, WR-04, could turn out to be Critical depending on server-side Idempotency-Key semantics owned by the Elixir side; flagged as WARNING here specifically because I can't verify server behavior from the Mac-side code alone.)

## Warnings

### WR-01: Journal-applied `save` entries silently discard locally-captured provenance (tier/origin/manifestDigest/sessionID/artifactSetJSON) — **FIXED** (plan 04-17, commit `0386b81`)

**File:** `playstead-mac/Playstead/Sync/JournalApplier.swift:311-332`
**Issue:** `applySave` builds the `SaveRevisionRow` to upsert using `SaveRevisionRow`'s memberwise initializer without passing `tier`, `origin`, `manifestDigest`, `sessionID`, or `artifactSetJSON` — so all five take their defaults (`tier: "promoted"`, `origin: "session"`, the rest `nil`). `SaveStore.insertRevision` (`Persistence/SaveStore.swift:194-235`) does `ON CONFLICT(id) DO UPDATE SET` across *every* column, including these five. When the journal later echoes back a revision this same device originally captured and uploaded — a normal case in a poll/sync loop, not an edge case — this upsert overwrites whatever tier/origin/manifestDigest/sessionID that local row actually had.

Concretely: a `baseline`/`external` capture (D-04's "changed outside a session" case) that gets uploaded and then echoed back through the journal has its `origin` silently rewritten to `"session"` and its `tier` to `"promoted"` (harmless here since baseline rows are already effectively promoted, but the origin flip erases the "this was found already-changed on disk" provenance). More concretely damaging: `sessionID` gets nulled to `nil` for any revision affected this way. `SaveSessionRecovery.abandonedSessionIDs` (`Saves/SaveSessionRecovery.swift:49-54`) derives its "session left open" list by diffing `sessionID`s between `staged` and `promoted` rows for a line. If a promoted row's `sessionID` is scrubbed to `nil` by an intervening journal apply before the app can rely on it, that session's `staged` sessionID is never subtracted out, and `SaveSessionRecovery` will re-attempt recovery for a session that was, in fact, already promoted.

**Why it matters:** The recovery re-attempt is idempotent-by-digest so it doesn't insert a duplicate row — but this is happening by luck (a second safety net), not by design; the actual bug is that the sync spine is quietly destroying local provenance metadata for a device's own revisions the moment they round-trip through the journal, which undermines D-39's session-grouped save history (a revision's `session_id` disappearing breaks the grouping key `SaveHistorySheet` presumably relies on — not reviewed in this pass) and generally violates D-17's "provenance carried from day one" commitment.
**Fix:** Preserve the existing local row's tier/origin/manifestDigest/sessionID/artifactSetJSON when they are already known, rather than letting the journal-applied defaults clobber them — e.g. fetch the existing row (already done for `localPath` via `existingLocalPath`) and carry its tier/origin/manifestDigest/sessionID/artifactSetJSON forward when present, falling back to the journal payload's own values only when the row is new.

### WR-02: `SaveCapturePoller.write()` uses remove-then-move, not an atomic rename, for the rolling `staged` file — **FIXED** (plan 04-17, commit `b66dfdf`)

**File:** `playstead-mac/Playstead/Saves/SaveCapturePoller.swift:298-323`
**Issue:** For every capture (`staged`, `promoted`, and `baseline`), `write()` does: write temp file, fsync, then `if fileExists(finalURL) { removeItem(finalURL) }`, then `moveItem(tempURL, finalURL)`, then fsync the directory. For the **content-addressed** `promoted`/`baseline` case this is harmless (the finalURL name is the content's own digest, so removing and rewriting identical bytes is a no-op crash-wise). For the **staged** case, `finalURL` is the fixed rolling name `session-<id>.staged.sav`, and the new bytes are, by construction, *different* from what's currently there (a staged write only happens when the digest differs from the last-staged digest). A crash between `removeItem` and `moveItem` leaves that session's staged file completely absent rather than holding either the old or the new bytes.
**Why it matters:** This is exactly the hazard D-06/D-47 exist to rule out ("never write in place… a crash… leaves the prior file completely untouched, because the rename is the only step that ever touches the target path"). Here the code touches the target path twice (remove, then move) instead of using a single atomic `rename(2)` call (as `SavePlanExecutor.renameIntoPlaceDurably` correctly does for the restore path). In the worst case — a crash in that narrow window at the exact moment `settle()` writes the session's final staged capture — the staged snapshot for that session is lost. This is partially mitigated because `SaveSessionRecovery.replay` re-reads the *live* artifact from `artifactSource` rather than from the staged file, and because a subsequent session's `startSession()` baseline check will pick up any divergence from the last known head — so the underlying bytes are not permanently lost, only the specific `staged` capture artifact is, and only in a narrow crash window. Still, this is a real deviation from the "atomic rename, never remove-then-move" discipline the rest of the phase is built on, in a file whose own doc comments claim D-06 compliance.
**Fix:** Use the `rename(2)` syscall directly (as `SavePlanExecutor.renameIntoPlaceDurably` does) rather than `FileManager.removeItem` + `moveItem` — `rename()` atomically replaces an existing destination on APFS, making the existence check and separate removal unnecessary and closing the crash window.

### WR-03: `LaunchSaveContext`'s default `compatibilityVerdict` is `.exact`, the permissive value, not the safe one

**File:** `playstead-mac/Playstead/Saves/LaunchSavePlanner.swift:38-50`
**Issue:** `LaunchSaveContext`'s memberwise initializer defaults `compatibilityVerdict` to `.exact` when a caller omits it. The one production call site (`LaunchSaveContextBuilder.buildContext`) always passes this parameter explicitly, so it is not exploitable today. But `.exact` is the one value that causes `LaunchSavePlanner.planIntoEmptiness` to silently auto-restore onto the launch path (`LaunchSavePlanner.swift:180-187`) — it is the *permissive* default, not the *safe* one. D-24's own stated posture is "the gate degrades toward strictness when identity is unknown"; a default that instead degrades toward permissiveness when a future caller simply forgets to pass a real verdict is the inverse of that policy.
**Why it matters:** This is a latent footgun rather than a live bug: nothing currently constructs `LaunchSaveContext` without passing `compatibilityVerdict`. But defaults are exactly the kind of thing a later, smaller change (a new test helper, a refactor of `buildContext`, a future call site added under time pressure) reaches for without re-reading this file's invariant — and the blast radius of getting it wrong is a silent auto-restore that D-44 was explicitly designed to prevent.
**Fix:** Default `compatibilityVerdict` to `nil` (which routes through `keep(notice: nil)` rather than an auto-restore) and require production call sites to opt into `.exact` explicitly, or remove the default entirely so every call site must state its intent.

### WR-04: `SaveUploadLane` mints a fresh `command_id` on every retry of the same revision, which may defeat the metadata commit's idempotency (needs confirmation against server-side `Idempotency` semantics)

**File:** `playstead-mac/Playstead/Saves/SaveUploadLane.swift:77-121`
**Issue:** `uploadAndCommit` generates `commandID = UUIDv7.generate()` fresh on every call, including retries of the same `revision.id` after a prior attempt's `PUT` succeeded but the subsequent `POST /saves/revisions` failed or timed out before the response was read. The `command_id` is included in the POST body (`params["command_id"] = commandID`) sent to the idempotent-commit endpoint. Per the phase's own design notes (04-CONTEXT.md D-16: "`Idempotency.fingerprint/1` canonicalizes a *parsed body*"), if the server's idempotency check for `POST /api/v1/saves/revisions` fingerprints the request body (which would include `command_id`), then two attempts of "the same" logical commit produce two different fingerprints under the same `Idempotency-Key` header (`"save-revision-\(revision.id)"`). Depending on how the server reconciles a same-key/different-body replay, this could either (a) silently create a second revision row from the same local capture, or (b) cause the server to reject the replay as a key-reuse conflict, which — combined with this lane's "never quarantine, retry forever" policy (`Sync/SaveUploadLane.swift:28-34`) — would leave the revision stuck retrying indefinitely with a body that will never match, never actually delivering it to the server while still reporting non-silently as `queued`.
**Why it matters:** If (a) is what happens, it's a lineage-integrity issue (duplicate revision, not byte loss). If (b) is what happens, it's effectively a permanent, non-obvious upload failure disguised as ordinary retry — the revision never becomes `.uploaded`, and because D-32's policy is "never silently terminal," it will keep visibly retrying without ever succeeding, which is honest but never actually resolves. Either outcome is worth confirming against the Elixir-side `Idempotency` module and the `saves/revisions` controller before shipping.
**Fix:** Mint the `command_id` once per revision (e.g., derive it deterministically from `revision.id`, or store the first-attempt `command_id` alongside the revision row) and reuse the same value on every retry of that revision's commit, so a retried POST body is byte-identical to the original and any idempotency-key-plus-body check on the server actually recognizes it as the same request.

### WR-05: `SaveStore.fetchHead` breaks ties on `rowid DESC` when a line has diverged, which may seed the wrong branch as "the" head for capture continuation (needs confirmation)

**File:** `playstead-mac/Playstead/Persistence/SaveStore.swift:261-278`
**Issue:** `fetchHead` (singular) is documented as "the current head... used by the capture poller to decide same-device byte-identical de-dup (D-30) and to derive the next capture's `parent_revision_id`." When a line has genuinely diverged (more than one row with no children), this query still returns exactly one row — whichever has the highest `rowid` — with no guarantee that row corresponds to the branch *this device* was last extending. If a remote device's head is journaled in (via `JournalApplier.applySave`, which inserts new rows with fresh, and therefore later, `rowid`s) after this device's own most recent local capture, a subsequent `fetchHead` call would surface the *other* device's branch as `knownHeadDigest`, not this device's own.
**Why it matters:** `SaveCapturePoller` uses `knownHeadDigest` both to suppress redundant staged captures on byte-identical reads (D-30) and, via callers, as the parent for the next promotion. Seeding it with the wrong branch's digest in a diverged scenario risks parenting a new local capture off a revision this device never actually played from — a lineage/provenance error rather than data loss (nothing is overwritten, per D-46/D-47's "never write in place" and the launch planner's own `heads.count <= 1` divergence guard), but still a violation of D-46's "playing extends only the local branch" intent if this code path is reached with more than one head present. I could not confirm from the reviewed files alone whether the actual capture-session wiring ever calls `fetchHead` while a line is diverged (the wiring that connects `SaveCapturePoller` to a live play session was outside this pass's file set), so I'm flagging this as needing confirmation rather than asserting it fires in practice.
**Fix:** Either make `fetchHead`'s divergence behavior explicit and safe (e.g., only ever call it after confirming `fetchHeads(...).count <= 1`, or have it return `nil`/throw when more than one head exists, forcing callers to handle divergence deliberately) or document at the call site why an arbitrary tie-break is safe there.

### WR-06: `GameRowView.play()` sets `saveLaunchNotice` before knowing whether the save plan actually executed successfully

**File:** `playstead-mac/Playstead/Library/GameRowView.swift:379-396`
**Issue:** `saveLaunchNotice = saveLaunch.notice` is assigned immediately after building the plan, *before* `adapterHost.launch(...)` — which is what actually runs `executeSavePlan` — is even called. If `executeSavePlan` throws (e.g., `SavePlanExecutorError.digestMismatch` from a corrupted CAS object, or `.preRestoreCaptureFailed`), `adapterHost.launch` itself throws, execution falls into the outer `catch { status = .error(...) }`, and the emulator never spawns (correct, matches D-44) — but `saveLaunchNotice` has already been set to a notice describing a restore/keep that did *not* actually happen (e.g., "Picked up from your {deviceName} save… Nothing on this Mac was replaced" when in fact nothing was restored at all because the attempt aborted).
**Why it matters:** Currently low-severity in practice because, per the code's own comment, no view in this codebase yet renders `saveLaunchNotice` ("No detail view exists yet... this property is the seam a future plan wires up"). But the state is being held specifically so a future view can render it, and as written it would show a confident, specific, false statement about what happened to the user's save on a failure path — exactly the kind of thing D-45's "silent auto-restore is safe only because D-44 gates it" reasoning depends on being trustworthy. Left as-is, this bug will ship silently the day someone wires up the detail view, unless they happen to re-derive the invariant themselves.
**Fix:** Set `saveLaunchNotice` only after `adapterHost.launch` (and thus `executeSavePlan`) has returned without throwing — or clear/suppress it in the `catch` block so a failed launch never leaves a stale success-shaped notice in state.

### IN-01: `SaveCompatibilityGate.evaluate` is only ever called with `candidate == target` in the reviewed launch-path caller, making most of its branches unreachable there

**File:** `playstead-mac/Playstead/Saves/LaunchSaveContextBuilder.swift:81-106`
**Issue:** `compatibilityVerdict(for:contentKey:saveKind:)` builds a single `SaveBinding` and calls `gate.evaluate(candidate: binding, target: binding)` — comparing the binding to itself. The method's own doc comment explains this is deliberate ("There is no independent on-disk binding to compare against when restoring into emptiness… so the target binding is built from the same facts as the candidate") and that the only branch that can actually fire is the `mediumID == nil` hard block. This is not a bug — I traced through `SaveCompatibilityGate.evaluate` and confirmed every other guard trivially passes when `candidate == target` by construction — but it means most of `SaveCompatibilityGate`'s cross-line/`same_title` logic (title-identity widening, `romSHA256` mismatch handling) is currently dead code from this call site's perspective. Worth confirming this gate's richer branches are actually exercised from wherever D-19's `same_title` cross-line restore path lives (not in this file set as reviewed).
**Fix:** None required if confirmed; otherwise a comment at the call site noting explicitly which SaveCompatibilityGate branches are exercised from which callers would help a future reader avoid re-deriving this by hand.

### IN-02: `SaveSessionRecovery.replayAll` re-reads the *current* live artifact for every abandoned session in a line, not each session's own historical bytes

**File:** `playstead-mac/Playstead/Saves/SaveSessionRecovery.swift:56-127`
**Issue:** When more than one `sessionID` is classified as abandoned for a line (e.g., two crashes in a row before a successful promotion), `replayAll` loops over each abandoned session and calls `replay`, whose `settle()` step reads bytes from `session.artifactSource` — the live, single, on-disk `.sav` file — not from that specific session's own staged snapshot (`session-<sessionID>.staged.sav`). Because there is only one physical artifact, every iteration reads the same current bytes; the loop is effectively idempotent-after-first-success (confirmed by tracing `alreadyRecorded`'s digest check), so no duplicate or wrong data gets written. This matches the single-artifact model the phase is built around and is not a defect, but the session-to-bytes attribution ("session A's abandoned capture") is, in the multi-abandoned-session case, arbitrary (whichever `sessionID` sorts first lexicographically gets credit for the recovered promotion) rather than reflecting which session actually produced those bytes.
**Fix:** None required for correctness; if session attribution in the save history UI ever needs to be precise for a multi-crash recovery scenario, this is worth a closer look at that point.
