<objective>
Close the two Critical findings from the phase code review: a lineage-scoping hole that permanently corrupts provenance, and a set of save-lane limits that are fully specified and entirely inert.

Purpose: Both defects share a shape this project has now hit three times — code whose tests pass because they assert that machinery exists, never that it is reached. CR-01 lets a client link two games' lineages together in an append-only structure, so the corruption cannot be undone. CR-02 leaves a paired device able to upload save revisions with no rate limit, no concurrency cap, and no size ceiling, while `mix test` reports D-33 as covered.

Output: A same-save-line parent rule enforced in both the application and the database, the D-33 limits actually applied on the save upload and commit paths, and tests that fail when enforcement is removed rather than when a constant is renamed.
</objective>

Tighten `resolve_parent/2` so it resolves the parent within the save line being committed to, not merely within the user. The save line is already resolved earlier in `commit_revision/3`'s multi — thread it through rather than re-querying. Return the registered save problem code for an unknown or out-of-line parent; reuse the existing `save_parent_unknown` vocabulary if its wording covers this case, and only add a code if it genuinely does not.

Add migration `20260904000005_constrain_revision_parent_to_save_line.exs` enforcing the rule in the database. The standard shape: add a unique index on `save_revisions` `(id, save_line_id)` — redundant on its own, but it makes the pair a referenceable key — then replace the plain `parent_revision_id` foreign key with a composite foreign key on `(parent_revision_id, save_line_id)` referencing `save_revisions (id, save_line_id)`. This makes a cross-line parent unrepresentable rather than merely unwritten by current code.

The migration must NOT delete or rewrite existing rows. History is append-only. If pre-existing violating rows would block the constraint, detect and REPORT them with their ids in the migration output and fail loudly, so a human decides — never silently repair or drop.

Check whether plan 04-05's `save_revision_parents` edge table has the same hole and constrain it identically if so.

Add `saves_lineage_scoping_test.exs` proving: a cross-line parent is refused with the expected problem code; a same-line parent still succeeds; a nil parent still succeeds; a cross-user parent is still refused; and a direct `Repo.insert` bypassing the context is rejected by the database constraint.

Apply the limits that already exist. Add the save-upload route to a scope that runs the concurrency plug with the SAVE namespace, so `save_upload_slot_key/1` is what gates it.

One real design point to decide and record rather than paper over: the `:upload_concurrency` pipeline's own comment states it must run after `:idempotency` so a replayed request never consumes a slot — but the save-upload route is deliberately off `:idempotency`, because `Idempotency.fingerprint/1` cannot fingerprint a stream (D-16). Decide explicitly how a retried save upload avoids consuming a second slot: either key the slot on the `command_id` in the path (which is stable across retries of the same upload, and is the natural fingerprint a stream does have), or release the slot on connection teardown. State the choice and its reasoning in the SUMMARY.

Invoke the rate limit on the metadata-commit path, mirroring how the imports path applies its own limit. Enforce `max_save_revision_bytes/0` against the declared length before streaming bytes.

Every refusal uses a save problem code registered in plan 04-03 with its decided status.
