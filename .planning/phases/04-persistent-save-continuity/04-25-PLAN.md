<objective>
Close `SaveOutboxDrainTrigger.fire()`'s time-of-check/time-of-use race so the single-lane drain guarantee the type exists to provide is actually true.

Purpose: 04-VERIFICATION confirmed directly against `SaveOutboxDrainTrigger.swift:41-61` that the read of `_lastTask` and the write of the new task happen in two separate locked sections. Two concurrent `fire()` calls — plausible when a resolution is enqueued at the same moment reachability flips online — can both read the same stale predecessor and both call `SaveOutbox.drainOnce` concurrently, so both passes see the same pending entry before either `markDone` deletes it. This defeats the type's own documented invariant and the specific concurrency truth 04-23's frontmatter declared. It was flagged rather than scored as a criterion-5 failure only because the server's `device_id` + `idempotency_key` receipt layer deduplicates the duplicate send; the client-side guarantee is still false.

Output: one critical section in `fire()`, a test that genuinely races `fire()` from separate threads and observes that `drainOnce` is never in flight twice, and a deterministic source-level gate that goes red the moment the two sections are split again.
</objective>
