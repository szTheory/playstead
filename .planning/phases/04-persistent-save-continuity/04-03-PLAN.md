<objective>
Fix the server-side inherited defect that refuses save uploads (D-64) and register the failure vocabulary and limit namespaces the save endpoints will need (D-33).

Purpose: `Readiness.required_bytes/2` computes `requested + max(1 GiB, 5% capacity)` and gates `LocalDisk.open_write/1`, so a 32 KB save upload is refused with 507 whenever the blob volume is under ~1 GiB free — the server rejects the one artifact that cannot be reconstructed in order to reserve space for artifacts that can. This plan makes the reserve additive and leaves the general margin exactly as shipped.

Output: `open_write/2` with `reserve: :critical` and a 64 MiB hard floor, six registered problem codes, and a `save:`-namespaced upload-slot accounting path — all extensions of shipped machinery, no parallel implementations.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| device → blob volume | A device-authenticated upload consumes finite server disk |
| save write ↔ game-byte write | Two classes of write share one volume with different reconstructability |
| error code registry → client microcopy | Clients key user-facing save failure copy off the machine code only |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-03-01 | Denial of Service | `open_write/2` `reserve: :critical` | high | mitigate | The reserve bypasses only the `required_bytes/2` margin; a 64 MiB physical hard floor still refuses the write, and a behaviour test proves refusal below the floor |
| T-04-03-02 | Denial of Service | unbounded save uploads exhausting the volume | high | mitigate | 8 MiB per-artifact cap enforced during streaming (`save_revision_too_large`, 413), 120 revisions/hour/device via the shipped `RateLimiter`, and `save:`-namespaced `UploadSlots` concurrency accounting |
