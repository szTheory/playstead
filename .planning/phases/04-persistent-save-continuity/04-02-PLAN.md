<objective>
Fix the three Mac-side defects that each independently block a Phase 4 success criterion on its own terms: the Time Machine exclusion boundary (D-63), the missing launch mutual exclusion (D-65), and the too-weak `saveDirectory` readiness check (D-42).

Purpose: These are defects in already-shipped Phase 2/3 behaviour, not new capabilities. Three of eight independent research agents found D-63 unprompted — CONTEXT.md names that convergence as the strongest signal in the fan-out and asks for it to be sequenced early. Nothing later in the phase is safe until a second emulator cannot open the same `.sav`.

Output: Per-directory backup exclusion with an idempotent stale-flag clear, a per-`assetSetID` launch mutex spanning prepare → spawn → exit, and a `saveDirectory` check that proves a file can actually be placed rather than that a directory is nominally writable.
</objective>

    - Given a fresh root, after init: the root URL itself reports `isExcludedFromBackup == false`.
    - Given a fresh root, after init: a `saves/` subdirectory and a `playstead.sqlite3` file placed under the root report `isExcludedFromBackup == false`.
    - Given a root that already carries `isExcludedFromBackup == true` (the existing-install case), after init the root reports `false` and the five managed directories report `true`.

  <action>
Replace `excludeRootFromBackup(fileManager:)` with two functions on `AppPaths`.

`excludeReconstructableDirectoriesFromBackup(fileManager:)` iterates exactly `[objects, partials, launch, emulators, bios]` and sets `URLResourceValues.isExcludedFromBackup = true` on each — never on `root`, and never on the saves directory. The saves directory is deliberately absent from the managed list already, so it becomes Time-Machine-eligible by omission rather than by an explicit `false` write.

`clearStaleRootBackupExclusion(fileManager:)` reads `root`'s `isExcludedFromBackup` resource value and, when it is `true`, writes `false`. It must be safe to call on every launch: when the flag is already `false` or absent it performs no write and returns without error. This is the migration path for installs shipped before this fix, where the root flag inherited down to `saves/` and `playstead.sqlite3`.

Call `clearStaleRootBackupExclusion` and then `excludeReconstructableDirectoriesFromBackup` from `init(root:fileManager:)`, after `createDirectoriesIfNeeded(fileManager:)`, in that order — clearing first so a root-level `true` can never re-inherit onto a directory whose own flag is being written in the same pass.

Keep the existing `try?`-tolerant style of the file: a resource-value write failing on an exotic volume must not prevent app launch.

Write `AppPathsBackupExclusionTests.swift` under `PlaysteadTests/CacheTests/` covering the five behaviours above, each against a fresh temporary root created and torn down per test. Register the new file in `playstead-mac/TestPlans/Unit.xctestplan` if that plan enumerates files explicitly; if it enumerates targets, no registration change is needed.

  <action>
Add an `AdapterLaunchMutex` sibling to `AdapterProcessRegistry` in the same file, following the identical locking discipline: a `final class ... : @unchecked Sendable` with a `static let shared`, a private `NSLock`, and a private `Set<String>` (or dictionary keyed by `assetSetID: String`). Expose `tryAcquire(assetSetID:) -> Bool` and `release(assetSetID:)`. `tryAcquire` returns `false` — it does not block — when the key is already held, so the caller can surface an ordinary refusal rather than deadlocking the UI.

Wire it into `AdapterHost`'s launch path so the mutex is held across the whole prepare → spawn → exit span: acquire before any save-directory preparation or materialization work begins, release exactly once when the spawned process's termination is observed by the same mechanism `AdapterProcessRegistry` already uses. Release must be idempotent — releasing a key that is not held is a no-op, never a precondition failure.

When `tryAcquire` returns `false`, the launch must fail with a distinct, non-fatal error case that the caller can render; do not silently proceed and do not spawn a second process. Do not branch any of this on `AdapterExit`'s classification — the mutex releases on termination regardless of which of the four cases the classifier returns (D-05).

Write `LaunchMutexTests.swift` under `PlaysteadTests/AdapterTests/` covering the five behaviours above, driving the mutex directly rather than spawning a real emulator.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| app → user's backup system | `isExcludedFromBackup` decides whether irreplaceable bytes reach Time Machine |
| two launch attempts → one save artifact | Concurrent emulator processes share one 32 KB mmap-backed file |
| readiness check → launch path | A false-ready verdict lets the emulator spawn against a save path it cannot write |

| T-04-02-02 | Tampering | concurrent emulator writes to one `.sav` | high | mitigate | `AdapterLaunchMutex` keyed by `assetSetID`, held across prepare → spawn → exit, released on termination regardless of `AdapterExit` case; `tryAcquire` returns false rather than spawning a second process |
