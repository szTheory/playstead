<assumption_delta_decision>
**Noun now primary:** the *save line*, identified by `(user_id, content_key, save_kind, slot)` where `content_key` is the ROM sha256 (D-10).

**Decision:** `promote`. Before this phase a save was implicitly a per-device file at a per-game path. This phase introduces a second device producing revisions of the same progress, which is exactly the singular→plural transition. The generalized identity — the save line — is promoted to the primary key of the model, and "the save on this Mac" is demoted to one device-scoped view (`current`) of one revision on that line. Adding a device-keyed save alongside a line-keyed one would reintroduce last-write-wins by structure, which D-14 forbids.

**Rationale:** `save_kind` and `slot` ship day one even though only `"battery"`/`"0"` exist, because both are unrecoverable if omitted from a published payload (D-10). `content_key` is the ROM sha256 rather than `asset_set_id` so a re-import cannot orphan every save on a game.

**Companion invariant test (accepted):** `saves_test.exs` asserts that two revisions committed by two different devices against the same `(user_id, content_key, save_kind, slot)` land on one save line, for every supported `save_kind` value.
</assumption_delta_decision>

  <action>
Build the single path, one file per layer, no second call sites and no batching.

**Server schema and migration.** Create `save_lines` with a client-suppliable `binary_id` primary key, `user_id`, `content_key` (the ROM sha256, a 64-char lowercase hex string), `save_kind` (default `"battery"`), `slot` (default `"0"`), and timestamps; add a unique index on `(user_id, content_key, save_kind, slot)`. Create `save_revisions` with a `binary_id` primary key, `user_id`, `save_line_id` FK, a nullable `parent_revision_id` self-FK, `blob_sha256`, `size_bytes`, `origin_device_id`, `device_captured_at`, and a server-assigned `recorded_at`; add the index on `(save_line_id, parent_revision_id)` that D-10's Discretion note names as required for branch-head derivation. Forward-only migration; follow the existing curation migrations' shape for binary-id PKs and user scoping.

**`Playstead.Saves` context.** `Playstead.Saves.commit_revision/3` takes the scope (`user_id`), the device, and the commit attributes, and performs D-26's exact four-step order inside one `Ecto.Multi`: resolve-or-insert the save line, commit the pending blob through `Playstead.Blobs` (never through the store directly, never reimplementing fsync/rename), insert the `save_revisions` row, append the `save` journal entry through the same `ChangeJournal` call the curation context uses. The idempotency receipt is written by `Idempotency.execute/4` around the whole thing at the controller layer, matching `curation_controller.ex`. Copy curation.ex's moduledoc discipline note about the row and the journal entry living in one `Ecto.Multi`, never separate transactions. The context knows nothing of CAS layout and `blobs` learns nothing about saves.

**`Playstead.Sync.SavePayload`.** Follow `CurationPayload` exactly: `@frozen_keys`, an inner `type`, and a builder that produces the journal payload. Carry from day one: `origin_device_id`, `capture_method`, adapter id and version, `save_format`, `format_confidence`, `blob_sha256`, `size_bytes`, and a nullable `play_session_id`. Lineage itself lives in the `save_lines`/`save_revisions` tables and not in the journal, because `Compaction.run/0` deletes journal rows at 90 days and journal-only lineage would have a 90-day event horizon.

**Two endpoints.** `SavesController` gets both halves in one module. `PUT /api/v1/saves/uploads/:command_id` copies `imports_controller.ex`'s `body_stream/1` and `@chunk_size` verbatim, requires `Repr-Digest` and `Content-Length`, streams into `Playstead.Blobs.put_stream/3` with `reserve: :critical`, enforces the 8 MiB cap during streaming returning `save_revision_too_large`, and produces a TTL'd pending blob keyed by the command id. `POST /api/v1/saves/revisions` copies `curation_controller.ex`'s `run_idempotent` shape and calls `Saves.commit_revision/3`. Both routes live under `:device_auth`; the metadata commit additionally runs the `:idempotency` pipeline, the streamed upload does not fingerprint its body. Delegate every non-2xx branch to the existing `action_fallback PlaysteadWeb.Api.V1.FallbackController` and use only the codes registered in plan 04-03.

**Mac local store.** Add `SaveStore.swift` following `CurationStore.swift`'s shape, plus a forward-only block in `Migrations.swift` creating local `save_line` and `save_revision` tables mirroring the server's identity tuple, with a local `durability` column taking one of `localOnly`, `queued`, `uploaded`. Never model these three as one enum shared with `current`/`restored`/`conflicted` — those are separate axes handled in plan 04-09.

**Mac capture, thin.** `SaveCapturePoller.swift` is an actor that, while a game session is open, reads the adapter-declared artifact once per second, hashes the whole buffer with a one-shot `SHA256.hash(data:)` (never `StreamingSHA256`, which is reserved for large or multi-file artifacts), and treats three consecutive identical digests as quiescence. On quiescence it performs D-06's write order exactly: whole buffer already in memory, one digest, write to a temp file, `fsync`, `rename`, `fsync` the containing directory, and only then insert the SQLite row. On session end it runs an unconditional settle pass and promotes exactly one revision for the session. The settle pass must not branch on any `AdapterExit` case. Capture runs under the `AdapterLaunchMutex` established in plan 04-02.

**Mac upload lane.** `SaveUploadLane.swift` reuses `OutboxWorker`'s actor-serialized in-order drain, exponential backoff, and attempt cap, and is drained ahead of the curation outbox and downloads. For one revision it performs the two calls in order — streamed upload, then idempotent metadata commit — and marks the local row `uploaded` only after the commit returns. It never reaches a silent terminal state; a lane entry that cannot progress stays visible (its attention surface arrives in plan 04-06).

Verify with `saves_controller_test.exs`: one test drives the full server path — upload bytes, commit metadata, assert a `save_revisions` row exists, its blob is readable back through `Playstead.Blobs` with a matching digest, and one `save` journal entry was appended — plus one replay test asserting the same idempotency key returns the original receipt and creates no second revision.
