<objective>
Close the three review Warnings that are concrete paths to degraded save durability: a non-atomic staged write, a journal echo that blanks local capture metadata, and a retention horizon that silently forgets a user already resolved a conflict.

Purpose: Each of these is individually survivable and none is exotic. Together they undermine the three properties the phase sells — that a capture in progress is safe, that crash recovery knows what it captured, and that a decision the user made once stays made.

Output: An atomic replace on the staged path, a column-preserving journal merge, and a compaction rule that keeps acknowledgment evidence while still expiring ordinary entries.
</objective>

  <name>Task 1: WR-02 — make the staged-save write atomic</name>
  <files>playstead-mac/Playstead/Saves/SaveCapturePoller.swift, playstead-mac/PlaysteadTests/SavesTests/SaveCaptureAtomicityTests.swift</files>
  <read_first>
    - `playstead-mac/Playstead/Saves/SaveCapturePoller.swift` lines 296-322 — the write helper: temp write, `fsync`, conditional `removeItem`, `moveItem`, directory `fsync`
    - `.planning/phases/04-persistent-save-continuity/04-SAVE-P1-REPORT.md` — the MEASURED APFS behaviour from plan 04-01; the fix must be consistent with what was measured rather than with what seems reasonable
    - `.planning/phases/04-persistent-save-continuity/04-CONTEXT.md` — D-06 and D-47, the decisions this code is meant to satisfy
    - `playstead-mac/Playstead/Persistence/` for any existing atomic-replace helper worth reusing rather than duplicating
  </read_first>
  <behavior>
    - Writing a staged save over an existing staged file replaces it in one step; no observable state has the target absent.
    - The previous staged file remains readable right up until the replacement is in place.
    - A failed write leaves the previous staged file intact and removes the temp artifact.
    - The directory entry is durable before the write is reported complete.
    - Writing where no previous file exists still succeeds.
    - The payload is never read back and rewritten — the replacement moves the file, it does not copy its bytes.
  </behavior>
  <action>
Replace the `removeItem` + `moveItem` pair with a genuinely atomic replace. `rename(2)` overwrites an existing destination atomically on APFS — Darwin's `FileManager.moveItem` refuses an existing destination, which is why the remove was added, so use the syscall directly or `FileManager.replaceItemAt(_:withItemAt:)`. Preserve the existing `fsync` of the file and of the containing directory; the ordering (data durable, then rename, then directory durable) is what makes the guarantee hold across a crash.

Keep the temp-file cleanup on the failure path.

Add `SaveCaptureAtomicityTests.swift` asserting: an existing staged file is never observably absent across a replace; a write failure leaves the prior file intact; a first write with no prior file succeeds; and the implementation performs no read-back of the payload. Assert the absence of the remove-then-move shape directly, so the regression cannot return silently.
  </action>
